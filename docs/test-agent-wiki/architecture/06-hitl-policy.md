# 06. 人工介入与审批

[返回目录](./index.md)

## 1. 人工介入不只有批准按钮

| interaction_type | 场景 | 可选动作 |
| --- | --- | --- |
| clarify | 100 是并发数还是请求速率 | 选择或补充 |
| choose_plan | 多种业务路径需用户确定 | 选择方案或修改目标 |
| approve_action | 对被测系统执行动作 | 批准一次、在范围内批准、拒绝 |
| reauthenticate | 业务会话失效 | 重新登录或取消 |
| resolve_evidence | 流程图分支或结果矛盾 | 标注、补充材料、保持未知 |
| reconcile | 副作用是否发生不明确 | 核对事实后决定, 不直接重复 |

用户说“可以”必须对应当前明确等待项. 存在多个待处理事项时要求选择, 不批量推断同意.

## 2. 审批流程

[![策略检查、自动批准、人工决定和重新校验流程](/images/test-agent-wiki/05-hitl.svg)](/images/test-agent-wiki/05-hitl.svg)

首先检查硬边界, 然后检查授权范围, 最后才决定是否询问. 用户修改参数必须回到校验入口. “帮我批准”仍不能跨过系统硬边界.

Codex 将沙箱范围与审批策略区分, 本项目借鉴这一分离原则, 不宣称复制其所有内部实现. [官方审批说明](https://learn.chatgpt.com/docs/agent-approvals-security)

## 3. 三种用户模式

| 模式 | 允许自动进行的工作 | 仍需介入 |
| --- | --- | --- |
| 手动确认 | 普通回答、范围内只读准备 | 有副作用的动作, 歧义和重新认证 |
| 帮我批准 | 硬规则确认的低风险动作, 已授权目标与参数范围 | 不确定动作、越界参数、不可验证脚本、危险环境 |
| 授权范围内自动执行 | 用户明确授权包内的步骤 | 目标/脚本/负载越界、凭证失效、语义不清 |

“帮我批准”的首期实现建议是确定性策略, 不是另一个拥有无限权限的模型. 将来使用模型辅助风险分类时, 只能提高审查要求或提供依据, 不单独突破规则授予权限.

授权包包含目标集合、环境、工具集合、允许动作、最大负载、截止时间、脚本哈希/版本及适用 task/run. 不能只保存 allow_all=true.

## 4. 绑定与执行前复核

审批对象最小包含 approval_id、requester_id、task_id、action_id、normalized_params_hash、script_hash、target_set、policy_version、expires_at、decision_version.

批准和执行之间存在时间差. 启动前再次验证: 用户会话/委托仍有效, 参数和脚本未变, 目标未变, 策略未收紧, 审批未过期. 任一改变则重新评估, 不复用旧批准.

审批检查通过后原子记录工具调用与任务版本. 直接调用任务 API、Skill 脚本或表单入口都不能跳过这一逻辑.

## 5. 等待与恢复

- 等待项和图检查点持久化后, 释放模型连接和运行槽位.
- 用户可以关闭客户端; 重新登录后查询未处理事项.
- 两个窗口同时回复时, 通过 decision_version 只接受一个决定, 另一个返回 409.
- 用户修改参数: 新参数版本 → 重新预检 → 新审批, 不在旧决定上附加备注后执行.
- 拒绝: REJECTED, 记录拒绝原因但不要求用户解释.
- 超时: EXPIRED, 再次执行需新请求.
- 用户撤销未执行批准: 使授权失效; 已执行部分只能停止后续动作, 不能承诺回滚业务系统.

## 6. 示例

用户要求“对测试环境查询接口按每秒 100 次持续 5 分钟”. 系统先确认这里的速率是请求速率且场景每次迭代包含多少请求, 再生成配置. 审批卡片显示环境、目标、请求方法、负载模型、时间、停止阈值、数据写入可能性和凭证身份的脱敏标识.

如果用户将 100 改为 1000, 原审批立即失效. 如果测试过程中发现应跳转到另一个主机, 网络策略先拦截; 模型不能因为“任务需要”自行扩展目标.

以上数字只是说明语义的教学示例, 不代表批准公司环境承受此负载.
