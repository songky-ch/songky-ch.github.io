# 18. Harness 运行机制与模块协作

[返回目录](./index.md)

本章将 [04 的 Agent 循环](04-agent-tools-skills.md)、[05 的任务执行](05-tasks-executor.md)、[06 的 HITL](06-hitl-policy.md) 串成可实现的控制逻辑. 保持 Windows 客户端、Linux 单业务主服务、按任务启动并回收子进程、不使用 Docker 的既定边界. 不改用 Codex 服务, 不新增多 Agent 架构. 核查日期: 2026-10-27; 全章为待实施设计.

## 1. Harness 是什么

模型产生下一步建议, Harness 负责让建议进入可控执行循环: 准备输入、调用模型、检查工具请求、等待执行或人工回复、处理失败、保存进度和结束运行. OpenAI 对 Harness 的描述也强调模型周围的上下文、工具、进度、失败和审批系统. 本项目借鉴职责划分, 不依赖其特定实现. [官方说明](https://developers.openai.com/blog/codex-as-a-platform)

Harness 不等于一份工作流, 也不是另一个必须购买的框架. 现有 Agent Runtime、工作流、策略、调度和执行器共同构成它. 一个主服务进程仍可包含这些逻辑模块; 耗时或不可信工具继续交给受限子进程.

## 2. 谁拥有哪一种状态

[![Harness 的控制层、任务层和执行层职责](/images/test-agent-wiki/11-harness.svg)](/images/test-agent-wiki/11-harness.svg)

从用户请求进入主服务读起. Agent 循环管理 run, 调度器管理 task, 执行器管理一次 attempt. 等待任务完成时释放模型连接, 由持久事件恢复 run; 不让模型一直询问任务结束没有.

| 模块 | 拥有的状态与动作 | 不能越界承担 |
| --- | --- | --- |
| API/会话层 | 身份、消息版本、请求幂等、SSE 订阅 | 不直接运行测试脚本 |
| Agent Runtime | run 状态、预算、工具提案、当前计划、上下文和 Prompt 版本 | 不依据模型文本直接改任务结果 |
| 工作流/LangGraph | 领域节点、依赖、条件分支、检查点 | 不替代任务队列、权限边界或副作用账本 |
| 策略/HITL | 动作校验、交互版本、批准范围与有效期 | 不用会话摘要证明已批准 |
| 工具网关 | 注册表、Schema、调用 ID、ToolResult 规范 | 不因工具描述自称只读就放宽权限 |
| 调度器 | 持久队列、并发额度、租约、取消、恢复对账 | 不用模型决定 OS 资源回收 |
| 执行器 | attempt 内的程序启动、事件、进程树、文件清单 | 不继承模型或数据库全局凭证 |
| PostgreSQL/文件 | 事实、证据、检查点和审计记录 | Redis 不成为唯一恢复依据 |

不会建立第二套 Run/Task 状态枚举. 沿用 04 的 Run 状态和 05 的 Task 状态. `execution_status`、业务结论和报告状态仍分开, 断言失败不等于进程启动失败.

## 3. 一轮调用的确定性顺序

1. **接收并持久化.** API 验证身份和范围, 保存消息与幂等键, 为同会话串行安排 run. 控制操作如取消走独立接口.
2. **核对恢复事实.** Runtime 读取当前检查点, 先对账已有工具调用、任务与交互, 不因节点重放重复发业务请求.
3. **构造输入.** 按 [16](16-context-engineering.md) 筛选/压缩上下文, 按 [17](17-prompt-engineering.md) 组装固定版本 Prompt; 校验计量和预算.
4. **调用模型.** 通过适配器发出请求, 流式发送可展示内容. 不把未完成的工具参数分片交给执行器.
5. **解释输出.** 最终回答进入结果检查; 缺参进入 WAITING_INPUT; 工具请求进入注册表、参数、策略校验. 结构无效只做有上限修正.
6. **批准或等待.** 策略 deny 时保存理由, 有预算可让模型提出范围内替代方案, 重复同一被拒动作不得无限循环. ask 时持久化 interaction 与检查点并释放资源; allow 才进入分发.
7. **确定性分发.** 稳定工具调用 ID 关联账本. 轻量只读工具受限调用; 长任务按 05 的事务和调度协议创建 TaskSpec, 保存 WAITING_TASK.
8. **收集结果.** 任务事件落库后恢复图, 返回结构化 ToolResult 与证据引用. 重复事件由事件 ID/版本条件更新去重.
9. **继续或结束.** 再次核对预算、取消状态和真实任务状态, 才启动下一轮. 最终报告标明未完成项和证据, 长期记忆提炼作为独立后续任务, 失败不抹除已完成测试结果.

任何模型产生的计划都不能删除这些程序校验节点. 表单直接提交的确定参数仍走策略与调度, 不为复用 Harness 强制绕经模型.

## 4. 并发、工具关联与副作用

同会话串行推进上下文, 不等于全部用户或全部任务串行. 不同用户 run 可以在全局/用户额度内并发; 同 run 内已批准且无依赖的任务可按 DAG 并行. 写同一目标或共享资源的任务需要目标级互斥/额度规则, 不能仅凭“没有图依赖”认定安全并行.

模型返回的调用 ID 与平台稳定 `tool_call_id` 建立映射. 平台 ID 绑定 run、已持久提案和动作版本; 网络重试、事件重放使用原 ID. 新生成的一条相似提案不是天然相同操作, 还需检查业务效果键和已完成步骤, 防止模型再次提出已执行写操作.

并行结果按调用 ID 归位, 不按返回先后猜对应关系. 工具失败返回真实错误, 不伪造成成功内容让模型继续. `fail_fast` 停止新分发并请求取消在途任务; `collect_all` 收集各项状态, 不能等同于全部通过.

工具调用账本与任务记录在同一业务事务中建立. LangGraph 检查点与业务事务不假定原子提交; 节点重放先查账本. 外部服务副作用不受本地数据库事务保护, 结果不明沿用 UNKNOWN 与对账流程, 不能宣称 exactly-once.

## 5. 人工介入、取消与恢复

[![等待人工或任务之后恢复执行时必须重查的事实](/images/test-agent-wiki/12-resume.svg)](/images/test-agent-wiki/12-resume.svg)

从上方的持久等待状态进入. 人工回复和任务事件分别核验, 都要重新读当前事实; 不能把“收到一个事件”直接等同于“允许继续”.

| 事件 | 必做检查 | 去向 |
| --- | --- | --- |
| 补参或批准回复 | 身份、interaction 版本/有效期、动作/参数/脚本哈希 | 参数变化重新验证与审批, 合法才恢复 |
| 凭证失效 | 对应用户和目标绑定, 当前任务可否安全暂停 | WAITING_AUTH; 不把认证材料发给模型 |
| 用户取消 | 阻止新调用, 传播到所属未终止任务 | 回收进程树后确认停止; 无法确认则如实报告 |
| 修改当前任务 | 保存新消息和计划版本, 先停止冲突动作并核对已发生效果 | 重新校验与授权, 不修改正在运行的脚本 |
| 等待超时或拒绝 | 等待类型、所属动作和计划失败策略 | 结束该动作或相关 run, 保留已有证据 |
| 主服务重启 | 旧 attempt、OS 进程身份、租约/fence、已提交结果、检查点版本 | 05 的恢复对账后再推进 |
| 结果未知 | 外部效果是否可验证, 是否存在安全幂等机制 | UNKNOWN 待对账/人工处理, 不直接重跑 |
| 版本不兼容 | Prompt/Schema/图检查点是否可共同恢复 | 阻止恢复并明确处理, 不跳过节点 |

等待时不持有数据库事务、模型连接或无用 runner. 某些测试步骤不能无损暂停, 必须先终止到可控状态并说明已发生效果, 不把“等待用户”解释为冻结任意进程后可原样继续.

## 6. 失败分类与停止预算

| 失败位置 | 允许的处理 | 禁止行为 |
| --- | --- | --- |
| 模型超时/限流 | 在次数、时长、费用额度内重试, 记录可能重复计费 | 偷换模型或无限重试 |
| 上下文/模板构造失败 | 保存输入诊断, 修复或明确停止 | 删除核心规则强行发送 |
| 纯计算或只读工具失败 | 按工具声明有界重试 | 把“只读”视作无资源成本 |
| 有副作用工具未返回结果 | 先查账本和外部状态, 不能确认则 UNKNOWN | 按普通超时直接重复提交 |
| 测试断言失败 | 记录业务 FAIL 和证据, 按领域流程分析 | 改断言或删失败样本以求通过 |
| 报告生成失败 | 保留原始指标, 单独重试报告步骤 | 重跑真实压测只为获得报告 |
| 运行预算到限 | 停止新动作, 按既定策略终止/收集在途任务并给出状态 | 静默遗留子进程继续运行 |

预算包含模型/工具调用数、Token/费用、检索轮数、摘要次数、总时长; 每个外部调用还受单次超时约束. 恢复不会重置原 run 的累计预算. 达限后不能仅重新连上 SSE 就继续获得额度.

## 7. 追踪、回放与验收练习

一次调用链用 `request_id → run_id → model_call_id/tool_call_id → task_id → attempt_id → artifact_id` 关联. 记录状态转换、输入清单、Prompt 版本、模型配置、策略决定、预算、调用账本和结果证据. 日志脱敏, 不保存完整内部思维链.

回放分两类: 离线回放读取历史脱敏输入与录制工具结果, 验证流程判断, 禁止真实执行工具; 在线重测是新任务, 重新校验范围与授权, 不能沿用历史审批. 外部状态或资料已删除时说明回放限制.

对应 [B101-B110](13-branches-acceptance.md). 未来 P1/P2 使用不产生业务副作用的假执行器和录制模型响应, 注入“先落任务后崩溃”“重复完成事件”“审批后参数变化”“取消与完成同时到达”“预算耗尽”等场景. 检查只出现一次有效分发、等待不占执行资源、终态不被旧事件覆盖、UNKNOWN 不被当作成功.

再用一条合成 UI 专项任务贯穿三章: 模型提出探查 → Linux runner 返回大量日志 → 上下文保留关键证据并压缩闭合历史 → 模型提出修改脚本 → 策略要求审批 → 用户改变参数 → 新版本重新校验 → 任务执行 → 报告引用真实结果. 预期不能靠摘要中的批准文字跳过新审批. 本轮未执行这些工程验证.

| 术语 | 中文含义 | 本章作用 |
| --- | --- | --- |
| Harness | Agent 运行控制系统 | 组合上下文、模型、工具、策略与恢复 |
| Agent loop | Agent 运行循环 | 调用模型、观察结果、继续或停止 |
| Workflow | 工作流 | 领域步骤与不可跳过的约束 |
| Checkpoint | 检查点 | 保存图的恢复位置, 不证明外部动作未重复 |
| Idempotency | 幂等 | 同一调用重放不重复产生可避免的效果 |
| Fencing token | 执行代次令牌 | 阻止旧 attempt 覆盖新状态 |
