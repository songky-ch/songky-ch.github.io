执行与审批: 先有提案, 再有动作

合成任务: 在测试环境创建一笔样例订单. 重点观察程序校验、审批版本与业务结果.

这个演示省略了什么?

真实系统需要数据库事务、身份验证、执行隔离、事件去重、进程回收和服务重启对账. 这里的状态只存在页面内存中, 刷新会重置. 未实现安全沙箱, 也没有真正执行订单写入. UNKNOWN 的恢复需外部证据, 所以本演示不会给出“重试即可成功”的按钮.

RAG 评测: 从样本走到报告

每次先固定配置, 再看合成检索与回答记录, 最后逐条评分和聚合. 改配置会重置整个实验, 避免混用结果.

实验配置

评分约定, 先看再跑

Recall@K = 命中相关文档数 / 相关文档总数.
Precision@K = 命中数 / K.
RR@K = 首个相关结果排名的倒数; 聚合均值为 MRR@K.

答案质量用“全要点匹配”规则: 必需要点齐全且没有额外错误断言才得 1. 忠实度用样例 fact-ID 与检索上下文计算支持比例. 这不是通用语义裁判.

没有相关性/答案标签、没有可见上下文、没有可评分断言时标 N/A. 评分故障单列, 不重新生成答案.

Agent 评测: 看环境结果, 也看过程约束

四个固定任务, 分别覆盖正常批准、参数变更、用户拒绝和目标服务故障. 同一任务集比较两个合成版本, 没有实际调用被测 Agent.

规则、模型裁判和人工分别做什么?

当前样例有确定的审批版本、执行事件与环境结果, 所以用规则评分. 对开放式回答的语义质量, 才需要独立模型裁判与人工标注校准. 本页面没有真实模型裁判或人工校准数据, 因此不显示虚构的裁判一致率或置信区间. 4 个合成任务的结果也不能证明某个真实模型更好.

沿用专项测试助手案例. 覆盖 10 个主题、29 条预设分支; 不代表你的真实项目经历或线上成果. 先自己回答, 再展开开发与测试视角核对.

10 个模块, 42 个合成情境. 选择故障, 逐步查看记录, 再展开面试答案. 保护字段、版本检查和指标是实际计算; 模型、OCR、数据库及服务结果均为预设, 不执行真实任务.
