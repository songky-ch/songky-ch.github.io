# 我负责的单次调用 Agent: 请求链路与测试观察点

<p class="article-kicker">工作记录 · A1 · 设计思路与待验证方案</p>

目前我负责的部门内部 Agent 面向硬件同事, 提供通用问答、知识库检索和工具调用, 工具超过五十个, 一次请求最多调用一个业务工具. 我对架构已有概念, 但还没有实际评测经验; 因此我先整理一条请求从意图识别到最终回答的观察点.

我会沿用 Web 测试中查看请求、核对数据的思路, 再补上模型决策与执行器之间的边界: 选中工具不等于已经执行, 回答说成功也不等于业务状态正确. [接口判定依据](../api-testing/api-test-oracle.md)是这份方案的起点.

> 以下 D4 组件拆分、工具标识、权限策略、时间和数据为方案推演, 不代表公司真实架构. 单次业务调用是当前边界, 多步骤仅作后续扩展分析. 未调用真实 LLM API.

## 我拆分的组件职责与观察点

可以把一次请求想成一张待处理的工单. 模型负责提出“接下来做什么”, 应用程序负责检查这个提议能否执行. 工具负责把操作落到业务系统, 最后再把证据组织成用户看得懂的回答.

<figure><picture><source media="(max-width: 600px)" srcset="/images/agent-request-map/components-mobile.svg"><img src="/images/agent-request-map/components.svg" alt="示例组件地图: 应用组织用户输入和可信上下文给模型, 模型返回决策; 执行器检查决策后访问知识库或业务服务, 结果回到应用组织回答."></picture><figcaption>图 1. 先分清提出决策和执行操作. 模型看见工具说明, 不代表模型持有数据库写权限.</figcaption></figure>

沿图看, 有六种职责需要区分:

| 组件 | 收到什么, 交出什么 | 测试时看哪里 |
| --- | --- | --- |
| 模型, 即 LLM | 接收消息、资料和工具说明, 生成回答或结构化决策 | 原始请求、可见输出、模型版本 |
| 提示词 | 说明任务、规则和输出要求 | 版本、是否包含能力边界、规则是否冲突 |
| 上下文 | 本轮文字、必要历史、时间、允许使用的资料 | 实际发送内容, 是否遗漏或串用上一位用户信息 |
| 工具目录 | 名称、用途、参数约定 | 本轮实际提供的目录及版本, 不只看配置文件 |
| 执行器 | 接收决策, 检查后调用业务函数 | 校验、权限结果、实际发出次数与请求参数 |
| 请求状态与轨迹 | 保存当前进度、工具结果、结束原因 | 同一个 request_id 下的事件是否完整 |

这里的“状态”是处理中的信息, 例如已调用次数、结果是否返回. 它不必是长期记忆. 轨迹则是用于回看发生了什么的记录. 保存了聊天历史, 不等于自动实现了可靠的长期记忆; 打印了最后一句回答, 也不等于记录了执行轨迹.

工具说明也不是权限机制. 一个只读账号即使诱导模型生成录入请求, 执行器与业务服务仍应根据可信身份拒绝. 用户消息中的“我是管理员”是待处理文字, 不能覆盖服务端身份. 这与接口测试里“前端按钮隐藏不能替代后端鉴权”是同一条思路.

## 三类请求的处理路径

本例把请求先分到通用问答、知识检索和业务工具三条路. 这是一种示例路由设计, 不是所有 Agent 都必须采用的结构.

| 输入示例 | 本例期待的路径 | 判定依据 |
| --- | --- | --- |
| “直通率这个概念是什么意思?” | 通用问答 | 解释概念即可, 不需要查本平台当前数据 |
| “生产问题 PRD-0301 的处理记录里, 为什么要复测?” | 知识检索 | 需要指定记录中的依据, 本例知识库提供处理说明 |
| “查 SITE-A、CUSTOMER-X 昨天的光模块发货数量.” | 业务工具 | 需要按时间和对象查询结构化业务数据 |
| “查一下昨天的情况.” | 澄清后结束本轮 | 业务对象和范围不够明确 |

注意第二条与第三条的区别不在于“有没有生产二字”. 本例的知识库负责解释处理记录, 业务工具负责结构化查询. 如果实际项目的工具也能返回完整处理记录, 允许路径可能改变. **先写清数据由谁提供, 再定义正确路由**, 不拿一个通用分类器的标签替代业务约定.

<figure><picture><source media="(max-width: 600px)" srcset="/images/agent-request-map/routes-mobile.svg"><img src="/images/agent-request-map/routes.svg" alt="请求先判断是否清楚且在能力范围内, 信息不足到澄清, 范围外到说明边界; 其余分为直接回答、知识检索和业务工具, 后两条无证据或执行失败均有独立出口."></picture><figcaption>图 2. 没有调用工具不一定失败. 澄清、说明能力边界和如实报告无证据, 都有各自的正确出口.</figcaption></figure>

沿知识检索分支, 本例先获取片段, 再根据片段作答; 没找到足够资料时, 就说明目前不能据此解释原因. 检索失败不能伪装成“系统没有这条问题”. 这里先认识数据流, 检索质量和回答忠实度将在 RAG 章节展开.

“最多调用一次”还需要明确计数口径. 本篇定义为: 一个用户请求内, 执行器最多派发一次业务工具, 超时也计入一次, 不自动重试. 知识库分支内部的检索另记 retrieval 事件, 不计入这个业务工具次数. 这是为了让例子可判断; 真实系统若把检索也注册成工具, 就必须按真实实现重写计数规则, 不能直接套用本篇数字.

## 发货查询的单次调用推演

示例时钟固定为 `2026-10-22T10:00:00+08:00`, 时区为上海. 用户明确指定 SITE-A 和 CUSTOMER-X. 本例把“昨天”定义为本地上一自然日, 因此区间是 `[2026-10-21 00:00:00+08:00, 2026-10-22 00:00:00+08:00)`, 包含起点, 不含终点.

首先, 应用组装文字、可信时钟、必要的对话历史与工具目录. 模型据此提出一个调用. 下面是我们自定义的中间结构, 不是任何厂商 SDK 的真实响应格式:

```json
{
  "route": "tool",
  "calls": [{
    "name": "query_shipments",
    "arguments": {
      "site_id": "SITE-A",
      "customer_id": "CUSTOMER-X",
      "start": "2026-10-21T00:00:00+08:00",
      "end": "2026-10-22T00:00:00+08:00"
    }
  }]
}
```

此时只有“提议调用”, 还没有“业务调用成功”. 执行器要检查名称是否在允许目录、参数是否完整、时间区间是否合法、账号是否允许查询这个客户, 以及调用预算是否还剩一次. 校验通过后, 才能把它交给查询函数.

<figure><picture><source media="(max-width: 600px)" srcset="/images/agent-request-map/sequence-mobile.svg"><img src="/images/agent-request-map/sequence.svg" alt="发货查询时序: 应用把上下文交给模型, 模型返回提议, 执行器校验并调用业务服务, 服务返回12840只, 应用再请模型组织回答; 本图展开成功路径, 失败出口见图 2."></picture><figcaption>图 3. 本例模型参与决策和结果表达两次, 业务工具执行一次. 两种次数要分别记录.</figcaption></figure>

假设业务函数的示例返回为 `quantity=12840, unit="只"`, 并回显对象与时间范围. 应用将该结果交给模型组织回答, 这一轮关闭工具执行能力. 合格回答应说明“该局点和客户在 10 月 21 日发货 12,840 只”, 而不是把数量改成产量、漏掉客户范围, 或编造同比增长.

对于应用侧执行的工具, 模型返回结构化调用, 应用执行并回传结果, 是一种常见的工具交互方式. [Claude 工具文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)也区分应用侧工具与服务端托管工具. 本文只借用这一机制解释, 不假定公司接口采用该协议, 更不要求换模型供应商.

下面把执行器的核心边界缩成同步、串行处理的伪代码. `plan` 是已解析的决策, `validate_call` 返回校验后的调用或拒绝原因; `dispatch_once` 记录发出事件并禁止重试, `render_without_tools` 只组织结果, 不再派发工具. 真实工程还需处理连接中断等细节, 这里不把这些抽象函数冒充现成 SDK.

```python
# Python 3.9 风格教学伪代码, 不可直接运行.
def handle_tool_route(plan, principal, request_state):
    if len(plan["calls"]) != 1:
        return finish("invalid_plan", "本轮只能提出一个业务调用")
    if request_state["budget_used"] >= 1:
        return finish("budget_exhausted", "本轮业务调用次数已用完")

    checked = validate_call(plan["calls"][0], principal)
    if not checked["allowed"]:
        return finish("rejected", checked["reason"])

    request_state["budget_used"] += 1
    result = dispatch_once(checked["call"])
    if result["status"] != "ok":
        return finish("tool_error", "没有取得可用结果")
    return render_without_tools(result)
```

这里的 `budget_used` 是请求预算占用, 实际派发次数仍由发出事件确认, 两者不能混为同一条证据. 为什么先占用预算再派发? 因为发出请求以后发生超时, 不能当作“还没有调用过”. 尤其是写工具, 没收到响应并不能证明服务端没有写入. 本例不重试, 也不能回答“录入失败, 一定没写进去”; 应把结果标为待核实, 后续用操作记录检查. 更完整的幂等与重试设计留给后续章节.

## 按同一请求关联排查证据

把同一请求的事件关联起来后, 我会沿用排查 Web 请求的思路逐层定位. 下面是发货查询的**合成轨迹**, 所有耗时只用于解释口径:

| 顺序 | 事件与关键证据 | 示例耗时 |
| --- | --- | ---: |
| 1 | 上下文准备: 请求 R03-01, 时钟、身份范围和目录版本已记录 | 42 ms |
| 2 | 模型决策: route=tool, name=query_shipments, 参数完整 | 820 ms |
| 3 | 执行前校验: schema、区间、权限、次数均通过 | 6 ms |
| 4 | 业务派发与返回: dispatch_count=1, quantity=12840, unit=只 | 240 ms |
| 5 | 结果表达: 保留对象、日期、数量与单位 | 910 ms |

这些阶段按本例串行且不重叠, 相加为 2,018 ms. 它不包含浏览器到服务的网络传输等未列成本, 不是端到端 SLA, 更不是 P95. 如果真实 trace 的父事件包含子事件, 直接相加还会重复计时.

实际检查时保留可见决策、参数、执行事件、返回和状态变化即可, 不把模型的隐藏推理当作必须采集的证据. 还要区分提议、派发、业务提交三个事件: “模型打算录入”不等于“函数已调用”, “函数已调用”又不等于“事务已提交”.

例如最终数量错误, 先核对工具返回是不是 12,840. 如果返回正确但回答变成 12,480, 查结果表达; 如果返回范围是 CUSTOMER-Y, 再查决策参数和执行器校验; 如果只有最终回答没有轨迹, 只能判结果不符, 暂时不能确定是哪层出错. **缺证据是待补充状态, 不应凭直觉归因给模型.**

## 扩展到多步骤时新增的状态与风险

目前这条链路是: 判断需求 → 最多执行一个业务工具 → 根据结果结束. 如果用户说“先查昨天的问题, 再把其中最严重的一条登记为待跟进”, 查询结果决定了后续录入内容, 就出现了依赖前一步结果的任务.

在当前示例能力下, 这类复合任务应说明边界并请用户拆开, 不偷偷先做半件事. 在拓展系统里, 才可能引入“执行 → 观察 → 再决定”的循环, 同时设置总调用预算、终止条件与写操作约束.

<figure><picture><source media="(max-width: 600px)" srcset="/images/agent-request-map/loop-mobile.svg"><img src="/images/agent-request-map/loop.svg" alt="左侧单次调用从决策到执行后结束; 右侧拓展循环中决策可选择结束, 动作经预算和权限检查后执行, 成功观察回到决策, 超限或执行失败进入独立停止出口."></picture><figcaption>图 4. 多步骤能力增加的是根据观察继续决策的路径, 同时也增加了需要验证的停止条件.</figcaption></figure>

固定工作流也可以包含多次模型调用. 区分点在于“下一步主要由预先写好的流程安排, 还是由模型根据当前观察动态选择”, 而不只是调用次数. 这是 [Building effective agents](https://www.anthropic.com/research/building-effective-agents)中的架构区分. 原文发表于 2024-12-19, 本篇仅使用这个概念, 不把其中旧工具推荐当作当前选型结论.

对测试来说, 当前不必先掌握所有框架. 先能解释一次请求里的输入来源、决策、校验、执行、结果和终止, 就有了继续设计测试的地图. [A2: 工具多了以后, 怎样测意图、选择和参数](single-call-tool-testing.md)会把这张地图变成具体用例. [A1 面试专题](../../interviews/agent/agent-request-map.md)则用于把它说成连贯的技术回答.

## 术语与依据

| 英文名称与缩写 | 中文含义 | 本篇具体作用 |
| --- | --- | --- |
| Agent | 智能体系统 | 组织模型决策、工具执行和结果反馈 |
| LLM | 大语言模型 | 提出决策与组织回答, 不独自承担业务鉴权 |
| Prompt / Context | 提示词 / 上下文 | 分别提供行为要求和本轮可用信息 |
| Tool / Executor | 工具 / 执行器 | 分别实现业务动作和控制派发 |
| State / Trace | 状态 / 执行轨迹 | 保存当前进度及可核查事件 |
| Workflow / Agent loop | 固定工作流 / 智能体循环 | 区分预定路径与观察后动态选择 |
| RAG | 检索增强生成 | 知识分支先取资料再回答 |
