# 业务级 Agent: 从生产决策到面试证据

本文继续使用测试团队的专项测试助手作为教学案例, 目标是能解释“谁做决定、谁执行、凭什么判定成功”. 不建设全量产品, 也不把学习案例写成个人项目履历. 前置知识是基本接口测试、状态和 JSON 参数.

[打开动态演示](/demos/agent-lab/index.html) → 选择“生产决策与面试”. [开发与测试面试专题](../../interviews/agent/production-agent.md). [原 Wiki 学习路线](/test-agent-wiki/architecture/19-learning-guide.html).

## 先看职责与证据流

<picture><source media="(max-width: 600px)" srcset="/images/agent-production/decision-flow-mobile.svg"><img src="/images/agent-production/decision-flow.svg" alt="请求、提案、校验、执行及独立证据判断"></picture>

先沿主线看测试需求如何变成提案. 校验不通过就阻断, 需要补充信息或改变动作时回到新提案; 通过后执行, 再依据环境证据判断, 超时的写入单独进入对账. 模型的“完成了”不等于环境中的任务确实存在.

业务复杂不自动意味着需要多 Agent. 本文把单 Agent、并行程序和多 Agent 作为不同候选, 以实际收益和可验证性决定是否拆分. 以下分支是教学路径, 不是完备的生产故障状态机.

## 01 项目背景与选型

从测试人员整理需求、选择接口和汇总证据的耗时讲起. 固定测试套直接交给工作流; 需求缺信息、需要根据反馈选择下一步时才引入模型决策. 创建任务、权限校验和执行测试仍由程序完成. 上线前后在同类任务中比较全量合格率、人工处理时间、P95 延迟和每个合格任务的总成本, 同时保留人工或工作流基线. 没有真实数据就说明尚未上线, 不编造提升比例. 重做时优先补齐基线、证据日志和高风险操作边界.

在动态页面选择本主题, 可逐步查看以下路径:

### 固定步骤

1. 用户输入: 执行既定回归套件
2. 代码: 校验环境和套件版本
3. 工作流: 依次执行已有测试步骤
4. 结论: 普通后端或工作流足够, 不增加自主规划

### 需动态补信息

1. 用户输入: 分析不完整需求并选择验证路径
2. 模型: 提取已知条件, 提议澄清或检索
3. 代码: 验证提案, 执行批准的工具并记录结果
4. 结论: 在受控工作流中加入 Agent 决策环

**验证要看什么:** 选固定测试套与开放式需求两类样本, 固定验收口径, 同时记录失败、转人工、耗时与成本; 不只展示成功样例.

**进一步追问:** 如果 Agent 更慢但节省人工呢? 分开统计机器等待和人工处理时间, 结合业务时限与风险评估净收益, 不能只比较响应速度.

## 02 任务执行与重规划

模型提出下一步工具与参数, 运行时维护状态并检查身份、参数、预算和审批. 工具结果绑定 call_id 返回, 模型再决定下一步. 有数据依赖的调用串行; 无依赖且资源允许的只读调用可以并行, 写操作不能默认并行. 新证据推翻计划时保留已完成事实, 更新剩余计划版本; 如果审批覆盖的目标或参数改变, 原审批失效. 用硬上限和无进展检测共同终止循环, 不能只在提示词里说不要循环.

在动态页面选择本主题, 可逐步查看以下路径:

### 结果改变计划

1. 模型: 先查接口文档再计划测试
2. 工具: 返回接口版本已停用的证据
3. 运行时: 保存事实, 计划 v1 更新为 v2
4. 出口: 新目标需重新校验与审批, 不能沿用旧批准

### 无进展循环

1. 模型: 再次查询同一缺失接口
2. 运行时: 输入与观测均未变化, 无进展计数加一
3. 运行时: 达到教学阈值 3 次, 禁止下一次调用
4. 出口: 停止并报告缺失条件, 可请求人工补充

### 总预算耗尽

1. 运行时: 派发前检查剩余期限与模型调用额度
2. 条件: 教学上限 8 次调用已经用完
3. 运行时: 拒绝继续规划, 取消可取消的在途工作
4. 出口: BUDGET_EXCEEDED, 有副作用的在途请求仍需对账

**验证要看什么:** 注入相同结果反复返回、依赖缺失、计划变更和取消, 检查无进展终止、未授权调用次数为零及已完成步骤不被重复执行.

**进一步追问:** 合法轮询也会重复调用, 怎么办? 轮询有独立次数、退避和期限; 无进展指状态与证据没有变化, 不能单凭相同工具名拦截.

## 03 工具错误与重试

运行时只接受注册且当前身份可用的工具. JSON Schema 通过不代表业务正确, 还要核对租户、环境、资源归属、金额单位和前置状态. 选错工具或参数错误应返回结构化错误供有限次修正, 缺业务信息则询问用户. 权限错误不能靠换工具绕过. 暂时性读错误可在期限内退避重试; 写超时可能已经提交, 先查状态. 只有服务端支持稳定幂等键、参数一致性和去重保存契约时才能安全重放相同操作, 本地加个 UUID 并不够.

在动态页面选择本主题, 可逐步查看以下路径:

### 不存在的工具

1. 模型: 提议未注册的 delete_everything
2. 运行时: 注册表查找失败
3. 运行时: 返回 UNKNOWN_TOOL, 不派发请求
4. 出口: 有限次修正工具选择, 超限停止

### 无权限

1. 模型: 提议启动其他项目的压测
2. 运行时: 当前身份无目标资源权限
3. 运行时: 返回 FORBIDDEN, 不调用业务服务
4. 出口: 拒绝或走授权流程, 不换身份重试

### 业务参数错误

1. 模型: schema 正确, 但 target=prod 而任务限定 test
2. 运行时: 比对任务环境约束, 拒绝执行
3. 模型或用户: 修正目标, 生成新参数版本
4. 出口: 重新校验并按策略审批

### 可重试读故障

1. 只读工具: 返回暂时限流且提供 Retry-After
2. 运行时: 检查剩余次数与截止时间
3. 运行时: 按提示和抖动退避, 教学样例下一次成功
4. 出口: 保存观测; 超过预算则失败结束

### 写入效果未知

1. 写工具: 已发送创建请求, 响应超时
2. 运行时: UNKNOWN, 不把它当成未执行
3. 对账: 用操作 ID 查询已存在的业务记录
4. 出口: 复用结果; 查不到且契约不明确则人工处理

**验证要看什么:** 模拟未知工具、跨用户资源、数量单位错、429、提交后断网, 核对调用被阻断或正确退避; 检查业务记录数量而非只看返回码.

**进一步追问:** 服务端不支持幂等又无法查状态? 标记 UNKNOWN, 停止自动重试并交人工对账. 不能把超时解释为失败未执行.

## 04 框架选择与边界

先列是否需要长任务、暂停恢复、流式事件、分支编排和可观测性, 再用故障样例验证框架. 简单单次调用可以用 SDK 加显式循环; 需要图状态和中断恢复时可评估 LangGraph. 它提供检查点及暂停恢复机制, 但业务权限、审批绑定、幂等契约、执行沙箱、队列容量和验收标准仍由应用落实. 不符合业务时优先通过节点与工具适配层扩展, 把业务状态与框架类型隔开, 而非直接修改框架内部.

在动态页面选择本主题, 可逐步查看以下路径:

### 简单任务

1. 需求: 一次结构化提取加一个只读工具
2. 候选: SDK 与显式状态循环
3. 验证: 错误处理、超时和观测接口满足需求
4. 结论: 不为简单路径引入复杂图编排

### 暂停恢复任务

1. 需求: 任务跨进程重启, 等人工审批
2. 候选: LangGraph 检查点与 interrupt
3. 恢复: 中断节点重入, 不能重复中断前写入
4. 结论: 框架承载流程, 业务层仍实现幂等和权限

**验证要看什么:** 用最小流程验证进程崩溃、审批暂停与恢复, 检查节点重入、检查点可读性、旧版本兼容和外部写入次数; 不只跑官方 happy path.

**进一步追问:** 恢复是否从中断的那一行继续? LangGraph 中断所在节点恢复时会从节点开头重新执行, 中断前的副作用必须避免重复; 具体行为还要按锁定版本测试.

## 05 知识库与上下文

先确认正确片段真的进入本轮模型输入, 而非只存在于检索日志; 再检查切分是否缺条件、版本是否冲突、否定语义和引用是否错配. 冻结输入单独比较生成与提示词, 不把所有问题都归因于召回. 上下文预算给系统规则、任务状态、最新证据和输出留空间; 旧对话可以提炼摘要, 但审批、目标、未完成动作、来源版本等保存为结构化事实. 结构化检索用于精确过滤实体、权限和时间, 摘要用于压缩叙述, 二者互补. 库存、当前执行状态等事实应查权威业务接口.

在动态页面选择本主题, 可逐步查看以下路径:

### 召回对而回答错

1. 检索: 找到“需订单号且 7 天内”的片段
2. 观测: 片段进入输入, 回答却只说“7 天内”
3. 诊断: 生成遗漏条件, 不是检索没命中
4. 出口: 固定证据重评生成, 保留条件完整性判据

### 上下文超限

1. 输入: 大量历史与工具日志超过预算
2. 程序: 保留约束、待办、审批版本和证据引用
3. 压缩: 旧叙述变摘要, 原始日志放外部按需读取
4. 出口: 校验关键事实未丢失再继续, 不静默截断

### 实时业务事实

1. 用户: 当前压测任务是否已经停止?
2. 路由: 知识库只能解释规则, 无法证明当前状态
3. 工具: 查询授权范围内的任务状态接口
4. 出口: 接口不可用则报告未知, 不凭记忆宣称已停止

**验证要看什么:** 固定召回并注入相反条件、过期文档、长工具输出, 比对实际模型输入和证据引用; 实时状态题检查是否调用正确业务接口.

**进一步追问:** 摘要删掉“禁止生产环境”怎么办? 约束不只保存在摘要, 执行前由程序读取不可被摘要替代的结构化限制, 回归检查关键事实保留率.

## 06 多轮对话与记忆

最近交互、待补参数和执行状态属于会话状态, 需要恢复的部分存持久化检查点; Redis 适合带 TTL 的缓存或协调状态, 不能默认是唯一事实来源. 稳定偏好与经确认的事实可以进入长期结构化存储, 带用户、项目、来源、有效期与版本; 需要语义回忆的叙述可建立向量索引, 权威事实仍可回查. 模型提炼的是候选记忆, 先筛敏感信息、冲突与时效再写入. 检索前强制身份和项目过滤, 命中后再检查权限; 删除与失效也要同步索引和缓存.

在动态页面选择本主题, 可逐步查看以下路径:

### 偏好候选可保存

1. 对话: 用户明确偏好中文测试报告
2. 模型: 提出偏好候选并附来源消息
3. 程序: 核对范围与敏感性, 写入带版本的长期记录
4. 下次: 按用户和项目过滤后读取, 用户可更正或删除

### 跨项目命中被挡

1. 检索: 相似内容来自其他项目
2. 程序: 当前访问范围不包含该项目
3. 输出: 拒绝使用该记忆, 不把正文传给模型
4. 出口: 在授权范围重新检索或说明没有可用记忆

### 过期状态不记作事实

1. 历史: 昨天记录“任务运行中”
2. 读取: 状态已过期, 不能当作长期稳定事实
3. 工具: 查询当前任务状态
4. 出口: 用新观测回答, 保留历史仅作事件记录

**验证要看什么:** 两个用户使用同名项目与相似语句, 检查跨域召回为零; 再测更正、过期、删除和检查点恢复, 核对缓存与向量索引的旧值不可见.

**进一步追问:** 用户更正记忆后旧向量仍召回怎么办? 用当前事实版本和墓碑标记拦截旧记录, 异步清理向量与缓存; 不把向量匹配结果直接当真.

## 07 多 Agent 协作

先验证单 Agent 或普通并行工作流是否足够. 只有独立子问题、不同上下文或工具边界等确实带来收益时再拆. 例如接口风险与 UI 风险分析可以并行, 若只是固定程序步骤就不需要两个 Agent. 委派包包含 task_id、父任务、目标、约束、输入引用、输出 schema、预算与截止时间, 回传证据和未决事项, 不复制全部聊天. 用任务账本、租约和去重控制领取; 旧执行者失去租约后须由版本栅栏阻止提交. 外部写入交给明确的单一责任者并使用幂等契约. 汇聚器处理矛盾与部分失败.

在动态页面选择本主题, 可逐步查看以下路径:

### 可拆分并汇聚

1. 协调者: 分发 API 风险与 UI 风险两个独立任务
2. 子 Agent: 各用最小上下文, 返回带来源的结构化结果
3. 汇聚: 校验覆盖和冲突, 不以多数票代替证据
4. 出口: 形成候选测试计划, 写入由单一执行者负责

### 重复投递

1. 调度器: 同一 task_id 被重复领取
2. 账本: 只有当前租约版本可以提交结果
3. 过期执行者: 提交被拒; 外部写入另有幂等保护
4. 出口: 同一任务只采纳一个有效结果

### 子任务失败

1. API 分析: 成功; UI 分析: 超时
2. 汇聚: 标记部分完成, 不虚构 UI 证据
3. 策略: 剩余预算内重试只读分析或转人工
4. 出口: 明确覆盖缺口, 不标记完整测试计划

**验证要看什么:** 模拟重复投递、租约到期、迟到结果和相互冲突结论; 观察只有当前版本能提交, 外部副作用不重复, 部分失败不能报告全部完成.

**进一步追问:** 并行是否一定更快? 总延迟含分派、最慢子任务和汇聚, 总成本含所有子任务及重试. 在同一任务集对比合格率、P95、总 token 和单个合格任务成本后再决定.

## 08 可信结果与运行治理

把模型声称、工具传输成功、业务断言通过分开记录. 用任务 ID 串起模型调用、工具参数版本、授权、业务回执和断言. 恢复前先核对已完成的外部效果, 只恢复未完成部分; 补偿是新的业务动作, 也可能失败, 不能等同数据库回滚. 运行时在派发前限制总期限、模型调用次数、并发和费用预算, 在途操作超时仍需取消或对账. 延迟突增按排队、模型首字和总耗时、工具、检索及重试拆分, 再看 P95 与版本变化. 成本按输入输出 token、重复尝试、工具费用和成功任务数拆分.

在动态页面选择本主题, 可逐步查看以下路径:

### 成功写入后报告失败

1. 执行器: 已创建任务, 保存业务 ID 与回执
2. 报告生成: 模型超时
3. 恢复: 查询业务 ID, 确认任务存在
4. 出口: 只重生成报告, 不重建测试任务

### 回执无法确认

1. 工具: HTTP 200, 但环境断言未满足
2. 运行时: 记录传输成功与业务未通过
3. 诊断: 查看对象状态及前置条件
4. 出口: 业务失败或未知, 不声称任务成功

### 延迟成本上升

1. 监控: 同类任务 P95 与总成本比基线升高
2. 追踪: 排队正常, 工具重试次数明显增加
3. 定位: 检查依赖服务与超时配置, 不先盲换模型
4. 出口: 修复后按同口径重测, 观察错误率与单次合格成本

**验证要看什么:** 注入创建后崩溃、回执丢失、报告失败和子进程不退出, 检查恢复仅补缺失步骤、期限覆盖在途操作、UNKNOWN 保留对账线索.

**进一步追问:** 已经创建任务但报告生成失败? 对账确认任务存在, 使用原结果重做报告, 不重新创建任务; 若需要撤销则按业务补偿规则批准并执行.

## 09 版本评测与回滚

把模型、提示词、工具 schema、检索索引和评分规则作为可追踪版本组合. 用来源合规的脱敏样本、真实失败类型和合成边界构建评测集, 留出未用于调参的测试集. 比较时固定环境和任务, 先单因素替换以定位原因, 最终再验证完整组合; 随机输出要重复采样, 报告样本数与不确定性. 规则检查权限与业务结果, 独立裁判评开放语义并用人工标注校准, 换个模型不能自动保证客观. 灰度监控合格率、违规、成本与延迟, 超阈值切回已验证版本; 在途任务按其原版本完成或受控迁移.

在动态页面选择本主题, 可逐步查看以下路径:

### 离线改进但有安全退化

1. 评测: 新版本文字更完整, 但出现越权执行
2. 规则: 安全约束不允许被平均质量分抵消
3. 决策: 阻止发布, 定位工具策略或审批回归
4. 出口: 修复后重跑相同冻结任务与安全边界样本

### 灰度退化

1. 灰度: 同类流量下合格率下降, 排除样本结构变化
2. 发布器: 新任务切回已验证版本组合
3. 在途: 保留原版本或按兼容策略受控结束
4. 出口: 对账已有副作用, 不把版本回滚当作数据撤销

### 裁判自身失败

1. 被测任务: 已生成结果和工具轨迹
2. 评分服务: 超时, 得分为未判而非 0 或 1
3. 恢复: 重评保存的结果, 不重做真实业务动作
4. 出口: 单列评分覆盖率及故障数, 保留全量任务分母

**验证要看什么:** 同一任务配对比较旧新版本, 单列目标服务失败和评分器失败; 测灰度切换、在途版本固定以及不可兼容状态的处理, 检查回滚不重复副作用.

**进一步追问:** 回滚 Prompt 会撤销已经写入的订单吗? 不会. 行为版本回滚与业务补偿是两个过程, 后者需对账、权限和独立记录.

## 10 落地限制与退出条件

工程可以约束授权、预算、并发、重试和证据留存, 但不能保证模型在任意新需求上都理解正确. 自研重点通常是业务工具契约、权限策略、验收数据、环境断言和恢复规则, 不是必须重写通用调度或训练基础模型. 如果任务长期路径稳定、错误成本过高而又无法验证或审批, 应让确定性服务执行, 模型只做辅助解释或完全退出. 用满足业务风险约束后的净收益决定继续投入, 而不是因为已经用了某个框架就坚持.

在动态页面选择本主题, 可逐步查看以下路径:

### 继续投入

1. 任务: 动态决策确有价值且结果可验证
2. 比较: 在风险限制内对人工或工作流有净收益
3. 工程: 针对主要失败类型完善工具和证据
4. 出口: 小范围迭代, 继续监控投入产出

### 退回确定性方案

1. 任务: 路径固定或结果无法可靠验证
2. 比较: 协调与复核成本超过节省的人力
3. 决策: 后端或工作流执行, 必要时模型仅辅助理解
4. 出口: 保留业务能力, 降低自主执行范围

**验证要看什么:** 对不可逆、缺乏可核验证据和高歧义任务设计退出样本, 检查系统确实转人工或走确定性路径; 不以更高自动化率掩盖风险.

**进一步追问:** 模型能力提升能取消所有工程约束吗? 不能. 身份、授权、幂等与审计是系统责任, 与模型是否聪明无关.

## 三组可复现练习

环境: 支持 JavaScript 的浏览器, 无需账号或模型密钥. 打开实验室, 以下是预期验收结果, 不是业务系统实测.

1. 选择“工具错误与重试 → 写入效果未知”, 逐步走到对账出口. 再切换“执行与审批 → 写操作超时”, 批准并推进. 验收: UNKNOWN 阻止盲目继续, 模拟执行次数不增长.
2. 选择“知识库与上下文 → 召回对而回答错”, 说明错误位于生成. 再到 RAG 标签, K=3, 打开无依据断言, 推进到报告. 验收: 相关文档仍可全部召回, 答案全要点匹配与忠实度会暴露生成问题, 检索好不等于回答好.
3. 选择“版本评测与回滚 → 离线改进但有安全退化”, 再到 Agent 评测比较两个版本. 验收: 目标达成与合格分开, 安全违规不能被其他任务的正确回答抵消.

## 面试中如何说明业务指标

| 指标 | 口径 | 必须同时说明 |
| --- | --- | --- |
| 全量合格率 | 目标达成且无违规的任务数 / 全部纳入任务数 | 超时、失败、拒绝是否为任务预期, 不能事后排除难例 |
| 人工处理时间 | 同类任务实际人工操作与复核耗时 | 区分等待时间, 使用相同任务难度分层 |
| 单个合格任务成本 | 全部尝试的模型、工具等可归因成本 / 合格任务数 | 合格数为 0 时不可定义, 不能显示 0 元 |
| P95 延迟 | 观测任务耗时的第 95 百分位 | 报告样本数、窗口、超时与未完成任务, 避免幸存者偏差 |
| 评分覆盖率 | 已获得有效评分的任务数 / 应评任务数 | 裁判失败单列, 不当作被测系统成功或失败 |

没有真实样本就使用这些口径设计实验, 不写虚构的上线前后数字. 若重新做一次, 应根据失败分布决定优先补工具契约、数据、审批还是模型, 而不是固定回答“升级模型”.

## 自测与答案

- 问: 参数通过 JSON Schema, 为什么仍不能执行? 答: 类型正确无法证明环境、用户、资源和单位符合目标, 要做业务语义及授权检查.
- 问: 重启恢复时重新创建任务是否正常? 答: 先对账已发生的写入, 仅恢复缺失步骤. 检查点本身不能撤销或去重外部副作用.
- 问: 什么时候需要独立评测模型? 答: 开放语义难以用规则判断时可采用, 但仍要与人工标注校准. 确定性的权限与业务状态优先规则判定.

## 新增工程追问: 用项目证据回答

[项目证据实验](/demos/agent-lab/index.html) 新增 10 个模块、42 个合成情境. 与原有 10 个主题、29 条叙事分支互补. 本节未声称实现后端或部署模型. 所有百分比门槛与相似度数值均为样例, 不构成行业基准.

### 问题改写: 高相似也可能改错

改写候选不能取代原问题. 检查实体、否定、数值单位、时间范围、权限和意图; 相似度只作辅助信号. 错别字纠正可能改变字面关键词, 所以保护的是规范化实体与约束, 不是所有原始字符.

**如何验证:** 构造只改变否定、单位和实体的最小对照样本. 记录原问题、候选、保护槽位和决策; 同时评价召回收益与意图损坏率.

**演示入口:** 指代有证据, 安全补全 / 高相似但删除否定 / 把 5 秒改成 5 分钟 / 指代不清, 先问用户.

### 文档入库: 复杂表格与切片

可用文本层优先解析, 扫描页按需 OCR. 表格保留行列、合并单元格、表头、单位与页码, 也可生成带表头的行组片段参与检索. 语义切片、固定长度和重叠都是可比较策略, 没有固定 512 必错的规则.

**如何验证:** 检查双栏阅读序、跨页表头、单位、公式符号和出处. OCR 置信度不等于业务正确; 与抽样人工真值核对, 不明内容隔离复核.

**演示入口:** 文本层与结构可用 / OCR 丢失单位 / 跨页表头待确认 / 固定切片丢失否定条件.

### RAG 诊断: 不堆组件找证据

先冻结失败现场, 分别定位解析、切片、召回、重排与生成. 重叠可能增加重复, 多路召回可能增加噪声, 重排可能增加延时; 用同一评测集比较改动, 不把整套组件当作必胜答案.

**如何验证:** 检查正确证据是否在语料、候选池、Top K 和最终模型输入中; 只改变故障层后重评, 记录效果和成本.

**演示入口:** 切片破坏前提 / 召回有噪声 / 证据正确但答案幻觉 / 公式抽取不确定.

### 多 Agent: Manager 也有边界

本教学案例采用 Manager 统一调度, 因为审批与证据汇聚容易集中管理. 这不是企业唯一架构. 事件驱动、交接和分层结构也可使用; 关键是所有权、权限、预算与冲突处理. Manager 本身也需持久化与故障恢复.

**如何验证:** 验证租约过期后旧执行者无法提交, 外部工具另做幂等. 冲突用来源版本和证据裁决, 证据不足交人工, 不能由 Manager 凭空定真伪.

**演示入口:** 两个独立分析任务 / 重复投递与迟到结果 / 子任务证据冲突.

### 断点恢复: 写入与检查点之间

检查点保存状态和结果引用, 不能原子覆盖任意外部服务. 恢复先加载持久化状态与实际操作账本, 再查询业务效果. 相同操作复用幂等键, 改参数必须新建操作并重新批准. 不承诺任意故障下 100% 恢复.

**如何验证:** 在发送前、服务提交后、回执后、检查点落盘前分别注入故障. 断言业务记录数量、批准版本和下一动作, 不只看对话恢复了.

**演示入口:** 写入已提交, 检查点未保存 / 写入效果无法查询 / 副作用前崩溃, 服务支持幂等.

### 模型服务: 质量与资源准入

调用托管 API 不等于部署模型. 自部署还需权重与许可证、运行时兼容、显存及 KV cache 容量、量化回归、并发调度与压测. 小模型/大模型路由要在业务集上验证; 灰度监控质量、延时和资源, 不只看 token.

**如何验证:** 记录硬件、模型和量化版本、上下文长度分布、并发、首 token 延时与吞吐. 服务超时是否可以重试取决于流式输出和后续工具效果, 不能重复发送业务动作.

**演示入口:** 小模型候选满足门槛 / 小模型质量退化 / 显存预算不足 / 服务超时但已开始输出.

### 意图路由: 多意图与兜底口径

规则、分类模型和 LLM 是可选组合, 不必每次逐层经过. 多意图可形成任务依赖图, 不等于必须拆成多轮对话. 兜底占比须定义分母和路由触发条件; 没有证据支持成熟项目统一低于 5%-10%.

**如何验证:** 用误路由代价校准置信阈值, 检查缺参、拒识、冲突意图与越权. 按流量类型看路由精确率、召回、澄清率、成本与端到端合格率.

**演示入口:** 高置信规则命中 / 多意图有依赖 / 歧义需要澄清 / LLM 占比 40% 的合成流量.

### 记忆一致性: 持久记录与缓存

MySQL 可存消息、任务、事实与快照元数据, 大文档原件通常放对象存储并保存引用; Redis 可缓存会话且自身也可配置持久化. 关键消息和状态逐次落盘, 数据库事务同时写 outbox, 消费者按版本更新缓存; 不是等会话结束再保证一致性.

**如何验证:** 测试缓存更新失败、乱序、重复事件、进程崩溃、删除后旧值复活. 重要决策读当前权威版本, 明确最终一致窗口和用户读己之写要求.

**演示入口:** 数据库新版本, 缓存旧版本 / 持久化失败, 不确认成功 / 删除事件重复投递 / 等会话结束才落盘的风险.

### RAG 指标: 名称不能代替定义

区分召回、证据支持、事实正确、问题相关性与运营可靠性. 忠实不必然正确, 幻觉率也只有在相同断言集合和二分类规则下才是 1-忠实度. 线上脱敏抽样、人工复核、漂移告警与冻结回归集互补, 不能只监控一个准确率.

**如何验证:** 固定相关性标注粒度和分母, 分别统计不适用、失败和有效评分. 问答匹配可定义为回答覆盖任务要点, 不等于语义相似度; 上下文相关性需相关性标签或独立裁判.

**演示入口:** 证据有噪声并含不支持断言 / 裁判失败 / 没有召回标签 / 没有可核验断言.

### 完整项目如何讲清楚

先说明这是学习设计与可运行的浏览器模拟, 尚未开发上线. 场景是专项测试助手: 输入需求, 解析证据, 选择工具, 对需要执行的动作审批, 记录结果并独立评测. 选一个 T-001 的失败现场贯穿: 改写删除否定被拦截 → 文档单位不明暂停入库 → 恢复写操作前查账 → 评分缺材料单列. 页面中的各模块是独立情境, 不声称它们组成已运行的后端流水线.

回答按“业务问题、边界、关键决策、失败处理、验证证据、尚未完成”组织. 已有模拟检查可以说明具体断言; 真实成功率、节省工时和上线效果尚无数据. 未来要以人工/工作流为基线, 在相同任务分层比较质量、人工时间、延迟和每个合格任务成本, 不能编造一个上线提升值.

### 资料与保证边界

- [LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence): 检查点与跨会话存储是不同职责, 持久化组件不替代外部服务幂等契约.
- [LangChain 多 Agent 模式](https://docs.langchain.com/oss/python/langchain/multi-agent): 存在子 Agent、交接、路由等多种模式, 不支持“企业全部中心化”的断言.
- [Redis 持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/): 可选 RDB、AOF 等, Redis 不等于必然只存易失数据.
- [Docling 技术报告](https://arxiv.org/abs/2408.09869): 版面和表格解析属于文档处理机制, 不能把所有 PDF 当作纯文本或统一 OCR.
- [vLLM 并行与扩展](https://docs.vllm.ai/en/stable/serving/parallelism_scaling/): 模型服务部署需要匹配实际资源和并行方式, 本项目未运行推理服务.
- [小红书评测机制带读](../../learning/ai-evaluation/redtech-evaluation.md): 输入快照、分维度状态、校准与回放, 含原文页码和迁移边界.

以上框架文档核查于 2026-10-28, 此处解释职责, 不提供未经本机验证的部署命令. 未引用“5%-10% 兜底率”作为成熟度基准.

新增术语: outbox 是与业务记录在同一事务写入的待投递事件; tombstone 是删除墓碑, 阻止迟到旧事件恢复已删除数据; lease version 是任务所有权版本, 用于拒绝旧执行者提交; KV cache 是推理时注意力键值缓存, 会影响服务容量.
