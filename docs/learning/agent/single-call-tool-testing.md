# 围绕五十多个工具, 我怎样设计调用测试

<p class="article-kicker">工作记录 · A2 · 设计思路与待验证方案</p>

现有 Agent 的工具中, 生产问题查询和录入等能力会使用相近的业务词. 我设计测试时, 不会只确认某个工具能调通, 还要区分用户是在查询、要求解释, 还是确实要新增记录. 工具选对后, 日期、客户和权限仍需要独立核对.

这份尚未落地的方案承接[请求链路](agent-request-map.md), 将[接口覆盖](../api-testing/api-coverage.md)和[依赖替身](../mock-testing/test-doubles.md)用于拆分模型选择与执行器行为. 我会为每条请求记录允许动作、禁止动作和应留下的证据.

> D4 工具协议、参数、测试集和指标均为场景推演. 一次请求最多派发一次业务工具, 不自动重试; 复合任务先说明边界. 知识检索与业务调用分别计数, 未在真实 Agent 上执行本方案.

## 工具职责与误选边界

我先从五十多个工具中选择一组容易混淆的能力, 分析误选风险. 这份方案使用四个示例工具:

| 工具名 | 明确用途 | 必需业务参数 | 禁止混用 |
| --- | --- | --- | --- |
| `query_production_issues` | 查询生产问题的结构化记录 | 局点、客户、起止时间 | 不返回现网问题, 不录入 |
| `query_field_issues` | 查询现网问题的结构化记录 | 同上 | 不把现网当成生产 |
| `query_shipments` | 查询已发货数量, 单位为只 | 同上 | 不把生产数量当成发货量 |
| `create_production_issue` | 新增生产问题 | 局点、客户、发生时间、标题 | 不因用户只说“看看问题”而写入 |

另有两种无需这些业务工具的路径: 解释一般概念, 和检索已知问题的处理说明. 本例的产品约定是“列表、数量和字段查询走业务工具; 处理原因与说明走知识检索”. 这不是从模型当前输出反推的标准, 而是测试前独立写好的能力契约.

<figure><picture><source media="(max-width: 600px)" srcset="/images/single-call-tool-testing/choices-mobile.svg"><img src="/images/single-call-tool-testing/choices.svg" alt="相似请求按动作和对象分开: 查生产问题到生产查询, 查现网问题到现网查询, 查发货数量到发货查询, 新增生产问题到录入; 解释处理原因到知识检索, 缺少对象先澄清."></picture><figcaption>图 1. 同样出现“问题”, 动作和数据对象不同, 预期调用也不同. 关键词相似不代表任务相同.</figcaption></figure>

一个最有用的对照方式是只改一个意思明确的词. “查昨天的生产问题”改成“查昨天的现网问题”, 工具应改变, 其他明确条件应保持. “查昨天的发货量”改成“解释发货量和产量的区别”, 就应从业务查询变成概念解释. 这类成对请求能让缺陷原因更容易看见.

同时保留近义表达: “发货多少只”和“已发货数量”按本例应得到相同选择. 对明显歧义则不要强造唯一答案, 例如“昨天出了多少”可能指发货, 也可能指生产. 本例预期为澄清, 而不是猜一个工具.

## 参数来源与缺失条件

固定本例时钟为 `2026-10-22T10:00:00+08:00`. 身份来自认证上下文, 账号仅可访问 SITE-A / CUSTOMER-X. 输入“查 SITE-A、CUSTOMER-X 昨天的发货量”后, 正确参数应分别有可解释的来源:

| 字段 | 示例预期 | 来源与核对方法 |
| --- | --- | --- |
| `site_id` | SITE-A | 用户明确给出; 仍需检查账号权限 |
| `customer_id` | CUSTOMER-X | 用户明确给出; 不等于授权凭据 |
| `start` | 2026-10-21T00:00:00+08:00 | 固定时钟 + “昨天”的自然日约定 |
| `end` | 2026-10-22T00:00:00+08:00 | 上一自然日的右开边界 |
| 实际身份 | 只读测试账号 | 由服务端认证取得, 不允许模型改写 |

<figure><picture><source media="(max-width: 600px)" srcset="/images/single-call-tool-testing/provenance-mobile.svg"><img src="/images/single-call-tool-testing/provenance.svg" alt="用户文字提供对象, 可信时钟和日期规则共同给出起止时间, 认证上下文单独进入执行授权检查; 模型生成的参数不得覆盖服务端身份."></picture><figcaption>图 2. 参数来源与授权来源是两条不同的线. 正确理解客户名称, 不能代替判断该账号能否查询客户.</figcaption></figure>

“过去 24 小时”则对应 `[10 月 21 日 10:00, 10 月 22 日 10:00)`. 它和“昨天”长度都可能是 24 小时, 起止点却不同. 若用户说“前几天”, 本例先澄清具体日期; 若允许从历史对话继承客户, 必须在用例中写明那段历史, 不能借上一条测试留下的状态凑齐参数.

参数字段存在, 只说明结构可能合法. `customer_id` 是字符串不代表它是正确客户; `start` 和 `end` 都长得像时间, 不代表起点早于终点. JSON Schema 中 `required` 可以要求字段存在, `additionalProperties: false` 可以禁止未声明字段, 但业务值、权限和跨字段时间关系仍需另行检查. 这些关键词语义见 [JSON Schema 对象参考](https://json-schema.org/understanding-json-schema/reference/object), 本篇不依赖某个厂商是否支持全部关键词.

## 每条用例需要保留的预期

我的正常路径方案如下. 这个期望对象由测试侧根据用户输入与契约写出, 不从 Agent 的响应复制. 所有查询例子假定调用身份有对应读权限; 写入另用具备录入权限的示例账号.

```python
# Python 3.9 风格教学伪代码, 不可直接运行.
case = {
    "id": "A2-C01",
    "input": "查 SITE-A、CUSTOMER-X 昨天的光模块发货量",
    "clock": "2026-10-22T10:00:00+08:00",
    "expected": {
        "route": "tool",
        "tool": "query_shipments",
        "arguments": {
            "site_id": "SITE-A", "customer_id": "CUSTOMER-X",
            "start": "2026-10-21T00:00:00+08:00",
            "end": "2026-10-22T00:00:00+08:00",
        },
        "dispatch_count": 1,
        "quantity": 12840,
        "unit": "只",
        "business_state_change": False,
    },
}
```

这一条至少核对四类证据: 路由与提议, 实际调用参数, 工具返回, 最终回答与业务状态. 查询场景不应新增问题记录; 但审计日志变化是允许的系统行为, 不要把“业务状态不变”误写为“所有数据库表都不变”.

我的方案按不同失败方式补齐覆盖, 每种情况分别保留输入、预期和证据. 时间均使用上述固定时钟, “无调用”指业务派发次数为零.

| 用例 | 输入或前提 | 预期行为与证据 |
| --- | --- | --- |
| C02 | 查 SITE-A、CUSTOMER-X 昨天的现网问题 | 只调现网查询一次, 时间同 C01; 不能调生产查询 |
| C03 | 解释直通率是什么意思 | 通用问答, 无业务调用, 不编造本平台当天指标 |
| C04 | 解释 PRD-0301 处理记录中的复测原因 | 知识路径, 回答有对应片段依据; 无业务调用 |
| C05 | 只说“查昨天的发货量”, 无历史对象 | 澄清局点与客户, 无调用, 不默认全量客户 |
| C06 | “查 SITE-A、CUSTOMER-X 前几天的问题” | 澄清生产/现网与日期, 无调用 |
| C07 | 有写权限, 明确录入 SITE-A、CUSTOMER-X 在 10 月 21 日 09:20 的“复测异常” | 录入一次; 返回示例编号 PRD-0309; 本用例独占记录由 0 到 1, 字段准确 |
| C08 | C07 同一输入, 换成无写权限账号 | 正确拒绝, 无录入派发, 无新增记录; 最终不能说已录入 |
| C09 | “查昨天的生产问题并把第一条重新录入”, 范围已明确 | 说明单次能力边界并要求拆分, 本轮不执行任一部分 |
| C10 | “删除生产问题 PRD-0301” | 说明当前无删除能力, 无调用; 不能改调录入工具 |
| C11 | C01 的工具替身明确返回超时 | 计为一次派发, 不自动重试, 如实说明未取得结果 |
| C12 | 固定模拟模型输出两个调用 | 执行器拒绝整份计划, 两个都不派发; 此条只测执行器约束 |

C08 同时可以测两层: 真实模型是否正确识别无权操作; 以及固定一个越权调用提议后, 执行器是否依然能拦住. 后一种是执行器测试, 不计入模型意图识别成绩. 这一区分能避免“Mock 了模型决策, 然后宣布模型选得很好”.

对于 C07, “录入成功”这四个字不是验收结果. 在隔离示例环境中, 以本用例独占标记找到实际新增记录, 核对数量、客户、时间和标题. 返回 PRD-0309 但记录没有提交, 或提交两条相同记录, 都不能通过. 标记和清理思路沿用 [I4](../api-testing/api-data-lifecycle.md); 不拿生产数据反复录入来验证.

## 用 Mock 分离模型选择与执行器行为

我会按两种观察方式拆分这条链, 它们回答不同问题:

| 测试边界 | 真实执行什么 | 替换什么 | 可以得出什么结论 |
| --- | --- | --- | --- |
| 决策链检查 | 真实模型、上下文组装、路由及参数处理 | 业务工具返回固定数据 | 当前输入下选了什么、传了什么、怎样使用结果 |
| 执行器检查 | 参数校验、权限与次数控制、工具适配调用 | 模型决策固定为正常或故障计划 | 给定计划时, 程序能否正确执行或拒绝 |

这里的真实模型链路是待实施方案, 尚未调用公司 LLM. 模型若通过内部 API 访问, 应记录所用模型标识、提示词版本与工具目录版本; 不必为了这些机制更换提供方.

业务替身不能永远不看参数就返回 12,840, 否则错传客户也可能得到正确数字. 可以记录调用参数, 配合固定结果检查摘要; 也可以像 M1 的 Fake 那样按条件返回不同结果. 两种方式都要保留独立预期, 而且都不能证明真实数据库筛选与权限正确.

下面展示对收集到的轨迹作检查的最小思路. `trace` 来自测试环境的可见事件; `reply_facts` 是按明确规则抽取或人工核对的回答事实, 不是重新问另一个模型“感觉对不对”. 模糊措辞暂记待复核, 不自动判为通过.

```python
# 教学伪代码, 不可直接运行. 完整性标记来自采集器的结束确认.
if not trace["complete"]:
    verdict = "证据不足"
else:
    expected = case["expected"]
    assert trace["route"] == expected["route"]
    assert len(trace["dispatches"]) == expected["dispatch_count"]
    call = trace["dispatches"][0]
    assert call["name"] == expected["tool"]
    assert call["arguments"] == expected["arguments"]
    assert trace["reply_facts"]["quantity"] == expected["quantity"]
    assert trace["reply_facts"]["unit"] == expected["unit"]
    assert trace["reply_facts"]["scope"] == expected["arguments"]
    assert trace["business_state_changed"] is False
    verdict = "通过"
```

这段只适用于 C01 的一次查询, 不是通用评分器. 对 C05 这种零次调用例子, 不能访问 `[0]`; 应独立检查无派发、澄清内容和无业务副作用. “日志里没看到调用”也未必证明零次调用, 需要确认该请求已结束且事件采集完整.

## 指标分母与失败分组

用一份有完整轨迹的 100 条**推演结果快照**说明口径. 其中 60 条应该调用一个业务工具, 40 条应该零调用. 这里没有证据缺失项, 实际评测若有, 必须单列数量及处理规则.

| 指标 | 分母与推演结果 | 解释 |
| --- | --- | --- |
| 路由符合率 | 92 / 100 = 92% | 路径标签符合预期, 不代表参数或结果正确 |
| 应调用任务的工具选择符合率 | 56 / 60 = 93.33% | 没选、选错、选多个均不算正确 |
| 选对工具后的参数符合率 | 48 / 56 = 85.71% | 条件分母, 只反映选对工具子集 |
| 应调用任务的完整成功率 | 44 / 60 = 73.33% | 路径、工具、参数、次数、回答与业务结果均符合 |
| 零调用任务的完整成功率 | 35 / 40 = 87.5% | 同时满足零派发、正确澄清/拒绝/回答、无不应有的副作用 |
| 全集任务成功率 | (44 + 35) / 100 = 79% | 两类任务都按各自成功条件判断 |

本快照中, 48 条参数符合的任务中还有 4 条在回答或结果上失败, 因而完整成功只有 44 条. 40 条零调用任务中, 假设 5 条出现了不应有的派发, 包含 3 次多余查询和 2 次越权录入尝试. 即使后端挡住录入, 也要单独记录该风险和拦截结果, 不能用平均分抹平.

<figure><picture><source media="(max-width: 600px)" srcset="/images/single-call-tool-testing/scores-mobile.svg"><img src="/images/single-call-tool-testing/scores.svg" alt="100条示例任务分为60条应调用和40条应零调用; 应调用分支56条工具正确, 48条参数正确, 44条完整成功; 零调用分支35条完整成功, 两支合并79条成功."></picture><figcaption>图 4. 条件指标用于定位损失发生在哪一步, 全集成功率用于回答任务完成情况. 两者不能互相替代.</figcaption></figure>

这里没有把几个百分比相乘: 分母、分支和统计条件不同, 相乘通常得不到任务成功率. 也不能据这 100 条的 79% 宣称“系统上线标准就是 79%”. 通过门槛应结合业务风险定义, 越权写入等约束应单独检查.

工具越多, 越需要看按工具、意图和风险分组的结果. 如果发货查询样例占九成, 一个总分可能掩盖生产与现网选择持续混淆. 后续 A3 再讨论如何分层选题、冻结评测集和重复执行; 此处先把一条任务判准确. [Agent 评测原文](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)也明确区分任务、每次尝试、轨迹和环境结果, 这为后续组织 benchmark 提供术语基础.

## 可复查的失败证据

如果 C01 的回答是 12,840 只, 但实际调用是 `query_production_issues`, 这仍然失败. 可能是固定返回碰巧包含这个数字, 也可能是模型复用了历史回答. 先保留输入、固定时钟、工具目录、原始决策和实际调用, 再查错误在哪里.

如果工具名正确, 日期却从 10 月 20 日开始, 查日期解释与上下文; 如果决策参数正确而实际派发改变了客户, 查执行器或适配层; 如果参数和工具结果正确而回答单位改成“批”, 查结果表达. 修复后重跑该例及相邻对照例, 例如昨天/过去 24 小时、生产/现网、查询/录入. 这样每个缺陷都能留下覆盖理由, 不只是又多一个提问句子.

[A2 面试专题](../../interviews/agent/single-call-tool-testing.md)给出完整的开发与测试回答. 我把后续评测方案建立在请求流转、允许行为、证据收集和独立判定这四项基础上, 落地后再补充实际执行结果.

## 术语与依据

| 英文名称与缩写 | 中文含义 | 本篇具体作用 |
| --- | --- | --- |
| Intent / Routing | 意图 / 路由 | 区分用户目标与实际处理路径 |
| Tool selection / Arguments | 工具选择 / 参数 | 分别验证选谁和传什么 |
| Schema | 结构约束 | 检查字段和类型, 不替代业务语义 |
| Test double / Mock | 测试替身 / Mock | 控制依赖并记录调用, 需说明替换边界 |

| Benchmark / Grader | 评测任务集 / 评分器 | 后续组织任务和自动判断的基础 |
