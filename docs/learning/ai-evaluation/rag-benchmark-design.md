# 我的 RAG benchmark 设计: 任务、资料版本与回归证据

<p class="article-kicker">工作记录 · R5 · 设计思路与待验证方案</p>

我平时核对生产问题页面时, 会把筛选条件、接口响应和 SQL 查询结果放在一起看. 如果页面查的是“发生日期”, SQL 却按“更新时间”统计, 两边数字即使相同, 也没有证明功能正确. 把这个习惯延伸到 RAG, 我首先需要固定的同样是问题口径和独立依据.

[R3](retrieval-metrics.md)解决证据怎样核对, [R4](rag-answer-quality.md)拆开事实、上下文支持和引用. 到这里, 我需要把这些判断组织成一组能够反复比较的任务. 我的 benchmark 会包含任务、资料快照、身份与时钟、独立参考、评分约定和运行记录. 单独保存一张“问题 / 标准回答”表, 还不足以解释版本变化.

> 本文是我尚未落地的评测设计. 9 条任务、后文的资料更新和 100 条任务对比数字均为合成示例, 不是公司数据或实测结果. Python 3.9 风格代码是不可直接运行的伪代码. 本文未调用 LLM API, 没有生成一套已经验证有效的企业 benchmark.

## 我先固定一份能手工核对的资料

继续使用 [R1 的 D3 快照](../rag/rag-evidence-pipeline.md) `kb_d3_v1`. 时间为 Asia/Shanghai, 本例账号只允许访问 SITE-A / CUSTOMER-X. 每条 C 记录代表一个问题, G201 是指南, 不计入问题数量.

| ID | 类型 | 发生时间 / 文档日期 | 局点 / 客户 | 已知内容 |
| --- | --- | --- | --- | --- |
| C101 | 生产问题 | 2026-10-18 09:10 | A / X | 光功率波动, 已安排连接器检查, 原因待确认 |
| C102 | 生产问题 | 2026-10-20 14:30 | A / X | 复测告警, 已安排再次复测, 原因待确认 |
| C103 | 生产问题 | 2026-10-21 09:00 | A / X | 温度读数异常, 正在排查 |
| C104 | 生产问题 | 2026-10-19 11:00 | B / X | 复测告警, 正在排查 |
| C105 | 生产问题 | 2026-10-20 16:00 | A / Y | 光功率波动, 正在排查 |
| G201 | 排查指南 | 2026-10-17 | A / X | 复测告警排查步骤, 没有实际问题发生记录 |

表中的 A/X 是 SITE-A/CUSTOMER-X 的缩写. 完整快照由评测维护者用于建立参考, 不意味着模型或当前用户能看到 C104、C105. 权限过滤需要发生在资料进入模型上下文之前.

本例中“2026-10-21 之前”的边界固定为 `< 2026-10-21T00:00:00+08:00`, 按发生时间筛选. 我会把这条约定写入样本, 避免运行日期变化或默认时区改变预期.

## 我的第一组任务: 先覆盖判断分支

下面 9 条任务共用上述账号和快照. 它们用于把判定口径写清楚, 规模太小、资料关联太强, 不能代表真实请求分布, 也不构成独立的冻结测试集.

| 任务 | 用户问题与额外条件 | 独立参考与预期行为 | 主要检查 |
| --- | --- | --- | --- |
| T01 事实查询 | C102 的发生时间、局点、客户和现象是什么? | 10-20 14:30, A/X, 复测告警; 引用 C102 | 对象与字段绑定, 必答项完整 |
| T02 时间范围与全量列举 | 列出 10-21 之前 A/X 的全部生产问题, 给出 ID、发生时间和现象 | 仅 C101、C102, 各字段与源记录一致 | 不漏项, 不带入 C103、指南或越权记录 |
| T03 精确计数 | 10-21 之前 A/X 一共有多少条生产问题? | 完整合成快照中为 2; 需要可证明完整范围的查询依据 | 不能把 Top-K 返回条数当总数 |
| T04 跨记录关联 | C101 和 C102 哪条先发生, 是否已确认同一根因? | C101 更早; 两条原因均待确认, 无法确认同一根因 | 两条证据齐全, 顺序正确, 不推断共同根因 |
| T05 已知记录中的未知事实 | C102 已经确认的根因是什么? | 根因尚未确认; 引用 C102 的状态 | 不把再次复测写成根因或修复结论 |
| T06 相对时间 | 昨天 A/X 发生了哪些生产问题? 时钟固定为 10-21 10:00 | “昨天”按本例产品约定为 10-20 自然日, 仅 C102 | `[10-20 00:00, 10-21 00:00)` 和时区正确 |
| T07 范围不明确 | 前几天 A/X 有哪些生产问题? 没有默认时间规则 | 先澄清起止日期或天数, 不自行选范围 | 澄清意图和问题范围, 不要求固定话术 |
| T08 权限边界 | 请给出 C104 的详细情况 | 按本例约定提示无法提供该记录, 不透露存在性及业务字段 | 上下文和输出均不能泄露 C104 内容 |
| T09 检索依赖失败 | 问题同 T01, 但检索服务超时 | 表达当前无法完成查询, 保留依赖错误; 不断言记录不存在 | 系统不可用与业务无答案分开 |

T06 的自然日规则、T08 的对外提示方式, 都是这份合成方案的明确约定, 不是已经确认的公司产品行为. 接入实际项目时, 我需要先与需求和权限策略对齐这两项.

我会给每条任务附上类型、风险、证据依赖和期望行为标签. Ragas 对单来源与多来源问题的区分, 能帮助检查问题是否过于集中在单条资料查字段; 具体的时间、权限和业务状态仍需按这里的业务约定设计. [Ragas 测试集生成概念](https://docs.ragas.io/en/stable/concepts/test_data_generation/rag/).

T04 需要联合两条记录, 但不等于要求 Agent 进行两次工具调用. 一个受控检索调用也可以返回多条证据. 我不会据此改变当前 Agent 最多一次业务工具调用的限制, 更不会默认加上自动重试.

### 我特别保留精确计数这一条

T03 的标准数字虽然是 2, 但我的评分器不能只检查答案有没有这个数字. 假如检索器恰好返回 C101、C102, 模型就说“总共 2 条”, 它可能只是碰巧答对. Top-K 是候选截断条件, 不能证明全集只有两条.

在这份只有六条资料的样例里, 我可以从完整快照按类型、权限、时间过滤, 得到集合 `{C101, C102}`. 真正业务里, 如果问题表才是数量的权威来源, 我会用具备完整范围保证的结构化查询核对计数. 文档问答链路如果只有相似片段检索, 就需要明确无法确认总量, 或走已经获准的结构化查询路径.

因此我会为计数任务声明能力目标. 当前只支持片段检索的版本, “说明无法确认总量”可以通过诚实性检查, 但仍是计数任务未完成; 不能把它计成已具备精确统计能力. 若两个版本能力范围不同, 报告中保留这一差异, 不删掉困难样本来提高通过率.

## 我怎样建立独立参考

我会先从冻结的源记录整理预期, 再运行被测链路. 如果公司已有权威业务表, 我会像做 SQL 数据比对一样确认记录唯一键、发生时间字段、权限过滤和查询范围. 对文档内容, 则保存来源、修订版本和具体支持片段. 被测系统这一次检索出了什么, 不能反过来决定“应该有哪些证据”.

T02 的参考不是一段必须逐字复现的回答, 而是两条记录、各自字段、来源和禁止出现的结论. C101 和 C102 的顺序可以不同, 同义描述可以接受, 但不能漏一条, 不能将日期交换, 也不能把“待确认”写成“已解决”.

下面是 T02 的一份简化样本. `model_input` 是允许进入应用的输入; `evaluator_only` 仅供评测端使用. `C101@kb_d3_v1` 是本文的源记录版本标识, 不是某个框架规定的语法. 实际落地还需保存快照内容摘要, 不能只相信一个可被覆盖的名字.

```json
{
  "case_id": "T02",
  "family_id": "production-list-before-date",
  "benchmark_version": "d3_r5_demo_v1",
  "environment": {
    "source_snapshot": "kb_d3_v1",
    "principal_scope": {"site": "SITE-A", "customer": "CUSTOMER-X"},
    "now": "2026-10-21T10:00:00+08:00",
    "timezone": "Asia/Shanghai"
  },
  "model_input": {
    "question": "列出2026-10-21之前SITE-A/CUSTOMER-X的全部生产问题, 给出ID、发生时间和现象."
  },
  "evaluator_only": {
    "response_mode": "answer",
    "time_field": "occurred_at",
    "end_exclusive": "2026-10-21T00:00:00+08:00",
    "required_records": [
      {"id": "C101", "occurred_at": "2026-10-18T09:10:00+08:00", "phenomenon": "光功率波动"},
      {"id": "C102", "occurred_at": "2026-10-20T14:30:00+08:00", "phenomenon": "复测告警"}
    ],
    "required_evidence_groups": [["C101@kb_d3_v1"], ["C102@kb_d3_v1"]],
    "forbidden_claims": ["原因已确认", "问题已解决"],
    "reference_review_status": "synthetic_hand_checked"
  }
}
```

`required_evidence_groups` 在这份方案里表示“组间都需要, 组内允许等价来源”. 本例每组只有一个来源. 将来同一事实可能在经确认的工单与报告中都有依据, 我会列出经过复核的替代来源, 不因系统找到不同的有效证据就误判失败. 业务记录、源文件和切片 ID 也需要建立映射, 不能把一个记录的三个切片当作三个不同问题.

参考由谁确认、何时确认、仍有哪些争议, 我都会单独记录. 大模型可以辅助提出问题或草拟参考, 但我不会让生成问题的模型同时充当唯一事实裁判. 不确定的参考先进入待复核集合, 不进入正式通过率分母; 数量与原因必须报告, 不能静默消失.

## 从 9 条示例走向可用的回归集

真实任务来源会是经过授权与脱敏的请求、历史缺陷和风险设计. 高频请求帮助确定常见路径, 缺陷帮助保留容易退化的边界, 人工设计补充不常见但后果严重的权限和状态问题. 我目前没有这类实际请求样本, 所以不会给这 9 条示例冠以“生产分布覆盖率”.

建立开发集和冻结评估集时, 我会先按语义任务族、同源问题和近似改写分组, 再分配集合. “C102 什么时候发生”和“给出 C102 发生日期”不能因为字面不同就被随机拆到两边, 否则开发时实际已见过同一道题. 如果还要评估对新业务实体或新资料的泛化, 我会另外设计来源隔离的集合, 并说明它衡量的能力不同.

这里有一个我需要分清的边界: RAG 的知识库本来就应该包含回答所需的业务资料. 冻结问题对应的源记录出现在可检索快照中, 本身不是答案泄漏. 泄漏发生在评测问题、参考答案、评分提示或针对测试集整理的答案文档进入被测提示词、示例或索引, 使评测失去原本想测的含义.

冻结集也不是永远不看. 发现失败后可以分析和修复, 但频繁针对同一组题调参后, 我会把它称为回归集, 保留后续未参与调优的新集合验证泛化. 这 9 条任务全部公开在正文中, 本来就只承担设计演示, 不声称具备防泄漏能力.

## 我会把“版本”拆成能定位变化的几部分

LangSmith 文档支持数据集版本和指定 split 的评估. 这提醒我任务集需要版本化, 但工具里的数据集版本并不自动覆盖外部业务资料、权限规则或索引. 这些依赖仍需由评测方案单独固定. [数据集管理与版本](https://docs.langchain.com/langsmith/manage-datasets).

| 记录对象 | 我会保存的内容 | 为什么影响结论 |
| --- | --- | --- |
| 任务与参考 | 样本集合摘要、参考修订、任务族、待复核状态 | 问题或预期变化会改变难度和通过条件 |
| 资料与权限 | 源快照摘要、记录修订、可见范围、时区与时钟 | 决定应当回答什么、允许知道什么 |
| 检索与索引 | 切片策略、嵌入模型标识、索引构建、过滤、K、重排配置 | 决定哪些资料进入上下文 |
| 回答生成 | 提示词版本、模型标识、采样参数、实际输入输出 | 决定相同证据如何形成回答 |
| 评分与运行 | 规则版本、评判提示和模型、运行时间、失败阶段 | 决定怎样判分, 是否有缺失或外部失败 |

如果比较的目标就是新的切片或检索方案, 两边索引配置当然可以不同, 但必须来自同一份冻结源资料, 并把差异记录为本次改动. “固定条件”指控制无关变化, 不是禁止被测方案发生变化.

### 一次资料修订怎样影响已有样本

我另设一个**假想 v2**, 仅将 C102 的发生时间从 `2026-10-20 14:30` 更正为 `2026-10-21 08:30`, 其余内容不变. 这是用于分析依赖的新情境, 不回写 R1–R4 的 v1 事实.

| 受影响任务 | v1 参考 | 假想 v2 参考 |
| --- | --- | --- |
| T01 字段查询 | 发生时间 10-20 14:30 | 发生时间 10-21 08:30 |
| T02 10-21 之前的列表 | C101、C102 | 仅 C101 |
| T03 同范围精确数量 | 2 | 1 |
| T06 10-20 自然日的问题 | C102 | 空集合; 前提是完整范围已被查询 |

T04 仍是 C101 更早, T05 仍是原因待确认. 它们的最终文字可能不变, 但引用的 C102 版本已变, 仍需复核并重跑相关路径. T08 的权限用例和 T09 的故障用例也要确认新快照下的前置条件. 依赖表帮助缩小人工审查范围, 不能代替一次发布所需的整体回归.

<figure><picture><source media="(max-width: 600px)" srcset="/images/rag-benchmark-design/version-mobile.svg"><img src="/images/rag-benchmark-design/version.svg" alt="假想 v2 将 C102 日期由 10 月 20 日改为 21 日, 影响四条任务的参考. 比较算法 A 和 B 时, 应在同一 v1 或同一 v2 行内比较, 不能拿 A 的 v1 分数与 B 的 v2 分数直接归因."></picture><figcaption>图 3. 我会同时追踪资料到样本的依赖和版本比较的坐标. 更正源记录后, 索引与参考都需要同步.</figcaption></figure>

如果 A 版本在 v1 上测得 82%, B 版本在 v2 上测得 86%, 我不能把 4 个百分点全部归因给 B. 我的做法是在同一资料和任务参考下运行 A、B. 需要分析资料变化时, 再补齐 A/v1、B/v1、A/v2、B/v2 四个组合, 各行比较方案, 各列观察资料变化. 不支持旧快照重放时, 就明确说明无法完成这种归因.

## 我的执行记录会保留在哪一层出错

端到端评测会让系统从问题开始执行实际检索与生成, 用 R3 检查检索证据, 用 R4 检查回答. 另一个诊断实验可以固定正确上下文, 只看生成是否仍出错. 后者能帮助定位, 但不能作为端到端结果与前者混算, 因为它跳过了检索困难.

下面只表达执行顺序, 所有函数都是占位设计. 环境中的身份由测试运行器配置, 不能相信用户在问题里自报“我是管理员”. 这段伪代码不包含真实鉴权、快照加载或模型接入实现.

```python
# Python 3.9 风格设计伪代码, 不可直接运行.
def evaluate_suite(manifest, cases, system):
    verify_frozen_assets(manifest)
    results = []
    for case in cases:
        environment = configure_environment(case["environment"])
        trace = run_and_capture(
            system=system,
            question=case["model_input"]["question"],
            environment=environment,
            fault=case.get("fault_fixture"),
        )
        if trace.harness_failed:
            results.append(record_incomplete(case, trace))
            continue
        reference = case["evaluator_only"]
        checks = grade_behavior_and_evidence(trace, reference, manifest)
        results.append(record_checks(case, trace, checks))
    return report_with_denominators(results)
```

这里的 `harness_failed` 指评测运行器本身没有完成观测, 不能直接算系统答错. T09 则是预先注入的被测依赖超时: 只要运行器捕获到系统行为, 就应按 T09 的错误处理约定评判, 不因出现超时字样就跳过. 意料之外的真实服务超时也要报告为被测系统运行失败, 与评分器超时、运行器故障分开.

评分器遇到参考争议或缺少证据时, 我沿用 R4 的 `review` 状态. 已确认的权限泄漏或事实违规仍判 `fail`, 同时保留未决项. 我不会因为 LLM 评分器刚好没返回就覆盖已有的确定性失败证据.

## 版本对比时, 我更想看到哪几条变坏了

下面独立设想一个 **100 条任务、每条运行一次、所有任务均完成评分** 的对比报告. 它不是前面 9 条任务的运行结果, 也不是已经制作好的百条数据集.

| 同一任务的状态变化 | 数量 | 我会怎样处理 |
| --- | --- | --- |
| A 通过, B 通过 | 78 | 保留共同通过证据 |
| A 通过, B 失败 | 4 | 逐条看退化, 优先查权限与错误业务结论 |
| A 失败, B 通过 | 8 | 核查改善是否来自预期改动 |
| A 失败, B 失败 | 10 | 保留未解决问题, 不从样本中删除 |

A 的通过率是 `(78 + 4) / 100 = 82%`, B 是 `(78 + 8) / 100 = 86%`, 净提升 **4 个百分点**. 这个总数同时掩盖了 4 条退化和 8 条改善. 如果 4 条退化里有一条泄露越权资料, 我的发布判断就不能只依据总分上升.

A 共 82 条通过, B 共 86 条通过, 净提升 4 个百分点仍包含 4 条退化."></picture><figcaption>图 4. 对比单位是同一条任务, 不是两份没有对应关系的平均分. 这组数字只展示报告的计算方式.</figcaption></figure>

如果 100 条里有 3 条评分未决, 我会同时报告“已确认通过数 / 100”“已完成判定 97/100”和 3 条未决原因. 需要展示“通过数 / 97”时, 会明确它是已判定子集的比例, 不能替换全量口径. 每个业务类型也保留分母, 防止高频简单题遮住少量权限或计数任务.

对有随机性的输出, 我会进一步安排重复运行, 保留每条任务各次结果和通过频次. 例如两个版本、100 条任务、每条 3 次, 共 600 次被测执行, 不含评分器额外调用. 这只是计划规模, 不是“运行三次就足够”的通用门槛. 我会交错运行版本以减少时间漂移, 记录模型实际标识; 即使接口提供 seed, 也不承诺完全可复现. 固定参考的抽样人工复核仍需检查评分器是否稳定.

我最终想得到的是一份能够回答“哪些问题改善了、哪些问题退化了、证据是否可靠、还剩多少未决”的记录. 这与我已有的接口和数据比对经验能接起来, 也让我看见尚未具备的能力: 真实样本采集、参考复核、快照重放和模型评分校准都还需要实施验证.

配套[面试记录](../../interviews/ai-evaluation/rag-benchmark-design.md)整理了我会如何说明这份设计与实践边界. 后续 Mock 内容再把这里的依赖超时等情境落实到可控的测试替身方案.

## 术语与依据

| 英文名称与缩写 | 中文含义 | 本文使用方式 |
| --- | --- | --- |
| Benchmark | 评测基准 | 一组带环境、参考、评分与运行约定的任务 |
| Reference / Ground truth | 独立参考 / 真值依据 | 从冻结权威来源建立, 保留未知和复核状态 |
| Snapshot / Manifest | 快照 / 清单 | 固定资料与运行依赖, 记录版本及内容摘要 |
| Split / Holdout | 数据划分 / 留出集合 | 按任务族分组, 区分调优与后续验证 |
| Leakage | 泄漏 | 评测专用问题或答案进入被测输入, 破坏评测目的 |
| End-to-end / Fixed-context | 端到端 / 固定上下文 | 完整链路评估与生成诊断, 分开报告 |
| Paired comparison | 成对比较 | 在相同条件下逐条对照两个方案的结果 |
| Harness / Grader | 评测运行器 / 评分器 | 分别负责执行观测和证据判定 |
