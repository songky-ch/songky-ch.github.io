# 美团 Agent 评测全览带读: 从四个模块到可运行双环

用户说“给 A 门店做一份销售报告”, 系统可能回了“已完成”, 却查错门店, 或根本没有生成报告. 这种会根据任务选择工具并执行动作的系统, 就是智能体 (Agent). 评测要把报告、调用记录和评分规则对起来看, 才知道任务办得怎样, 下一步该改哪里.

本文沿着美团原文, 用同一个销售报告案例走完“发现问题 → 留下证据 → 分开修系统与评分规则 → 重新验证”的过程. 最后有一份无需账号的本地练习.

配套阅读: [开发与测试面试专题](../../interviews/ai-evaluation/meituan-agent-evaluation-overview.md).

## 学完能做什么

学完能把“报告做得好”写成几条可检查的条件, 分清是系统做错、评分规则判错, 还是日志不够, 并解释为什么得分提高仍可能不能发布.

前置条件: 能阅读 Python 字典、条件分支与测试断言. 本文不要求评测平台或模型账号.

本文的案例、图和代码都是教学补充. 来源与事实核查沿用 2026-10-17 的记录, 详细读取范围放在文末. 本次图文更新于 2026-10-19, 没有把格式更新当作重新核实原文或完成真实线上实验.

## 1. 先看全景: 一个线上问题怎样回到下一次验证

原文位置: 第一节 1.2、1.4 与第七节. 可以先抓住两件事: 一路把系统的能力修好, 另一路把样本和评分规则补准. 两路都要重新验证, 再用真实任务继续找问题. 这就是原文的两条反馈循环 (Loop). 四个模块负责承接这些工作, 各团队可以按自己的分工实现. [官方原文](https://tech.meituan.com/2026/09/10/Agent-Evaluation-White-Paper-01.html#_1-4-评测体系的构成).

![评测模块、共享样本与两条迭代循环](/images/meituan-agent-evaluation-overview/dual-loops.svg)

读图从 ① 开始: 真实运行产生记录, 在线质量判断、系统监控、用户反馈和抽样提供线索; ② 把线索对应到同一份样本, 检查证据. 如果缺了必要记录, 先走左侧的补采集路径, 补齐后回到 ②.

证据足够时到 ③ 分别检查系统行为和评价标准. ④ 的两路可以同时进入: 查错门店要修系统, 评分还给它通过就同时修标准. 然后把复核样本及修改版本带入 ⑤ 回测. 未满足发布条件时回到 ③ 复核, 满足后才到 ⑥ 受控线上验证. 新线索再回到 ②, 两条循环才真正接上. 分支的具体判法在第 3 节展开.

下面的表把职责翻译成本文教学案例里的具体产物. 案例是“为 A 门店生成销售报告”, 与原文商家分析场景相近, 但数据和实现由本文重新构造.

| 模块 | 要回答的问题 | 本例应留下什么 |
| --- | --- | --- |
| 离线评测 | 这次改动是否破坏已知能力? | 同一任务、同一标准、同一销售快照上的版本对照 |
| 在线评测与监控 | 实际用户任务是否成功, 运行是否异常? | 报告完成判定、工具错误、耗时, 连同各自分母 |
| 样本挖掘与归因 | 哪个样本值得复查, 问题在哪一层? | 错误门店参数、缺失报告、误判标准或证据缺口 |
| 观测基建 | 能否还原实际执行的输入、动作与结果? | 门店参数、返回数据、报告产物、运行关联标识 |

这张表是实施映射, 不是四套必须分别建设的服务. 一个脚本、一份任务表与一套可追踪记录也能承担最小职责.

## 2. 怎样把“给 A 店做报告”写成可检查的任务

原文位置: 第二节 2.1.1、2.1.2. 先固定用户要求和销售数据, 再写清什么结果算完成. 这样的一次检查单元叫任务 (Task); 把要求拆成逐项能判断的规则, 就得到评价标准 (Rubric). 原文用“问题、参考答案、评价标准”三元组组织这份资产. [原文定位](https://tech.meituan.com/2026/09/10/Agent-Evaluation-White-Paper-01.html#_2-1-1-评测集的构成).

教学任务的输入不是一句孤立的“做报告”, 还需要固定任务所依赖的事实:

```json
{
  "task_id": "sales-A",
  "input": {"shop": "A", "sales_snapshot": {"A": 100, "B": 9}},
  "expected_outcome": {"artifact": {"shop": "A", "sales": 100}},
  "rubric": {
    "tool_scope": "查询参数指向 A 门店",
    "artifact_exists": "报告产物存在",
    "artifact_correct": "产物门店为 A, 销售额为 100"
  }
}
```

上面用结构化数据格式 (JSON) 表示本文的教学任务, 不对应任何平台接口. 数值 100 来自合成销售快照; 真实系统还要固定日期、统计口径和数据来源.

### 端到端结果与过程证据各看什么

从用户请求一直验到最终交付, 叫端到端检查 (End-to-End / E2E). 本例要读取实际报告, 检查门店和销售额. 过程检查则沿调用记录核对参数、返回值和条件是否正确传递. 两路都从同一份任务要求出发, 分别拿自己的证据做判断:

![一份任务分别约束最终交付与执行过程](/images/meituan-agent-evaluation-overview/task-contract.svg)

读图先看上方固定的 A 店数据, 再沿两路分别往下走. 左路拿报告验证“有没有交付、内容对不对”; 右路拿工具记录验证“查的是不是 A 店”. 如果报告独立可验, 即使右路缺记录, 左路仍可保留自己的结果; 本例把两路合起来发布时, 需要的过程证据缺失就记为未知. 这个区分避免一句“失败”吞掉所有细节.

两路可能出现这些组合:

- 工具返回成功, 但查的是 B 门店: 调用状态正常, 业务任务失败.
- 查询和聚合都正确, 最后没有报告: 过程前半段正确, 端到端失败.
- 用另一种合法顺序得到正确报告: 不应因顺序不同而扣分, 除非任务明确约束该顺序.

最后一点是教学边界: 过程检查应针对必要约束, 不把唯一示范轨迹当作唯一合法策略. 本例固定查询工具是为了让练习容易验收; 它不要求真实业务必须使用同一个工具.

### 资产用途与评测对象是两个维度

原文的评测对象区分与资产用途区分可以交叉. 例如错题集既能保存“产物没生成”的端到端任务, 也能保存“跨门店参数错传”的过程检查. 黄金样本用来对齐业务质量, 挑战样本用来探索困难边界; 它们都需要明确来源、标准和适用范围. 本例的五条合成样本只演示机制, 不能充当真实业务的黄金集.

## 3. 发现坏样本后, 修系统还是修评分规则

原文位置: 第四节 4.3. 先按业务事实复核, 再检查两件事: 系统是否做错了, 评分规则是否把它判对了. 两个问题要分别回答, 所以同一个样本可能要改两处. [原文定位](https://tech.meituan.com/2026/09/10/Agent-Evaluation-White-Paper-01.html#_4-3-归因-从-这里出了问题-到-为什么出问题).

教学旧标准是“回复包含 `已完成` 即通过”. 它至少有两类问题:

| 可观察事实 | 旧标准结果 | 复核结果与去向 |
| --- | --- | --- |
| 回复“已完成”, 实际查错门店 | 通过 | Agent 的选参有错, 标准也漏检; 两路都要修 |
| 回复“已完成”, 但没有报告 | 通过 | 产物未交付, 同时是标准误放行 |
| 报告正确, 回复“报告已生成” | 失败 | 标准误拒绝, 无需强迫 Agent 改成固定措辞 |
| 缺失查询记录 | 可能通过 | 过程结论未知, 先恢复所需证据 |

把失败结果判成通过, 叫误放行 (False Accept); 把正确结果判成失败, 叫误拒绝 (False Reject). 要先拿独立复核的业务事实当参照, 才能判断规则犯了哪种错.

![必要证据缺失时先补采集, 证据齐全后独立判断两种修复](/images/meituan-agent-evaluation-overview/rubric-routing.svg)

读图可以走两个样本. “查 B 店却回复已完成”有完整证据: 左路认定业务错了, 右路发现旧标准误放行, 因而两路都产生修复项. “查询记录缺失”则在最上方走未知出口, 不进入下方的业务对错比较; 补齐后回到证据检查. 这对应脚本中先检查 `tool is None`, 再比较两个标准的顺序. 若某路无需修改, 它也带着明确结论进入共同回测, 不会被误当作另一条路的前置条件.

还要分清“确定没交付”和“不知道交付了没有”. 本例 `no_artifact` 明确表示没有生成报告, 所以是失败; `missing_trace` 表示过程记录缺失, 所以对应检查未知. 实际业务也需要能区分这两种证据状态.

图中的补采集、修复和重跑是需要执行的后续工作. 配套脚本只回放合成记录、计算结论并标记去向, 不会自动采集日志或修复系统.

下面是教学伪代码, 不可直接运行. `review_evidence` 代表按业务事实复核, `revise_agent` 和 `revise_rubric` 分别对应两个修改流程, 并不是真实软件接口.

```python
for case in sampled_cases:
    review = review_evidence(case)
    if review.evidence_missing:
        collect_missing_evidence(case)
        continue
    if review.agent_defect:
        revise_agent(case)
    if review.judge_disagreement:
        revise_rubric(case)
    add_reviewed_case_to_versioned_dataset(case)
replay_versions_on_same_dataset_and_rubric()
```

“同一标准”很关键. 如果旧版 Agent 用旧标准、新版 Agent 用新标准, 分数改变混合了系统能力变化与尺子变化. 应先在同一批记录上对比两把尺子, 再用固定的新标准比较两个 Agent 版本. [Langfuse 数据集文档](https://langfuse.com/docs/evaluation/experiments/datasets#versioning)提供了数据版本与生产记录入集的对应概念; 本练习仅记录版本标识, 未接入该平台.

## 4. 用户改了上一轮要求, 怎样沿记录找到出错点

原文位置: 第五节. 要判断“第二轮改成了本周, 为什么还出了上周的报告”, 得先把这一轮收到的要求、调用参数、返回数据和报告接起来. 一次执行的关联追踪叫 Trace, 其中一个有起止时间的操作单元叫 Span. 这两个名字的含义采用开放遥测体系 OpenTelemetry 的[官方定义](https://opentelemetry.io/docs/concepts/signals/traces/#spans), 不要求采集模型不可获得的内部思考.

![会话、执行与操作的关联层级](/images/meituan-agent-evaluation-overview/evidence-chain.svg)

读图先看会话 S1 中的第一轮要求, 再从第二轮向右跟踪消息: 当前条件应更新为“A 店 + 本周”, 工具也应收到这两个条件, 最后报告保留同样口径. 底部把三种异常与要回查的证据排在一起: 参数错了先查状态和选参; 参数对而数据错了查工具处理; 数据对而报告错了查产物生成.

图只把正确链路画成时序, 异常表提供排查方向. 第一处异常只是线索, 要用上下游记录和复现继续验证根因. 会话、轮次与任务是应用层的关联字段, 图中标识不是实际遥测报文.

本文建议记录的最小教学字段如下, 字段选择来自检查需求:

| 字段或证据 | 用途 |
| --- | --- |
| `session_id`, `task_id`, `turn_id` | 区分会话、跨轮目标和具体轮次 |
| `trace_id`, `span_id`, `parent_span_id` | 关联某次执行和它的子操作; 实际接入时按协议格式生成 |
| 用户本轮输入、当前业务约束 | 判断新指令是否覆盖了旧条件 |
| 工具名、参数、结果、时间 | 区分选参错误、工具错误和后续使用错误 |
| 产物或最终状态的稳定引用 | 独立验证报告是否存在、内容是否正确 |
| Agent、数据、标准、环境版本 | 让版本对照可以解释和复现 |

多轮例子: 第一轮要求“上周销售”, 第二轮改成“改为本周, 仍看 A 店”. 只看第二轮最终回复, 无法确定是否保留门店并更新了日期. 应顺序检查: 接收到的会话约束 → 工具日期与门店 → 数据 → 报告. 若下游使用了错误日期, 再核对上游传入的信息, 才能区分状态传递、参数构造与工具处理的问题. 第一处观察到的错误是定位线索, 不自动等于最终根因.

操作跨服务时, 把追踪关联信息随请求传过去, 这叫上下文传播 (Context Propagation); 异步或独立执行还可以用跨度链接关联. 会话标识属于应用层组织方式, 不需要把整段长会话塞成单一追踪. 这些是基于 OpenTelemetry 的教学设计, 不代表美团实际字段或架构.

证据不足的处理取决于检查项. 如果只缺过程记录, 但最终产物可独立验证, 可以报告“结果通过、过程未知”. 本例要求结果和过程都满足条件, 因而联合判定记为 `None`, 另报证据覆盖率. 真实环境只保存获准保留的必要数据, 不把原始用户记录带入公开练习.

## 5. 怎样分清能力变好了, 还是评分规则变了

### 先把同一批记录交给两把尺子, 再比较版本

原文第二节强调控制输入、标准和环境. 本例固定 `d1` 数据与 `r2` 标准, 只改变门店选择行为. 真实回测还要隔离每次试验的文件、数据库和缓存, 并记录模型、工具和知识版本. 若下游快照发生变化, 不能把分数变化直接归因于提示词修改. Anthropic 原文的 “Design the eval harness and graders” 也强调每次试验从干净环境开始. [补充来源](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

![固定同一批记录, 先比较标准, 再固定标准比较版本](/images/meituan-agent-evaluation-overview/controlled-comparison.svg)

读图先横着看: 旧版的同一批运行记录, 旧标准给 3/4, 新标准给 2/4, 差的是评分方法. 再沿新标准这一列向下看: 旧版 2/4, 新版 3/4, 差的是门店选择修复. 直接从左上角跳到右下角, 会把两个变量混在一起. 表里的分母始终是四条证据完整记录, 另有一条未知样本单独报告.

这个对照保存的是运行结果, 不是让旧记录随着新标准重新“执行”一遍. 规则可在相同记录上重评; 比较系统版本时才需要各版本自己的执行证据.

### 多跑几次, 要先说清楚“成功”指什么

美团 2.2 将重复试验与 Pass@k 放在同一条表述中. 真正计算时, 要把三个问题分开: 一次执行叫一次试验 (Trial); 成功试验数除以试验总数, 是试验通过率 (Pass Rate). 如果允许尝试 $k$ 次、其中一次成功就够, 看 pass@k; 如果要求这 $k$ 次每次都成功, 看 pass^k. [Anthropic 对随机性的说明](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

仅在同一任务的各次试验独立且成功概率相同为 $p$ 的简化条件下:

$$
\mathrm{pass@}k = 1-(1-p)^k, \qquad \mathrm{pass}^{k}=p^k
$$

把 $p=0.75$, $k=3$ 代入: 单次通过率是 75%; 至少一次成功为 $1-0.25^3=0.984375$, 约 98.44%; 三次全成功为 $0.75^3=0.421875$, 约 42.19%. 这里是概率模型示例, 不是三个真实样本足以估计可靠性的结论. 重复使用同一缓存或共享故障会破坏独立性; 多种任务混合时应逐任务估计后按已声明权重汇总.

本练习是确定性回放, 重复运行不会产生新的独立模型试验, 不用它测量真实 pass@k.

### 回测过关后, 还要验证真实任务

原文第三节分别讨论线上质量与运行指标. 本文把线上操作翻译成以下待实施方案, 本次未实际执行:

- 影子模式: 复制真实请求到隔离执行环境, 验证真实输入下的质量; 有写副作用的工具必须隔离, 避免重复提交业务动作.
- 随机分组对照实验 (A/B Test): 在可比较的分组上检查业务收益与约束, 避免仅比较两段时间的平均分.
- 巡检: 周期运行少量代表性任务, 保存失败证据与分数变化.

工具接口全部返回成功, 并不能证明报告内容正确. 任务比例变化也能改变总成功率, 因此同时报告任务分层、样本量、质量判定与系统错误. 本文不规定通用上线阈值, 也不把得分提高等同于业务价值已被验证.

## 6. 本地跑一次: 分数提高了, 为什么仍然挡住发布

环境: Python 3.9 或更新版本, 仅使用标准库, 不安装依赖、不访问网络. <a href="/examples/meituan-agent-evaluation-overview/practice.py" download>下载完整代码</a>, [查看本次完整运行结果](/examples/meituan-agent-evaluation-overview/practice-results.txt).

输入是脚本中的五种合成记录: 正常、查错门店、报告缺失、合法同义回复、过程证据缺失. `v2` 只修复查错门店, 保留其他问题, 这样可以观察回测是否诚实地保留未解决的风险.

1. 下载 `practice.py`, 阅读 `cases` 和两个版本的构造逻辑.
2. 在保存文件的目录运行:

```bash

```

读图从新版的五条记录开始. 三条通过、一条报告缺失、一条过程证据缺失, 分别进入三个状态. 图中先问五条是否都有所需证据: 本例只有 4/5, 因而走“阻断, 补证据”出口. 即使补齐第五条, 原来的报告缺失仍会在下一关阻断, 需要交付修复并重新回放; 只有五条证据齐全且全部通过, 才进入允许出口. 两个阻断出口都回到原始五条任务重新验证. 两关用于解释本例条件, 脚本用 `passed == len(rows)` 实现同一发布要求.

这里的 3/4 是“可判定样本中通过多少”, 4/5 是“全部样本中证据够多少”. 把两者并列, 才能看见未知样本. 这套五条全过的门禁只服务教学, 真实业务要另行声明哪些条件必须满足.

### 最小练习与验收

- 在本地副本修复 `no_artifact` 的产物交付, 并相应修改预期断言. 保留缺失证据分支时应得到四条可判定样本全部通过、总覆盖仍为 4/5、门禁仍为 `BLOCK`.
- 再补回 `missing_trace` 的所需证据, 更新预期. 验收应为新标准 5/5、覆盖 5/5、门禁 `ALLOW`. 如果有任一缺口仍为 `ALLOW`, 检查是否误把未知样本排出了门禁分母.
- 添加“只修改报告措辞, 内容不变”的样本. 验收: 新标准判定不变; 旧标准可能变化, 说明它依赖无关表面特征.

## 7. 遇到这些现象, 先查哪份证据

| 现象 | 先查什么 | 不能直接下的结论 |
| --- | --- | --- |
| 离线高分, 线上质量低 | 输入分布、环境快照、标准和结果证据 | 直接认定模型变差 |
| 工具正常, 最终结果错 | 业务参数、返回值语义、聚合与产物 | 调用成功就算业务成功 |
| 人工与评分器分歧 | 独立复核依据、条目歧义、缺失证据 | 一律要求 Agent 迎合评分器 |
| 总分变化, 分层分数稳定 | 任务类型比例与汇总权重 | 一定是版本能力改变 |
| 同一失败连续出现 | 共享工具故障、残留状态、数据版本 | 多次结果就一定独立可信 |

自测 1: 旧标准和新标准分别评旧版与新版, 能证明新版更好吗? 参考答案: 不能, 版本与标准两个变量同时变化; 需要交叉复评或固定标准比较.

自测 2: 报告能验证, 但工具轨迹缺失, 是否必须判整个任务失败? 参考答案: 取决于任务契约. 可以分别报告结果通过与过程未知; 本练习的联合契约需要过程证据, 所以标未知并阻断示例门禁.

自测 3: 为什么“所有工具都正确”仍可能无法交付? 参考答案: 中间数据正确不保证最终报告存在、保存位置正确或内容合格. 需要独立验证最终状态.
