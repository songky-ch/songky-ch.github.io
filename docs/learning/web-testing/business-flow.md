# 从页面操作还原一条完整业务链

<p class="article-kicker">第一批 · W1 · 从现有功能测试经验出发</p>

你在生产问题平台填写一条记录, 点击提交, 页面提示“录入成功”. 随后回到列表, 却找不到刚才录入的问题. 这时应该把缺陷提给前端, 还是后端?

先别急着判断归属. 页面成功提示、录入接口返回、数据保存和列表展示, 是同一件业务里的不同观察位置. 把它们串起来, 才知道哪里出现了偏差. 你已有的页面操作、Postman 请求查看和 SQL 比对经验, 都能放进这条链路里.

本文沿着“录入一条生产问题, 再把它查出来”展开. 目标是能说清每一步的输入、输出和判定依据, 并在结果异常时找到下一条需要核对的证据.

> 本批采用某光电维护平台的生产问题业务作为背景. 字段、接口、数据规模、耗时和内部结构均为教学模拟, 不代表所在公司的真实实现或个人实测成果. 数值用于呈现具体项目场景, 不作为通用达标线. 不需要本地运行代码.

## 先规定这条记录怎样才算录入成功

我们构造一条记录: 局点 `SITE-A`, 客户 `CUSTOMER-X`, 问题标题“产测复测结果异常”, 发生时间为 `2026-10-20 09:18:00 +08:00`. 为便于查找, 本次测试还带上唯一的教学标记 `DEMO-20261020-A17`.

为什么要有唯一标记? 同样的标题可能已经出现过. 仅凭列表里出现一个同名问题, 无法证明它就是刚才提交的那条. 真实系统未必有这个字段, 可以按现有能力选择业务编号或其他可追踪标识, 但不要把不唯一的标题当成唯一证据.

这个教学系统约定: 只有记录成功提交保存后, 录入接口才返回创建成功和业务编号. 本次模拟返回的编号为 `PRD-20261020-0143`, 创建人由登录身份确定; 保存后能够按编号查询详情. 创建接口与列表接口在本例中读取同一套已提交数据, 不假设存在缓存、搜索索引或异步同步.

这些约定决定了成功的含义: 数据只新增一条, 关键字段正确, 当前用户能重新查到, 列表遵守筛选与排序规则. “弹出了绿色提示”只是其中一个观察点.

从图的录入请求开始看. 页面把输入转成请求, 服务判断是否允许录入, 然后写入数据. 如果规则不满足, 请求应当从失败出口返回, 不应产生新记录. 如果保存完成, 返回编号供后续查询. 列表请求属于另一次调用, 它仍然可能携带错误的条件.

## 页面、请求和数据, 应该怎样一一对照?

假设页面显示北京时间, 请求与数据库统一记录带时区信息的时间. 那么 `09:18 +08:00` 与 `01:18Z` 表示同一时刻. 字符串不同不一定是缺陷; 关键是转换后是否保持同一个业务时刻.

下面是同一条模拟记录的三个观察位置. 数据库列名只是教学说明, 实际应以字段定义为准.

| 核对项 | 页面输入或预期 | 录入请求 | 保存后检查 |
| --- | --- | --- | --- |
| 局点 | SITE-A | `siteId = SITE-A` | 局点关联正确 |
| 客户 | CUSTOMER-X | `customerId = CUSTOMER-X` | 客户关联正确 |
| 发生时间 | 10 月 20 日 09:18, +08:00 | `2026-10-20T01:18:00Z` | 与输入表示同一时刻 |
| 标题 | 产测复测结果异常 | `title` 完整传递 | 内容无丢失或意外截断 |
| 创建人 | 当前测试账号 | 不由页面任意指定身份 | 与服务认证的账号一致 |
| 唯一标记 | DEMO-20261020-A17 | `clientReference` | 新增且仅有一条匹配记录 |

核对时先检查明确的契约, 不一看到差异就报错. 例如页面允许标题首尾有空格, 服务约定保存时去除它们, 那么保存值与原始输入不逐字相同仍可能正确. 如果根本没有约定这种处理, 才需要先澄清需求.

图里时间表示可以转换, 客户关联却不能悄悄丢失. 测试的关键是找到应该保持不变的业务事实, 再检查它经过各层以后是否仍然成立.

下面用 Python 3.9 风格伪代码表达检查思路. `submit_issue`、`load_detail` 和 `query_rows` 分别代表发送请求、查询详情和读取允许核对的数据, 不是现成 SDK 方法. `to_utc` 表示按明确时区规范化, 不是字符串截取.

```python
# 教学伪代码, 不可直接运行.
before = query_rows(client_reference="DEMO-20261020-A17")
assert len(before) == 0

response = submit_issue(form_data)
assert response.status == 201
issue_id = response.body["data"]["id"]

saved = load_detail(issue_id)
rows = query_rows(client_reference="DEMO-20261020-A17")
assert len(rows) == 1
assert saved["siteId"] == "SITE-A"
assert saved["customerId"] == "CUSTOMER-X"
assert to_utc(saved["occurredAt"]) == "2026-10-20T01:18:00Z"
assert saved["createdBy"] == authenticated_user_id
```

这里先确认标记不存在, 再提交和查询, 避免旧数据掩盖失败. 这些检查针对本条用例, 并不证明系统整体支持并发去重或幂等提交; 后面的接口章节会单独讨论这类问题.

## 列表里没看到, 先检查它本来应不应该出现

为了让数据判断更像实际项目, 我们给出一组规模适中的模拟数据: 台账中有 18,426 条历史记录; 当前用户可见且符合局点、客户、时间条件的记录有 142 条. 本次新记录也符合这些条件, 在隔离且没有其他写入的样例中, 保存后两项数量分别变成 18,427 和 143.

列表每页 20 条, 所以 143 条需要 8 页, 最后一页有 3 条. 这三个量不能混用: 全表记录数是 18,427, 当前筛选总数是 143, 第一页返回数量是 20. 用“第一页没返回 143 条”报缺陷, 就是在拿不同口径比较.

本例筛选区间为上海时间 10 月 1 日 00:00 起, 到 10 月 21 日 00:00 之前, 即左闭右开区间. 新记录发生在 10 月 20 日, 应当被包含. 列表按发生时间倒序, 再以编号倒序作为同一时刻的稳定排序规则; 在本次固定样例中, 它是符合条件的最新记录, 应出现在第一页.

**反例一: 页面实际传的是截至 10 月 20 日 00:00 之前.** 请求把整天 10 月 20 日排除, 列表不显示新记录便有了具体解释. 需要继续确认是页面组参错误, 还是界面对结束日期含义表达不清.

**反例二: 请求条件正确, 列表响应里也有这条编号, 页面却没显示.** 这时已经把范围缩小到响应之后, 可以检查页面过滤、字段映射、分页状态或渲染过程. 仍不能仅凭现象指定某一行前端代码有错.

**反例三: 按编号查询成功, 正确的列表条件却查不到.** 此时检查列表查询逻辑、可见范围及读路径. 只有确认真实系统存在不同读模型或异步同步, 才引入相应时延约定, 不把“可能是缓存”当成默认解释.

## 一次操作用了 342 ms, 该怎样解释?

用户说页面慢时, 首先需要说明从哪里开始、在哪里结束. 下面都是为教学构造的单次观测, 不是性能结果:

| 观察范围 | 示例耗时 | 含义 |
| --- | ---: | --- |
| 点击到请求发出 | 24 ms | 页面校验和请求准备 |
| 浏览器请求发出到完整响应收到 | 286 ms | 这次网络请求的客户端观测范围 |
| 响应收到到页面更新完成 | 32 ms | 后续数据处理与渲染 |
| 点击到页面更新完成 | 342 ms | 上述三个连续、不重叠阶段之和 |
| 服务端记录的处理时间 | 214 ms | 位于请求期间, 计时边界由服务日志定义 |
| 数据库调用时间 | 68 ms | 包含在这次 214 ms 的服务处理范围内 |

`24 + 286 + 32 = 342`, 但不能再把 `214 + 68` 加进去, 那会把嵌套阶段重复统计. 也不能看到 `286 − 214 = 72` 就断言网络慢了 72 ms: 两处计时边界不同, 差值还可能包含代理、排队等服务日志未覆盖的部分.

Chrome 的请求时间明细能够帮助拆分网络阶段, 其中等待首字节的时间并不等于纯数据库耗时. 具体定义可查 [Chrome Network 时间明细](https://developer.chrome.com/docs/devtools/network/reference/#timing-explanation). 本文的六个数值是独立教学设计.

如果产品约定“正常数据范围内操作应在 2 秒内完成”, 还需要补上操作类型、负载、设备、网络、统计窗口和采用的指标. 342 ms 的一次样例即使小于 2 秒, 也不足以证明全部用户的 P95 或 P99 满足目标. 这批先把测量范围说清楚, 分位数与负载模型放在性能专题讲透.

## 把排查结果写成别人能够复核的描述

“录入成功后查不到”只是现象. 一份更有用的教学缺陷描述可以是:

> 在隔离测试数据中, 用指定账号录入 SITE-A / CUSTOMER-X 的问题. 创建接口返回 201 和编号 PRD-20261020-0143, 按编号查询的字段正确. 列表请求的结束时间为 2026-10-20T00:00:00+08:00, 而界面表示要包含 10 月 20 日. 将结束边界修正为次日 00:00 后, 同编号记录可见. 目前证据指向界面日期语义与请求参数不一致, 尚未定位实现代码.

这段描述给出条件、证据和已知边界. 修复后回归的重点也随之明确: 当天 00:00、当天最后时段和次日 00:00 附近的数据是否按约定进入列表. 你不需要先掌握整套架构, 也能通过这种方式把页面测试做深.
