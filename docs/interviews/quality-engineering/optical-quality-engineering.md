# 光模块质量工程面试: 开发专家与测试专家视角

配套 [系统学习文档](../../learning/quality-engineering/optical-quality-engineering.md). 本文围绕光模块维护、日志解析、追溯、生产看板与 Agent/RAG 评测, 提供可独立阅读的参考答案. 所有案例均为教学场景, 不代表个人项目经历, 不应背成“我在生产已经实现过”.

核查日期2026-10-20. 理论来源与学习文档相同, 实验为 Python 3.12.14 标准库实现, 已执行范围见 [验证报告](/examples/optical-quality-engineering/results/report.json). 没有运行真实硬件、企业平台或真实模型.

## 开发专家视角

### 1. bin 能成功转成 CSV, 为什么仍然不能说明解析器正确?

**考察点**: 数据契约、独立判据、静默错误与可追溯性.

**回答结构**: 结论→字段含义→独立样本→下游约束→验证边界.

**参考答案**: 转换成功只说明程序完成了某条执行路径, 不能证明每个字节解释正确. 我会先确认协议版本、字节序、符号位、缩放、单位、有效位、记录长度和校验范围, 再用独立确认的字节样本逐字段断言. 例如温度原始值是有符号-100, 约定除以100, 应为-1°C; 如果被当无符号数, CSV 仍能正常生成, 但业务意义完全错了.

宽表还要检查通道列映射、时间与模块主键、缺失值和重复记录. 原始文件、解析器版本与分析结果需要能相互追踪, 这样出现错误才能定位受影响数据并重算. 往返编码测试有价值, 但若编码器和解码器共享同一错误, 往返仍可能通过, 所以不能替代独立黄金样本.

**递进追问与回答要点**: 新固件增加一个字段, 能否忽略后继续解析? 先看协议是否有长度或版本机制以及明确兼容约定. 无约定就不能猜测后续偏移. 生产者与消费者需分别验证 schema 兼容, 未知版本应明确报出, 不能静默按旧版读.

**易错回答与判断依据**: “多跑几个文件就行”缺少判据; “CRC对就是解析对”混淆完整性与语义; “与旧版一样就正确”忽略旧版可能有缺陷. 合格答案能给出独立样本和下游不变量.

### 2. 创建分析任务超时后重试, 怎样避免重复任务?

**考察点**: 幂等、事务、响应与状态区别、故障注入.

**回答结构**: 定义同一业务请求→稳定幂等键→原子约束→冲突处理→验证故障窗口.

**参考答案**: 客户端超时不表示服务端没有写成功. 我会让同一业务请求的重试携带同一幂等键, 服务端以空间和幂等键建立唯一约束, 并保存请求关键内容的摘要. 同键同内容返回之前的结果, 同键不同内容明确冲突, 不能覆盖旧请求. 检查与写入必须处于原子事务或等效机制中, 否则两个并发请求都可能先查到“不存在”.

测试要观察实际业务表、事件和审计记录. 本实验使用 SQLite 事务及唯一约束, 12次并发同键请求最终只产生一条草稿. 但分布式环境还需要验证写成功后响应丢失、消息重复、客户端重启和幂等记录保留时间等条件, 本地测试不能证明这些场景.

**递进追问与回答要点**: 如果请求触发设备采集这个外部动作怎么办? 数据库事务不自动覆盖外部设备. 需要明确外部操作的唯一任务标识、状态查询与补偿协议, 测试“受理、执行、完成”各阶段的重复与超时. 不能依靠无限重试解决.

**易错回答与判断依据**: “前端按钮禁用”挡不住重试和其他客户端; “加一把本地锁”不涵盖多实例. 合格答案能说明原子性边界以及服务端已成功但客户端未知的状态.

### 3. 生产看板首测良率从80%涨到90%, 如何判断是真改善?

**考察点**: 指标定义、分母、样本构成、迟到数据与可复算.

**回答结构**: 固定口径→重算明细→分层比较→确认数据变更→业务解释.

**参考答案**: 首先确认首测定义和统计窗口. 如果先过滤今天的记录再选每个模块第一条, 昨日失败、今日复测通过可能被错算为今天首测通过. 应在完整必要历史中识别首次测试, 再决定是否纳入窗口, 同时按事件ID去重并处理冲正.

其次比较同产品族、工位和批次的表现. 如果高良率产品占比提高, 总体上升并不表示每种产品都改善. 检查数据迟到、缺失、规则或维表版本和分母变化, 并让图表能下钻到明细复算. 实验中一个模块首次失败后复测通过, 另一个首次通过, 首测良率仍为1/2, 不能用最终通过数变成2/2.

**递进追问与回答要点**: 如果完整历史太大不能每次全扫? 可以复用已有仓库维护的可信首次事件状态或增量模型, 但需测试迟到更早事件、修订、补录和全量重算的一致性. 性能方案不能改变业务定义.

**易错回答与判断依据**: “接口返回数字与页面一致就通过”只能证明展示一致; “只看总量和总通过率”不能排除结构变化. 合格答案说明分母来源、时间语义和回算路径.

### 4. 如何把 Agent 评测接入已有测试平台, 而不重新造平台?

**考察点**: 职责划分、运行隔离、证据契约与发布门禁.

**回答结构**: 复用底座→补业务资产→隔离执行→输出可消费结果→接入门禁.

**参考答案**: 复用已有任务调度、环境、权限、制品、报告和 CI/CD. 我需要补充的是任务样本、环境快照、程序评分、模型评分量表及领域复核流程. 被测 Agent 只拿任务输入和允许工具, 黄金答案和评分提示留在评分侧. 工具写入指向沙箱, 每个案例有独立状态并能清理.

执行后保存回答、工具参数与返回、时间、版本及独立业务终态. 用 JUnit 表达确定性断言, 用 JSON 补充语义状态、切片指标和错误类型, 最后用门禁退出码连接流水线. 模型评分服务出错应显示评测未完成, 不能因为JUnit全绿就放行. 这是一组可接入的业务任务, 不是把调度、数据集管理和看板再实现一遍.

**递进追问与回答要点**: 平台只能收 JUnit 怎么办? 将门禁决策作为独立必过测试/审批项映射到现有能力, 语义未完成不能伪装通过. 完整分项JSON作为附件保留, 对于必须新增的报告能力与平台方确认契约.

**易错回答与判断依据**: “先搭一个评测网站再说”没有回应现有平台背景; “平台已经能跑用例, 所以评测完成”遗漏数据和判据. 合格答案清楚区分平台能力与业务质量责任.

### 5. RAG 召回率高, 为什么回答仍然可能错?

**考察点**: 检索与生成边界、证据适用性和指标定义.

**回答结构**: 召回只回答部分问题→验证适用性→检查实际上下文→评价主张与证据.

**参考答案**: 召回率高只表示标为相关的证据被找到了, 不表示证据排序合适、已进入模型上下文、版本适用或者模型正确使用了它. 对F2模块找到了F1阈值文档, 即使相似度很高也不能据此判断. 还可能在上下文截断时丢失关键片段, 或模型忽略限定条件.

我会分别记录候选、过滤、重排、实际上下文和引用. 先检查知识库是否有正确版本, 再看检索是否取回和保留, 最后看每个回答主张能否由证据支持. 忠实地复述过期文档也可能业务错误, 所以正确性、证据支持度和引用适用性要分开评分.

**递进追问与回答要点**: 没有相关文档时召回率怎么计算? 不能未经说明让空分母得到1. 本实验返回不适用, 单独评价正确拒答及错误检索行为. 平台必须明确口径和分母.

**易错回答与判断依据**: “把top-k调大即可”忽略噪声、成本与截断; “引用存在就可信”忽略是否支持主张. 合格答案能沿实际数据流定位.

### 6. 怎样设计一个可靠的模型评分器?

**考察点**: 量表、输入隔离、结构校验、校准及不确定性.

**回答结构**: 限定任务→定义锚点→独立人工标签→盲评校准→持续审计.

**参考答案**: 先限定评分对象, 例如回答是否受到给定证据支持, 不让模型去猜数据库是否落库. 量表需说明0、1、2分分别是什么, 什么情况必须unknown, 并提供领域反例. 对光模块分析, 低接收光功率本身不支持“激光器已经损坏”这样的确定根因.

在独立人工标注的校准集上比较一致率、错放率和分层误差, 修订后冻结模型、提示词和量表, 再做锁定集盲评. 成对比较时交换A/B顺序检查位置偏差. 程序验证返回schema、分值和证据ID, 无法解析则记录judge_error. 温度0不是绝对确定性证明, JSON合法也不代表语义正确.

**递进追问与回答要点**: 人工与模型一致率95%能上线吗? 还要看样本构成、人工标注质量和错放影响. 如果95%都是简单通过题, 一致率没有覆盖关键风险. 需要领域争议仲裁与高风险样本审计.

**易错回答与判断依据**: “更大的模型肯定可靠”没有校准证据; “让模型解释一下就可信”把自述当验证. 合格答案把评分器也当被测对象.

## 测试专家视角

### 7. 如何为光模块巡检设计系统测试, 避免只有正常用例?

**考察点**: 风险分解、测试方法、覆盖与判据.

**回答结构**: 确认规则→建立决策表→边界与状态→集成/专项→追溯验收.

**参考答案**: 我先确认对象身份、时间窗、规则版本、阈值精度、缺测和告警恢复条件. 将权限、对象匹配、数据有效和规则适用写成决策表. 低值边界用真实量化步长测试上下邻点, 不随意用无法被设备表达的浮点数.

再测迟滞与去抖状态、断连和恢复、重复采集、多个通道以及固件组合. 接口层核对任务状态和数据完整性, 端到端只保留关键链路, 性能按真实采集到达模式验证. 无采样必须与正常分开, 告警可能指向链路问题而非模块硬件根因. 每个高风险场景都要有可独立核验的原始数据和规则版本.

**递进追问与回答要点**: 时间只够两天怎么办? 按影响和变更选必测项, 优先错误对象、权限、缺测误判、核心阈值和恢复. 未覆盖的兼容组合明确记录为残余风险, 由既有流程决定是否接受, 不能把范围缩减隐藏在通过率里.

**易错回答与判断依据**: “功能、性能、安全各跑一点”缺少业务触发; “自动化越多越好”缺少判据与优先级. 合格答案能把某条风险落到具体输入和预期.

### 8. 如何证明测试真的能抓到错误?

**考察点**: 判据有效性、变异测试、独立样本与盲区.

**回答结构**: 不能只看覆盖→注入具体缺陷→检查预期失败→分析存活原因.

**参考答案**: 高覆盖只说明执行过代码, 不说明断言会识别错误. 我会选择与真实风险对应的小变异, 如把阈值的`<`改为`<=`, 把缩放倍数改错, 或删除权限检查, 验证哪些用例会失败. 本实验的边界缺陷被F1和F2边界题抓到, 能说明这两条断言有效.

但将自然语言结论改成“确认激光器损坏”时, 确定性检查仍可能通过, 因为它只看结构、对象和引用ID. 这揭示了语义判据缺失, 需要经校准的模型或领域人工复核, 不能再加一个检查status字段来假装修好了. 变异存活也可能是等价变异, 要看是否真的改变业务行为.

**递进追问与回答要点**: 代码覆盖100%是否还需要变异? 需要按风险评估, 因为覆盖与断言有效性不同. 但不要求对所有代码穷举变异, 优先关键规则和曾经逃逸的缺陷.

**易错回答与判断依据**: “跑完没有报错就是测试有效”是循环证明. 合格答案能指出被设计的错误、失败的用例和没有覆盖的行为.

### 9. 怎样建设 golden set, 防止评测越调越好却不泛化?

**考察点**: 样本治理、标注质量、泄漏与版本管理.

**回答结构**: 来源→独立标注→分组划分→隔离与冻结→受控更新.

**参考答案**: 黄金样本应包含任务、可用证据、适用版本、可接受结果和不能做的事. 先由领域人员基于证据标注, 对分歧仲裁, 证据不足就保留不确定结论. 同一模块、批次或事故的近重复要按组划分, 避免开发集和测试集只是同一事件的不同问法.

开发集用于调试, 校准集用于评分器调整, 锁定测试集用于最终比较. 被测Agent不能看到隐藏标签, 评分提示也不能从测试答案持续泄漏回来. 生产失败经复核后先进入挑战集, 在新版本数据集中纳入, 并保留稳定锚点和修订原因. 黄金答案会过期, 不能只因为名字叫golden就永久信任.

**递进追问与回答要点**: 没有真实数据时怎么办? 用合成场景验证协议和补边界, 明确它不能估计真实效果. 计划接入授权脱敏样本并重新校准, 不把17条教学样本宣称为生产benchmark.

**易错回答与判断依据**: “模型生成一万条就够”忽略代表性和标注偏差; “随机按行切分”可能事故泄漏. 合格答案明确样本独立单位与用途.

### 10. Agent 最终回复正确, 但工具调用错了, 算通过吗?

**考察点**: 过程、结果、安全与任务契约.

**回答结构**: 看任务定义→核对关键约束→独立终态→容忍等价路径.

**参考答案**: 不能只凭最后一句话通过. 如果用户要求分析模块A, Agent读取了模块B的数据后碰巧得出同一句结论, 对象约束已经失败. 如果越权关闭问题单后再改回, 最终状态看似正确也不能抹去中间副作用. 应验证必要工具参数、权限、证据身份和独立业务终态.

另一方面, 不应把合法的另一条路径都判错. 两个独立查询先后顺序不同可能不影响结果, 只要满足数据依赖、预算和禁止动作约束. 精确轨迹匹配仅适用于确有固定流程要求的任务, 否则应以约束和结果评分.

**递进追问与回答要点**: 平台没有工具轨迹怎么办? 当前只能评可见的回答与终态, 报告该限制. 要完成过程与安全判定, 需补充关联ID、工具名、参数和返回等观测契约; 不能从回答猜轨迹.

**易错回答与判断依据**: “结果正确就都通过”和“必须与黄金轨迹逐字一致”都过度简化. 合格答案能区分禁止行为与等价实现.

### 11. 候选成功率92%, 基线90%, 可以发布吗?

**考察点**: 配对比较、样本量、切片、统计与风险.

**回答结构**: 核实可比性→查看差异案例→分层与不确定性→结合硬门禁.

**参考答案**: 先确认是否同一批任务、环境、知识、预算和评分器. 不同批次的92%与90%不能直接比较. 对配对样本, 看哪些任务由错变对、由对变错, 再看高风险切片和延迟成本. 同一事故的多条问法、多次trial要处理相关性, 不能当作独立样本把区间缩得很窄.

总体提升不能抵消一条越权写入或无依据重大根因. 需要预先批准的门禁和最低证据量. 若区间太宽、关键切片缺样本或judge未完成, 结论应是继续收集证据或待复核. 不应为了赶发布临时删除失败项.

**递进追问与回答要点**: 10条关键用例全部通过是否说明可靠? 只能说明这些用例通过. 即便按独立同分布二项样本解释, 10/10的Wilson95%区间下界约0.722; 若样本是刻意设计而非代表性抽样, 更不能拿该区间推总体.

**易错回答与判断依据**: “涨了2%就发”没有样本和风险依据; “p值小就肯定有业务价值”忽略效果大小和损失. 合格答案区分统计证据与业务决策.

### 12. 灰度后发现解析值错误, 回滚代码够不够?

**考察点**: 生产质量闭环、数据副作用、回滚与重算.

**回答结构**: 停止扩大影响→确定影响范围→隔离产物→恢复/重算→回归与复盘.

**参考答案**: 不够. 错误解析结果可能已经进入宽表、看板和分析结论, 回滚代码不会自动修复这些数据. 首先停止新版本继续处理或扩大灰度, 根据文件哈希、解析器版本、时间和分区找到受影响产物. 隔离错误结果, 按批准流程重算并核对下游, 保留修订审计链.

同时比较控制组, 防止把采集源变化误认为发布问题. 恢复后抽样检查数值和业务结论, 复核受影响的问题单是否产生错误操作. 将经确认的最小复现加入回归, 更新缺失的门禁与监控. 这些动作需要已有发布和数据治理流程配合, 不能让Agent自行删除或覆盖生产数据.

**递进追问与回答要点**: 灰度比例只有1%, 为什么仍可能风险大? 如果这1%集中于关键模块族、特殊批次或高价值链路, 影响不由比例独自决定. 应选择可比且风险可控的灰度单元, 同时设时间和样本要求.

**易错回答与判断依据**: “回滚后监控恢复就结束”漏掉历史数据和业务副作用. 合格答案说明影响定位依据和可验证恢复结果.

## 面试自测方式

任选一题, 用2分钟给结论、机制、业务例子和边界, 再接受一个追问. 如果只能说框架或指标名, 不能给出具体输入、观察证据和失败去向, 说明尚需回到实验. 不需要背诵全部代码, 但应能解释为何这样断言以及什么仍未验证.

![门禁与复核的机制图](/images/optical-quality-engineering/06-release.svg)

沿图走一遍“17项程序检查全过但语义证据缺失”的情况, 应到待复核, 而不是灰度. 再走“阈值变异被抓住”的情况, 应到阻断和修复后重评. 能解释这两条路径, 才说明理解了测试通过与发布通过的区别.
