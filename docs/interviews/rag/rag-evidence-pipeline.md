## 开发专家视角

### 知识库有记录, 为什么回答还是可能漏掉?

**关注点**: 离线与在线链路、可追溯性、上下文边界.

**表达顺序**: 区分链路 → 追踪目标资料 → 定位首次丢失 → 复测.

**我的回答**: 有记录只是第一层条件. 资料还要经过解析、切分和索引, 在线提问再检索候选、组织上下文并生成回答. D3 示例案例中 C102 在源库, 可能尚未同步入索引; 也可能进了索引但被错误日期过滤排除; 还可能检索命中却被上下文预算截掉. 我会沿稳定的资料 ID、片段 ID 和版本逐层对照, 确认 C102 首次消失的位置. 若上下文明确包含它但回答漏掉, 才把关注点移到生成和任务理解. 这是一套定位方法, 不代表已经在公司部署过该链路.

**进一步讨论**: 源记录更新了, 模型仍复述旧内容, 是幻觉吗?

未必. 如果模型收到的索引片段仍是 v1, 它可能忠实于旧证据, 却不符合新业务事实. 应比较源版本、索引版本、同步完成和实际可见时间. 事实新鲜度与基于给定证据的忠实性是不同检查.

**我需要避免的判断**: 只保存最终回答, 或看到漏答就改提示词, 都缺少定位依据. 索引任务成功也不等于每条目标资料已正确可检索.

## 测试专家视角

### 前五条片段中有两条问题, 可以回答全库只有两条吗?

**关注点**: 完整枚举、精确统计、相关检索与授权.

**表达顺序**: 先看问题类型 → 确认数据口径 → 验证完整性 → 限定结论.

**我的回答**: 不能仅凭 Top-K 结果得出全库总数. 前五条只是相关候选, 可能漏掉后面的记录, 同一问题还可能占多个片段. 对“有哪些”或“多少条”, 需要明确是否要求完整集合, 使用可证明完整的过滤、分页或聚合结果. R1 六份冻结资料可手工核对过滤后只有 C101/C102, 因而这个小例子能说两条. 真实系统若只能给相关片段, 应说明是本次检索找到的内容, 不冒充全量.

**进一步讨论**: 精确业务查询一定要走 RAG 吗?

不一定. 生产问题若有日期、局点、客户等结构化字段, 可由业务查询接口返回完整结果, 再让模型解释. Agent 可以按能力路由到工具. 测试仍应核对账号权限、字段口径和返回集合, 不因使用了自然语言就放松业务断言.

**我需要避免的判断**: 把片段数当问题数、把文档更新时间当发生时间、把用户提供客户当授权依据, 都会改变结论. 必须有独立口径和可信权限证据.
