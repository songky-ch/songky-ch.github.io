# 五种 RAG 面试专题: 开发与测试视角

配套学习: [五种 RAG 的同异对比与实现流程](../../learning/rag/rag-architectures.md).

面试时, 先把“资料怎样找到, 由谁决定下一步, 最后依据在哪里”讲清楚, 再说技术名称. 回答前或回答过程中先查外部资料, 叫检索增强生成 (RAG, Retrieval-Augmented Generation). 根据任务选择工具并检查结果的执行主体, 叫智能体 (Agent).

这篇专题比较固定流程, 混合检索, 智能体控制的问答 (Agentic RAG), 智能体承担检索职责 (Agent-as-retriever), 以及利用图关系辅助找证据的 GraphRAG. 它们分别关注流程, 找资料的方法, 职责和知识组织方式, 不需要强行选出一个“下一代”.

- 分类: RAG. 内容类型: 面试专题. 核查日期: 2026-10-18.
- 表达与图解更新: 2026-10-19 同步新版规范, 保留原来源日期与运行记录. 本次不声称重新核查全部来源或运行真实模型.
- 来源版本: 2026-10-18 的官方在线文档; LlamaIndex 可组合文档 Agent 参考明确为 v0.10.17 历史示例. 其接口不作为当前实现建议.
- 验证状态: 配套标准库练习已运行, 验证排名, 证据契约, 脚本化动作预算和手工图溯源. 未运行真实 LLM (Large Language Model, 大语言模型), Embedding (文本向量表示) 或完整 GraphRAG 服务.
- 下列为技术参考答案与合成场景, 不代表学习者的项目经历或真实面试出现频率.

统一场景: D1 记载 2026-10-01 支付服务 E1042 原因为连接池耗尽; D2 是通用支付排障手册; D3 记载结算依赖支付; D4 记载对账依赖结算; D5 记载另一事故为通知模板配置错误.

## 开发专家视角

### 1. 五种 RAG 是五种互斥架构吗? 怎样说明它们的边界?

**考察点**: 能否按设计层级区分术语, 避免把框架名称当成算法或升级顺序.

**回答结构**: 共同目标 → 四个设计问题 → 每个名称的位置 → 一个可组合案例.

**参考答案**: 它们能组合, 因为回答的不是同一个问题. 传统两步流程规定先找资料再回答; 混合检索说的是把关键词与语义两路结果合并; 智能体控制的问答, 则让模型看完当前结果后再决定下一步. 如果把查资料这项工作交给一个智能体, 让它只交回原文和出处, 就是本文约定的检索职责划分. 图增强方案另外考虑怎样把对象与关系组织起来.

例如, 上层智能体可以先调用混合检索找错误码, 再调用图检索找下游依赖; 缺原文时, 请检索智能体补齐. 反过来, 固定生成流程也能调用检索智能体. 我会先说明每个组件实际做什么, 再给它贴名称.

术语需先约定: LangChain 文档的 Hybrid RAG 是流程混合, 不专指关键词加向量. Agent-as-retriever 没有统一框架标准, 我会说明所指的是主动搜索阅读, 还是可组合检索组件, 以及是否负责最终回答. [依据: LangChain Retrieval](https://docs.langchain.com/oss/python/deepagents/retrieval#rag-architectures).

**递进追问与回答要点**: “检索 Agent 不用向量库, 还算 RAG 吗?” 如果把取得的外部材料用于生成答案, 仍符合广义 RAG. 无向量库只说明召回实现, 不代表没有词法索引, 搜索服务或数据准备.

**易错回答与判断依据**: “GraphRAG 是 Agentic RAG 的下一代”缺少层级依据. “用了 LangGraph 就是 Agentic”也不成立, 应观察下一步是否由模型基于状态选择, 还是只是顺序执行固定节点.

![五种 RAG 对应的控制, 召回, 职责与知识表示分工](/images/rag-architectures/architecture-map.svg)

答第 1 题时, 按图中四个问题逐行解释即可. 这是一张职责图, 不要把四行说成系统必定依次经过的四步.

### 2. 如何从文档开始实现传统 RAG? 答错时先查哪里?

**考察点**: 数据链路, 来源设计, 检索与生成归因.

**回答结构**: 离线表示 → 在线召回 → 上下文 → 生成 → 分层定位.

**参考答案**: 我会先把文档解析成能独立理解的小段, 给每段保留标识和原文位置, 再编码并建向量索引. 问题到来后, 先确定可访问的资料范围, 用兼容的查询编码找前 k 个候选 (Top-k), 取回原文, 去重后装入模型能容纳的上下文, 最后依据这些原文回答并标注出处. 候选还可以重新排序, 叫重排 (Reranking). 只要这些步骤仍由代码预先规定, 就还是固定流程, 不因多调用了一次模型而改变控制方式.

对 E1042, D1 是当次根因证据, D2 只是一般排查. 若 D1 未进入候选, 排查解析, 切分, 索引, 编码, 查询和过滤; 若在候选但没进上下文, 查排序和裁剪; 若已经进入上下文却答错, 查生成及断言与引用的支持关系. 不能一开始只换模型或改提示词. 原始 RAG 论文的模型训练公式与工程两步问答也需要分开. [依据: Anthropic RAG primer](https://www.anthropic.com/engineering/contextual-retrieval#a-primer-on-rag-scaling-to-larger-knowledge-bases), [RAG 原论文](https://arxiv.org/abs/2005.11401).

**递进追问与回答要点**: “增加 k 就能解决遗漏吗?” 可能提高覆盖, 也增加噪声和上下文成本. 若事实在解析时已丢失, 权限过滤错了或片段断掉必要条件, 增加 k 没有针对根因.

**易错回答与判断依据**: “相似度高所以答案正确”混淆检索相关性与事实支持. 合格回答应能展示 D1 在候选, 上下文和引用中的具体位置.

### 3. BM25 与向量结果怎样融合? 为什么融合后仍可能答错?

**考察点**: 排名信号, 分数量纲, 召回与重排边界.

**回答结构**: 两路互补 → 同一语料标识 → 融合公式 → 反例 → 验收.

**参考答案**: 两路先分别找资料, 再合成一份排名. 关键词一路常用 BM25 (Best Matching 25, 词法相关性排序函数), 适合利用错误码等词项; 向量一路按语义匹配. 两路应使用同一版本, 同一权限范围和同一套片段标识, 才能把同一片段识别出来.

合并可以用倒数排名融合 (RRF, Reciprocal Rank Fusion): 不直接比较两路原始分数, 而是让每个名次贡献一点分数. 等权时把各路的 `1 / (c + rank)` 加起来, 排名从 1 起. 这样解决了原始分值不好直接相加的问题, 但它并不知道哪段原文足以证明当次根因.

例如词法结果 `[D1, D2]`, 向量结果 `[D2, D3]`, 两路融合会让都出现的 D2 排第一. 这对融合规则是正确的, 但 D2 不能证明当次 E1042 的根因. 需要检查当次证据覆盖, 必要时在候选中做更细的相关性或证据判断. 重排不能恢复两路都没找回的 D1. 不应未经归一化直接把 BM25 分数与余弦值平均. [依据: Elastic RRF](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion), [Qdrant 多阶段查询](https://qdrant.tech/documentation/search/hybrid-queries/).

**递进追问与回答要点**: “RRF 常数设 60 就最优吗?” 60 是 Elastic 文档默认值, 不是通用最优. 候选窗口, 权重支持和具体实现也有差别. 参数应依据固定验证集和业务目标评估, 不能把一种引擎默认值移植为理论结论.

**易错回答与判断依据**: “混合检索保证更准”忽略噪声, 重复候选和过滤差异. 判断依据是同语料同生成条件下的证据覆盖与答案支持, 不是流程里有两个搜索器.

![双路排名融合后 D2 排第一, 上下文只留一条时仍缺当次根因证据](/images/rag-architectures/hybrid-fusion.svg)

第 3 题先从两路独立结果走到融合分数, 再沿图底部“只留第一条”的路径说明反例. 算对了融合分数, 仍不等于回答有依据.

### 4. 如何设计 Agentic RAG, 避免无限检索和提前结束?

**考察点**: 状态, 工具契约, 预算与可观察执行记录.

**回答结构**: 状态定义 → 行动循环 → 约束执行 → 完成与不足两种出口.

**参考答案**: 我会让系统记住原问题, 还缺哪些资料, 已找到的证据, 做过的动作和剩余预算. 模型提出下一步, 应用先检查参数, 权限和调用额度, 再真的执行工具. 查到 D3 后, 系统知道结算依赖支付, 但还不知道结算的下游, 所以把结算作为线索再查 D4.

可以结束时, 要分别看“证据够了”和“已经不能继续”. 前者可以给有出处的回答; 后者只能报告已知范围和缺口. 预算耗尽, 工具失败, 重复查不到新资料, 都不能被写成“业务上没有这条关系”. 调用上限由代码执行, 不能只在提示里说“最多四次”. 对打招呼这类任务, 应用允许时可以直接回答, 不必先检索.

轨迹记录工具名, 参数, 结果, 来源和状态, 无需保存模型内部推理. 既要防止循环, 也要防止拿到一条关系就宣告所有下游已找齐. 官方教程展示了选择检索, 相关性判断, 改写再检索的一种实现, 不是要求每个系统都采用同一节点设计. [依据: LangGraph custom RAG agent](https://docs.langchain.com/oss/python/langgraph/agentic-rag).

**递进追问与回答要点**: “没有新证据是否等于没有其他下游?” 不等于. 只能说明本轮没有发现. 应报告搜索范围, 数据覆盖或预算限制; 不能把一个策略的失败推成业务事实.

**易错回答与判断依据**: “让模型自己决定停止就够了”缺少可执行约束. 正确实现应能在工具前拦截超预算调用, 并在不足出口明确记录缺失证据.

![智能体的免检索直答, 继续查询, 证据完成与预算或工具失败出口](/images/rag-architectures/agent-loop.svg)

讲第 4 题时, 先走“查 D3, 回来判断, 再查 D4”的成功路径, 再走预算不足的出口. 这能说明停止检索和查证完成是两回事.

### 5. Agent-as-retriever 应返回答案还是证据? 与上层怎样交接?

**考察点**: 职责边界, 接口设计, 原文保真和来源完整性.

**回答结构**: 约定职责 → 输入输出 → 搜索阅读过程 → 上层验证.

**参考答案**: 按本文的约定, 它交回证据, 最终答案由上层组织. 上层要说清楚查什么, 在哪里查, 最多花多少调用. 检索智能体再看目录, 搜错误码, 打开命中的原文, 必要时追踪引用. 返回时要带上原文, 文档标识, 版本, 位置和还没确认的部分.

比如搜到了 D1 的标题, 还不能直接交付当次根因. 应打开对应段落, 确认日期与服务, 再把这段原文交回. 若另写了一段总结, 就标成总结, 不伪装成引用原句. 上层核对出处和问题覆盖后再作答.

这种按需寻找和读取的实现可以不建向量库, 也可以内部调用向量, 词法或图检索. 它适合已有导航结构和引用链的资料, 不足以证明大规模语义检索无需索引. 上层固定生成并不妨碍内部检索循环具有 agentic 行为. [依据: Anthropic Context retrieval and agentic search](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents#context-retrieval-and-agentic-search). 证据包字段是本文教学设计, 不是官方通用协议.

**递进追问与回答要点**: “子 Agent 只给出一段总结, 能直接引用吗?” 可作为中间总结, 但需区分其生成内容与底层材料. 关键结论应回取原文, 否则上层无法验证总结是否遗漏条件或混入推断.

**易错回答与判断依据**: “多 Agent 比单 Agent 更准确”没有机制证据. 这里考察的是检索出口与信息保真, 并不要求多个 Agent.

### 6. GraphRAG 的 Local 与 Global 如何实现? 什么情况下不用图遍历代替统计?

**考察点**: 图知识表示, 局部关系与全局综合, 来源及更新.

**回答结构**: 广义与具体实现 → 离线建图 → 两种查询 → 证据与统计边界.

**参考答案**: 先把资料中的对象及关系整理出来, 让查询可以沿关系找证据, 这就是广义的图增强问答, 不一定使用特定图数据库或社区报告. Microsoft 的具体路线会先从文本单元抽取并整理实体关系, 再把连接紧密的对象分组, 称为图社区 (Community), 并为这些分组生成社区报告 (Community Report). 每个关系及报告中的依据还要能追踪回原文. 实际落地时, 别名, 方向, 业务时间和失效更新都需要单独核对.

局部搜索 (Local Search) 从具体对象进入, 把相关关系, 原文和其他资料放到一起. Q2 可以从支付反向查谁依赖它, 找到结算与对账后再回取 D3 和 D4. 这条遍历是案例设计, 不代表官方查询总是固定两跳. 全局搜索 (Global Search) 则把选定层级的社区报告分批提炼要点, 再合成主题, 这种做法叫 Map-reduce (分批处理再汇总), 适合 Q3. 如果要求事故精确次数或排名, 则需要定义记录与去重单位后对完整数据做确定性统计. 生成摘要的强调程度不能当数量. [依据: GraphRAG Dataflow](https://microsoft.github.io/graphrag/index/default_dataflow/), [Local](https://microsoft.github.io/graphrag/query/local_search/), [Global](https://microsoft.github.io/graphrag/query/global_search/).

**递进追问与回答要点**: “D3 更新后只更新文本向量够吗?” 不够. 应检查关系, 来源映射和派生报告, 图结构变动可能影响社区. 已生成的摘要仍可能保留旧结论. 精确更新范围取决于实际依赖, 不能承诺永远只有一个社区受影响.

**易错回答与判断依据**: “存在依赖就证明发生事故传播”混淆潜在影响与事实因果. 应另有当次事故状态证据. “所有 GraphRAG 都做社区总结”把具体实现当通用定义.

![离线建图后, 局部依赖查询与全局社区报告综合分别执行, 依据不足时均说明缺口](/images/rag-architectures/graph-flow.svg)

第 6 题沿图左侧讲具体对象, 沿右侧讲整批资料. 两条在线路径从同一入口分开, 不能说成先局部再全局. 左边的依赖不证明事故传播, 右边的摘要也不能代替精确计数.

## 测试专家视角

### 7. 怎样公平比较五种方案, 又避免只测最终回答?

**考察点**: 可比实验, 数据分层, 中间证据与过程评测.

**回答结构**: 固定条件 → 按问题类型分组 → 分层指标 → 资源代价与结论边界.

**参考答案**: 先让各方案面对同一批资料, 同一组问题和同一访问范围, 并标好每题真正需要哪些原文. 能固定的条件尽量固定, 比如生成模型和上下文预算; 各自多花的建库, 工具和模型开销单独记. 问题也要分开看: 局部事实, 精确错误码, 换一种说法的语义问题, 多跳依赖, 全局主题, 无答案和资料版本变化. 只测 Q1, 无法判断方案是否擅长全局总结.

然后把中间结果摊开看: 原文有没有解析错, 候选里有没有必需资料, 装入上下文时有没有丢掉, 最后每个结论和引用是否都有依据. Q2 要单独检查 D3 和 D4 是否同时在场. 智能体还要看工具参数和预算, 图方案要看实体, 关系方向与出处, 全局总结要看漏了哪些主题. Recall@k (前 k 召回率) 以标注相关项为分母, 不替代完整推理链验收. 记录模型用量, 工具次数, 延迟分布和建库更新成本, 并对随机执行重复测量. 这些是本文实验设计, 不是某框架默认分数.

**递进追问与回答要点**: “最终答对但引用 D2, 怎么判?” 若任务要求可验证的当次根因, 答案文本可能碰巧正确, 引用支持仍失败. 将结论正确性和证据支持分开计分, 避免掩盖问题.

**易错回答与判断依据**: “一个综合分最高就能上线”缺少风险与分组证据. 合格结论应说明哪些任务改善, 哪些未完成, 以及资源代价和实际样本范围.

### 8. 检索指标提升, 但答案没提升, 怎样定位?

**考察点**: 对照实验, 覆盖与排序分离, 上下文与引用检查.

**回答结构**: 核对指标口径 → 比较中间结果 → 控制变量重放 → 锁定层级.

**参考答案**: 先看提升的是一般相关片段数量, 还是当次问题必需证据. 固定排名练习中, 融合补入 D1, 但让 D2 排在前面; 如果最终只留一条上下文, 必需证据依然丢失. 对比融合前后的候选, 排序, 去重和实际上下文, 确认标识和语料版本一致. 再固定同一份正确证据重放生成, 看是否仍答错. 若正确上下文能答对, 继续定位候选选择与裁剪; 若仍答错, 查生成是否使用证据及引用断言是否匹配.

重排阶段的正确性不应只用结果列表变化衡量, 需要检查正确证据被保留的情况. 也不要把检索空结果当成可放心回答“没有故障”.

**递进追问与回答要点**: “换更大模型解决了, 能判断原因为模型能力吗?” 只能说明在这组输入下行为不同. 原检索, 上下文, 提示或随机性仍可能有影响, 应固定输入重放并比较中间证据后再归因.

**易错回答与判断依据**: “召回高所以只能是生成模型的问题”跳过了上下文预算和必需证据覆盖. 必须拿出实际送入模型的证据, 不能只看搜索返回日志.

### 9. 如何测试 Agent 的预算, 证据不足和重复检索?

**考察点**: 强约束验证, 过程风险和失败出口.

**回答结构**: 构造缺口 → 控制工具 → 检查动作与状态 → 检查最终表述.

**参考答案**: 我会先把工具结果固定下来, 让第一次查询只给 D3, 第二次才给 D4. 把预算设为 1, 看它是否真的只调用一次, 并明确说第二跳还没查完; 预算足够时, 再看两份证据是否都找齐. 接着让工具一直返回同一段资料, 检查系统会不会停止重复, 有没有把已知范围夸大成全部结果. 超时, 参数错误和空结果要分别看, 不能一律解释成“业务上没有这条关系”.

需要的观察项是实际工具调用, 参数, 返回文档标识, 预算变化, 证据集合和结束状态. 真实模型测试应重复运行; 确定性脚本只能验证应用约束和数据契约, 无法证明模型会正确规划. 本文练习用脚本验证“一次预算不能假装完成两跳”, 未评测真实 Agent.

**递进追问与回答要点**: “工具返回文档包含要求忽略上层规则的文字, 测什么?” 把这类文字当检索数据, 检查其不能改变允许工具, 访问范围和预算, 最终答案也不能把其中指令当成已授权动作. 权限和预算执行仍应在应用侧可观察.

**易错回答与判断依据**: “有最大轮数测试就覆盖循环”忽略单轮内可能发生的多次调用, 工具返回膨胀和超时. 应检查真正消耗资源的执行位置.

### 10. 如何验证 GraphRAG 的抽取, 溯源, 更新和访问隔离?

**考察点**: 图数据质量, 派生内容依赖和跨层泄露.

**回答结构**: 金标小图 → 边和实体检查 → 查询验收 → 更新与隔离.

**参考答案**: 我会先选几份意思明确的原文, 人工标出对象, 别名, 关系类型, 方向和出处. 再故意加入同名但不同的对象, 一个对象的不同称呼, 否定描述, 生效时间变化和依赖环. 先核对图里的关系能否回到原文, 再查路径. 比如移除 D4 后, 输出就不能继续声称已确认对账这条关系. 全局总结还要另查社区报告用了哪些资料, 覆盖了哪些主题; 局部路径查对了, 不能代替全局总结验收.

更新 D3 时, 同时检查受影响的图关系, 原文映射, 向量和派生报告, 区分业务生效时间与资料更新时间. 访问隔离不只验证原文块过滤: 社区报告可能已聚合受限材料, 需验证用户不会通过报告或中间摘要看到越权信息. 这是落地测试要求, 不声称官方默认查询器已实现完整权限治理.

**递进追问与回答要点**: “回答找到了真实的两跳路径, 还能错在哪里?” 可能使用旧关系, 反向误读, 同名实体合并或把潜在依赖写成实际事故. 应检查时间, 方向, 实体身份和结论措辞各自对应的证据.

**易错回答与判断依据**: “图数据库能查出路径就算正确”只证明存储和查询可运行. 路径的业务含义, 抽取真实性和用户是否有权看到还需原文证据.
