# 怎样讲清接口关联、数据隔离与失败清理?

<p class="article-kicker">第二批 · I4 面试专题</p>

配套学习: [多个接口串起来以后, 怎样管理数据和断言](../../learning/api-testing/api-data-lifecycle.md). 本文的录入、更新和清理入口为教学约定, 不表示已经在真实项目实施.

## 测试视角: 创建接口的返回值, 怎样用于后面的测试?

考察数据关联与判定依据是否分开. 可以按“先验证创建 → 提取编号 → 查询与更新 → 与独立预期比较”回答.

### 可以这样回答

“我先确认创建响应符合契约, 再取出本次新编号, 不使用固定历史编号继续执行. 后面的详情和更新都带这个编号. 但标题、客户、局点等预期保留在测试输入里, 不完全照抄被测接口的返回值.

“例如更新标题后, 我重新查询详情, 既核对新标题, 也检查编号和客户没有变化, 本次标记下仍只有一条记录. 如果创建失败, 后面的步骤因前置失败未执行, 不会拿旧数据凑出成功结果.”

### 追问: 更新响应和详情一致, 为什么还不够?

两个接口可以一致地返回错误旧值. 一致性只是证据之一, 还要与用户本次要求的新标题比较. 动态编号可以从响应关联, 关键业务预期应来自契约和输入. 不能让被测系统同时扮演答题者和唯一判卷者.

易错回答是“把所有响应保存到全局变量, 后面直接用”, 却没有说明生命周期、唯一标记和失败后的行为.

## 开发视角: 怎样让关联测试稳定, 又不依赖执行顺序?

考察准备能力、数据所有权和接口职责. 先区分场景内部依赖与独立用例之间的依赖, 再说明回收边界.

### 可以这样回答

“完整的创建后更新场景可以包含顺序依赖, 因为这是业务本身. 但另一条只检查权限的用例, 应准备自己的记录, 不等待这条链路先成功. 可以复用创建数据的方法, 每条用例使用不同运行标记和独立记录.

“清理能力需要精确定位本次所有的数据. 如果测试环境提供管理入口, 也必须限制到相应环境、运行标记和所有者. 初始检查发现来源不明的旧记录时应停止, 不应直接把它删掉当作准备成功.”

### 追问: 创建已经写入, 但没有拿到编号, 怎么清理?

如果已有预先保证唯一的运行标记、明确的所有权和授权管理能力, 可以按这个标记核对本次数据. 如果缺少这些条件, 应记录待处理对象与证据, 不能通过宽泛时间范围删除. 对可能继续后台执行的请求, 还需确认完成状态或采用相应隔离回收机制, 不能假设客户端报错就结束了写入.

## 测试视角: 断言失败后清理也失败, 最后报告哪一个?

两项都报告. 主检查失败说明实际业务结果与预期不一致; 清理失败说明执行环境还有残留. 例如详情仍是旧标题, 同时清理返回权限错误, 应保留两个错误、对应步骤及本次编号. 不让清理的新异常掩盖主失败, 也不因为清理成功就把主失败改成通过.

追问“用 finally 就解决了吗”时, 应说明 finally 只提供收尾执行位置, 不保证清理正确、范围安全或异常不会被覆盖. 还需要所有权检查、失败分别记录和明确的测试运行器结果约定.

## 术语与依据

| 名称 | 含义与用途 |
| --- | --- |
| Correlation | 把本次动态编号传到后续请求 |
| Test isolation | 避免用例顺序与残留数据影响结果 |
| Setup / Teardown | 明确准备、执行与回收的边界 |
| Primary failure | 保留主检查失败, 与收尾问题分开 |
