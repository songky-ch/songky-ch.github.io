# I1 面试记录: 我判断接口结果时, 不只看 HTTP 200

<p class="article-kicker">面试记录 · I1 · 判断依据与经验边界</p>

对应[工作笔记](../../learning/api-testing/api-test-oracle.md). 我的实际工作以 Web 功能测试、Postman 请求排查和 SQL 数据核对为主. 下面整理我对这类问题的判断方法, 具体故障与数值使用推演场景, 不作为已发生的项目成果.

## 测试视角: 接口返回 200, 你还会检查什么?

关注点是能否根据用例预期组织断言. 我的表达按“输入与身份 → 契约 → 响应 → 数据变化”的顺序展开, 不需要罗列所有测试类型.

### 我的表达

“我先看本条用例的目的. 正常查询返回 200 可能符合预期, 没权限的请求却不应该因为返回 200 就判通过. 接着核对内容类型、业务码、关键字段和实际结果, 需要写数据时还会检查新增或更新是否符合约定.

“比如生产问题录入, 我先准备唯一标记, 确认旧数据中不存在. 有权限且输入有效时, 本例约定返回 201 和编号, 并新增一条字段正确的记录. 如果标题超过约定长度, 则期望 422 且不新增数据. 状态和数据变化两项都要满足.”

### 追问: 所有响应字段都要逐字比较吗?

不必. 编号、创建时间或请求标识可能是动态值, 应按契约核对类型、格式、范围和关联关系. 业务输入如果允许规范化, 比如等价时间转换, 也不能机械按字符串比较. 相反, 只断言“字段不为空”又可能过于宽松, 需要说明具体风险和判定依据.

我需要避免的判断是“只要有 200、success 和 data 就通过”, 因为它没有证明输入条件、权限和业务结果正确.

## 开发视角: 分页接口怎样定义, 才容易验证?

我关注的是接口契约和数据稳定性. 先说清总数与本页数, 再解释筛选、排序和数据变化.

### 我的表达

“我要明确页码从哪里开始、每页范围、筛选条件、可见权限和排序. total 应说明是全表数还是筛选后总数. 在本例中, 全表 18,427 条, 筛选后 143 条, 每页 20 条, 所以第一页 20 条、第八页 3 条, 三者并不矛盾.

“我会用独立构造的已知数据核对有序编号, 不只检查条数. 相同时间需要稳定的次级排序, 否则翻页可能出现不稳定结果. 还要说明数据集是否会在翻页期间变化, 以及产品对此的约定.”

### 追问: 翻到第二页出现上一页的编号, 一定是实现缺陷吗?

先看测试条件. 在固定数据、明确稳定排序且使用相同筛选的样本中, 跨页重复违反预期. 如果分页期间新增了更靠前的记录, 基于偏移量的页面边界可能移动; 此时要结合产品对动态列表的一致性约定判断. 不能拿持续变化的数据当静态基准, 也不能用“数据会变化”掩盖固定样本中的重复.

## 测试视角: 这批接口测试通过率 98%, 怎么解释?

我需要说清统计对象、分母和未完成记录. 我的表达:

“这只是某次用例集合执行的结果, 不是生产请求成功率. 假设 100 次用例执行中有 80 次有效输入、20 次预期拒绝. 有效输入 78 次符合全部断言, 20 次拒绝也符合预期, 所以用例通过率是 98%. 有效输入单独的业务完成比例则是 78/80, 即 97.5%.

“我还会报告哪两次失败、是否存在测试环境或证据缺失, 避免一个比例掩盖关键问题. 样本量和分布不足时, 不把这个比例外推成整个平台质量.”

追问“4xx 越少越好吗”时, 应说明反向用例正确得到约定拒绝也是通过. 把所有 4xx 当测试失败, 或把所有 2xx 当测试成功, 都忽略了预期.

## 术语与依据

| 名称 | 中文含义 | 本篇作用 |
| --- | --- | --- |
| Test oracle | 测试判定依据 | 在接口实际返回之外建立独立预期 |
| Assertion | 断言 | 将预期转成具体检查 |
| API contract | 接口契约 | 解释状态、字段和业务变化 |
| Pagination | 分页 | 说明数量、顺序和数据变动的约定 |
