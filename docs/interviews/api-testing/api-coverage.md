# I3 面试记录: 生产问题查询的参数、权限与分页覆盖

<p class="article-kicker">面试记录 · I3 · 判断依据与经验边界</p>

对应[工作笔记](../../learning/api-testing/api-coverage.md). 这份记录整理我对尚未落地方案的面试表达. 我会说明设计依据、预期证据和验证边界, 将技术理解与实际完成的工作区分开; 示例数据与结果均为推演.

## 测试视角: 查询参数很多, 你怎么选用例?

我关注的是能否从规则得到独立预期, 而非报出用了多少种测试方法. 我的表达顺序是契约、固定样例、单因素、关键组合、覆盖证据.

### 我的表达

“我先明确参数默认值、合法范围、权限、日期边界和排序, 再准备能够区分这些规则的小样本. 例如 8 条生产问题中, 有其他客户、其他局点、区间外记录和不同类别. 对 A/X 账号查 10 月 20 日的产测问题, 我能手工得到 0201、0202、0208 三条.

“每页设为 2 后, 两页分别是两条和一条. 我会同时比较总数、有序编号及跨页重复, 再单独改变页数边界、空值或类别. 组合重点放在权限与过滤同时生效、同一时刻的次级排序等交叉位置, 而不是把所有参数机械相乘.”

### 追问: 同时传错三个参数, 能否算三项反向覆盖?

不能直接这样算. 如果第一项错误已经让请求被拒绝, 后两项可能没有执行到. 应先让其他条件合法, 分别验证各项规则; 只有契约明确了多错误优先级, 才为组合请求定义确定的优先结果. 多个错误都返回 400, 也不等于每个字段都被正确校验.

我需要避免的判断是“正常、异常、边界都测一遍”却无法给出任何固定数据与预期. 判断依据是能否解释一条用例为什么存在, 它失败时能暴露哪条规则.

## 开发视角: 列表已经过滤权限, 详情是否还需要检查?

我关注的是功能权限与对象范围. 先说明不同入口都要维持授权约束, 再解释列表总数和详情的契约.

### 我的表达

“需要. 调用者知道一个编号, 不代表可以访问它. 列表只展示 A/X 的记录, 不能阻止调用方直接请求 A/Y 的详情. 读取和更新都需要结合当前账号、操作和目标对象检查权限.

“列表里的 total 也要与 items 使用相同授权范围, 否则可能从统计值泄露其他客户信息. 我会给范围外详情约定明确的拒绝响应. 例如示例系统用 403, 真实产品也可能按隐藏存在性的要求使用另一种约定, 测试应依据已确认协议.”

### 追问: 固定分页样例没有重复, 能证明实时列表永不重复吗?

不能. 静态样例验证的是固定集合与排序下的窗口正确性. 数据在翻页期间新增或删除, 偏移分页边界可能移动. 开发需要说明产品对这种变化的约定; 测试要区分固定快照回归和动态数据场景, 不能互相代替.

## 测试视角: 32 条计划, 26 条通过, 你会报多少通过率?

先问剩下 6 条的状态. 若 2 条执行失败、4 条阻塞, 已执行通过率是 26/28, 约 92.86%; 计划完成率是 28/32, 即 87.5%. 同时列出失败风险与阻塞条件, 不能把阻塞算成通过, 更不能把用例通过率改名为业务规则覆盖率.

追问“是否可以发布”时, 回答应回到失败内容、阻塞是否触及关键链路和项目发布标准. 一个百分比无法单独替代风险判断.

## 术语与依据

| 名称 | 含义与用途 |
| --- | --- |
| Test fixture | 为独立预期提供固定数据与身份条件 |
| Object-level authorization | 验证对具体记录的访问权 |
| Invariant | 检查总数、范围和跨页成员等保持条件 |
| Offset pagination | 解释动态数据导致的分页边界移动 |
