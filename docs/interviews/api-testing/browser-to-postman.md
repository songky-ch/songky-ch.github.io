# I2 面试记录: 从页面异常到 Postman: 我的请求复现思路

<p class="article-kicker">面试记录 · I2 · 判断依据与经验边界</p>

对应[工作笔记](../../learning/api-testing/browser-to-postman.md). 我的实际工作以 Web 功能测试、Postman 请求排查和 SQL 数据核对为主. 下面整理我对这类问题的判断方法, 具体故障与数值使用推演场景, 不作为已发生的项目成果.

## 测试视角: 浏览器异常, Postman 正常, 你怎么定位?

我关注的重点是请求等价性和证据顺序. 先确认两次请求是否可比, 再讨论浏览器行为, 比直接说“前端问题”更有依据.

### 我的表达

“我先从页面操作定位对应请求, 对照方法、地址、参数、身份、服务环境和数据窗口. 尽量导入原请求复现, 不一开始就手工重写. 如果账号或日期不同, 两个结果本来就不一定相同.

“对齐以后, 我会区分请求没发出、预检失败、返回无法被页面使用, 以及响应正确但页面显示错误. 前几种情况分别需要看页面触发、跨域条件和身份上下文; 最后一种再检查页面处理. Postman 桌面请求成功不能证明浏览器路径没有问题.”

### 追问: 复制成 cURL 导入, 是否就保证一样?

不保证. 会话可能已过期, 当前环境变量、代理、重定向或 Cookie 管理可能不同, 请求期间数据也可能更新. 复制能减少人工漏字段, 但发送前仍需检查解析后的实际目标和参数. 不应把复制动作当作完成等价性证明.

我需要避免的判断是“Postman 通了就交给前端”. 正确的下一步取决于两端差异发生在哪个观察位置.

## 开发视角: 跨域报错时, 服务端一定没有处理请求吗?

这个问题检查对浏览器与服务边界的理解. 先区分实际业务请求是否发出, 再讨论响应可用性.

### 我的表达

“不一定. 某些跨域请求会先预检, 预检失败可能让后续业务请求不发出. 但也可能请求已经到达服务端并被处理, 只是响应不能被页面脚本读取. 所以看到浏览器报跨域错误, 不能直接推断没有写入.

“如果是写操作, 我会先用请求或业务标识核对实际结果, 再考虑是否重新提交. 同时检查预检、允许来源、凭证发送条件等证据. 不会用关闭保护的方式代替定位.”

### 追问: Postman 网页版也完全不受浏览器条件影响吗?

还要看请求通过什么代理发送. 桌面客户端、Desktop Agent 与网页中的发送路径不能一概而论. 面试时说明这一边界即可, 不需要背未经核实的界面选项. [MDN CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)和 [Postman 官方说明](https://learning.postman.com/help/resolve-issues/sending-requests/fixing-a-cors-error)支持上述区分.

## 测试视角: 改一个日期参数后查到了, 你能得出什么结论?

可以按“固定条件 → 唯一变量 → 结果差异 → 结论范围”来回答:

“假设页面要求包含 10 月 20 日, 原请求却以当天 00:00 为不包含的上界. 我先保留参数在 Postman 复现, 得到同样的 142 条. 然后固定身份、环境和数据快照, 只把上界改成次日 00:00, 得到 143 条, 且目标编号出现.

“这能支持日期参数与页面语义不一致的判断. 但它没有直接指出哪行代码错误, 也不能证明所有日期都存在同样问题. 后续需要查组参逻辑, 并回归边界附近的数据.”

追问“286 ms 变成 241 ms 是否说明性能提升”时, 应回答本次仅两次不同客户端观测, 缺少受控条件与重复采样, 不能据此形成性能改善结论. 时间差可以记录, 原因需要另行验证.

## 术语与依据

| 名称 | 中文含义 | 本篇作用 |
| --- | --- | --- |
| cURL | 请求工具及其表达方式 | 辅助迁移原请求 |
| CORS | 跨源资源共享机制 | 区分服务执行与浏览器响应访问 |
| Preflight | 预检 | 判断业务请求是否实际发出 |
| Desktop Agent | Postman 桌面代理 | 说明网页端请求的不同发送路径 |
