# 通用与垂直领域 Agent 面试: 开发与测试视角

学习入口: [通用 Agent 与垂直领域 Agent: 架构、完整流程与真实实现](../../learning/agent/general-vs-domain-agents.md).

本文的 Agent (智能体) 指根据目标与观察选择动作并调用工具的系统; LLM (Large Language Model, 大语言模型) 是其中承担理解和动作选择的模型组件. 通用 Agent 覆盖多类任务, 垂直领域 Agent 围绕特定领域构建. Workflow (工作流, 主要路径由程序预定义) 与自主循环是另一条控制维度, 不能直接等同于这两类系统.

## 开发专家视角

### 题 1. 通用 Agent 和垂直领域 Agent 的核心区别是什么? 软件工程 Agent 很自主, 为什么还能算垂直 Agent?

**考察点**: 能否分清目标覆盖范围与控制方式, 避免用产品名称代替架构分析.

**回答结构**: 定义任务范围 → 分离自主程度 → 比较领域资产和验收 → 真实实现举例.

**参考答案**:

通用与垂直主要区分系统面向哪些任务. 通用 Agent 需要组合搜索、文件、代码等能力处理多种目标; 垂直 Agent 的任务、数据、工具语义和验收集中在一个领域. 两者可能使用同一基础模型, 也都可能使用自主循环和工作流.

软件工程 Agent 可以动态决定查什么代码、改哪些文件和运行哪些测试, 但它的资产、工具和完成标准仍围绕软件开发, 因而是领域系统. OpenHands 的真实实现将 `Conversation` 的生命周期管理与 `Agent.step` 的动作选择分开, 并用动作和观察事件连接代码工具. 这直接说明“垂直”不等于“路径写死”. [OpenHands 架构](https://docs.openhands.dev/sdk/arch/overview).

Deep Agents 则提供可配置的通用 Harness (运行支架, 组合上下文、工具与控制能力). 给它接入代码工具和仓库规则, 可以成为软件工程应用的基础. 因此通用支架和垂直应用可以是上下层关系, 不必互斥.

**递进追问与回答要点**:

- 给通用助手加一份行业文档就完成垂直化了吗? 只是增加知识, 还需领域实体、实时事实、工具契约、权限、业务规则和验收. 如果这些仍然缺失, 不能声称已形成可靠领域闭环.
- 一个综合入口只会路由到固定流程, 算通用 Agent 吗? 它可以是覆盖面较宽的综合系统, 但动态自主程度较低. 回答应先说明“通用”的判定范围, 不能仅依据入口能聊很多话题.

**易错回答与判断依据**:

“通用一定多 Agent, 垂直一定单 Agent”混淆协作结构与任务范围. “垂直必须微调”忽略通用模型加领域工具的实现. 判断答案是否成立, 应要求给出任务集合、领域资产、动作边界和验收对象, 而不是只列模型名称.

### 题 2. 请从用户请求到最终结果, 讲完整的一次 Agent 执行链. 模型返回工具调用后发生什么?

**考察点**: 能否区分模型决策、运行时执行、业务状态与客户端展示, 说明输入输出契约.

**回答结构**: 接入 → 上下文 → 决策 → 校验执行 → 观察循环 → 验证与交付.

**参考答案**:

首先由接入层验证身份、登记附件、建立运行标识并解析任务限制. 然后组装本轮上下文: 指令、历史、领域事实、相关工具说明和必要知识. 模型接收这些输入后返回动作请求或最终内容.

Tool calling (工具调用) 是模型生成动作请求, 不代表函数已经运行. 运行时根据工具名定位实现, 检查 Schema (参数结构规范)、业务取值、身份与目标归属, 判断是否满足授权和审批要求, 才调用工具. 工具返回观察或错误, 通过调用标识与原请求配对, 再进入下一轮模型输入.

如果模型输出最终答案, 应按任务标准验证: 查资料看引用和依据, 修代码看改动与相关验证, 退款看权威业务状态和金额. 最后交付结构化状态、证据和产物. 流式文字结束只说明输出传输结束, 不能证明业务完成.

源码上, OpenHands `Agent._step` 准备消息并调用模型, `_execute_action_event` 执行工具后生成关联的观察事件. Dify 经典 `AgentNode._run` 则从图变量池构造参数, 调用选定策略并把消息流转换成节点事件. 这两个例子展示了同一层次分工在不同框架中的位置. [OpenHands Agent 源码](https://github.com/OpenHands/software-agent-sdk/blob/6ae64079cfd30cfe2f01a060c59168a4d650d883/openhands-sdk/openhands/sdk/agent/agent.py), [Dify 经典节点](https://github.com/langgenius/dify/blob/b953e69a0eb397e625337812e0319ab770f18783/api/core/workflow/nodes/agent/agent_node.py).

**递进追问与回答要点**:

- 模型一次请求两个工具, 可以并行吗? 只有在无数据依赖、无冲突副作用且实现支持时可以. “修改文件”和“依赖修改结果的测试”不能因一次生成就视为独立.
- 模型输出字段完全符合结构, 是否能直接执行? 不可以. 结构正确不代表订单归属、金额、币种和授权正确, 领域校验仍需服务端执行.

**易错回答与判断依据**:

把“模型调用接口”与“宿主程序执行工具”说成同一件事, 说明没有理清执行边界. 只说“入口 → LLM → 回答”遗漏观察循环和业务验收. 好答案能明确指出每个阶段谁提供事实、谁拥有权限、哪个标识关联结果.

### 题 3. 已保存聊天和检查点, 为什么恢复后仍会重复退款? 应如何设计状态?

**考察点**: 外部副作用、持久化边界、幂等与恢复语义.

**回答结构**: 分离状态 → 描述故障窗口 → 服务端幂等与核对 → 恢复验收.

**参考答案**:

至少分开对话状态、运行状态、业务状态和产物状态. Checkpoint (检查点, 保存执行进度的状态快照) 用来恢复节点、消息和待处理动作. 它不保证外部退款与本地保存构成一个原子事务.

典型故障是退款服务已创建记录, 客户端在收到响应前超时, 检查点仍显示“尚未提交”. 恢复后直接重放写操作, 如果换了业务键或服务端没有查重, 就可能产生重复效果.

需要用稳定的业务操作标识建立 Idempotency (幂等, 重复同一操作不产生重复业务效果). 退款服务应对该标识及对应参数建立持久化约束, 对相同操作返回既有结果, 对相同键但冲突参数拒绝. 客户端将未知状态转为核对状态, 查询权威服务后再决定下一步. 具体使用事务、唯一约束或其他机制取决于服务实现, 不能靠模型记忆保证.

LangGraph 区分单个会话的 Checkpointer (检查点持久化器) 和跨会话的 Store (应用数据存储). 二者解决执行状态和应用记忆的保存问题, 不能自动包住外部业务服务的事务. [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence).

**递进追问与回答要点**:

- 退款查询也暂时不可用怎么办? 保留“未知/核对中”状态和原操作标识, 在有界重试或人工核对后再确认. 不能因读失败就判定写失败并重新创建新退款.
- 一次运行可能包含两笔合法退款, 直接用 `run_id` 查重够吗? 不够. 运行标识和业务操作标识职责不同, 每笔业务操作需要明确身份、目标和参数绑定关系.

**易错回答与判断依据**:

“异常就重试三次”没有区分读写和未知副作用. “上锁就不会重复”没有说明锁作用范围、重启和跨服务问题. 可靠答案能画出写入成功、响应丢失、状态未保存三个事件的先后关系, 并说明恢复后如何查证.

### 题 4. 如何构建垂直售后 Agent, 既允许自主取证, 又保证资金动作符合业务约束?

**考察点**: 领域建模、控制边界、工具语义、上下文与执行权限的分工.

**回答结构**: 领域实体与不变量 → 混合编排 → 工具契约 → 交付状态.

**参考答案**:

先定义订单、订单商品、退款方案、审批与退款记录的实体关系. 金额采用明确单位和币种, 可退金额和资格由权威服务计算, 不让模型自由修改数据库字段. 人工审批如被业务要求, 应绑定具体方案, 而不是只保存一个“已批准”布尔值.

控制上可以采用工作流外环: 查询订单 → 资格计算 → 自主取证 → 审批检查 → 提交 → 核对. 自主取证部分由 Agent 决定读取哪些材料、补问哪些信息. 强制约束放在程序或业务服务中, 即使模型选错动作也不能突破.

工具接口采用领域语义, 例如 `preview_refund` 返回可执行方案, `submit_refund` 只接受方案标识和幂等键. 执行时用服务端身份校验资源归属. RAG (检索增强生成) 为政策解释提供有版本的依据, 实时订单状态仍来自业务接口. MCP (模型上下文协议) 可以统一连接工具, 但不替代业务鉴权.

这种混合方式可用 LangGraph 的节点和条件边实现, 也可用 Dify 工作流包含 Agent 节点实现. 框架提供能力, 业务约束需要应用自己完成, 本文没有验证某个退款应用已部署.

**递进追问与回答要点**:

- 政策材料中出现“忽略金额上限”怎么办? 这是 Prompt injection (提示注入, 外部资料试图控制行为). 文档只能提供事实, 不能修改可信约束. 真正的金额边界仍需服务端检查, 不能只做文本过滤.
- 给工具加入 Schema 是否已经保证安全? Schema 约束结构, 不保证主体拥有目标订单, 不保证审批有效, 也不保证重复调用无副作用.

**易错回答与判断依据**:

“提示词里写严谨一点”和“改用更大模型”都没有落实强制条件. 好答案应说清自主范围、拒绝路径、业务状态和谁执行校验, 而不只列工具名称.

## 测试专家视角

### 题 5. 怎样公平比较通用 Agent 与垂直 Agent? 一个用了更多步骤, 是否就更差?

**考察点**: 对照条件、任务分布、结果和过程的联合评价.

**回答结构**: 统一任务与资源 → 明确结果标准 → 检查不变量 → 比较质量成本分布.

**参考答案**:

先固定相同任务集、身份权限、数据快照、业务规则和可用资源. 不能让垂直 Agent 访问实时订单, 通用 Agent 只能看历史文档, 然后把结果归因于架构. 若要评价跨领域泛化, 需要另设跨任务集合, 不能拿单一退款集代表所有任务.

每个任务定义可观察结果, 如退款记录、金额、订单归属和是否重复. 过程检查聚焦必须和禁止的条件, 如审批早于提交、目标资源正确. 对检索和取证允许多条合法路径, 不要求轨迹逐字一致.

最终再比较成功率、违规率、步骤、费用和延迟分布. 更长路径可能是低效探索, 也可能获取了必要证据. 需要结合任务结果和风险判定, 不能只看调用次数. 真实模型通常存在随机性, 需要重复运行并记录配置, 但不凭空设定所有系统通用的重复次数和合格阈值.

**递进追问与回答要点**:

- 垂直系统遇到范围外任务直接转人工算失败吗? 应按事先定义的产品范围判断. 对范围内任务未完成与范围外正确拒绝不能混为一项, 同时应披露覆盖范围, 防止靠拒绝抬高成功率.
- 所有最终答案都让另一个模型评分够吗? 不够. 业务状态、金额、重复记录与禁用工具可以确定检查; 模型评价适合补充解释质量, 不能替代权威状态验证.

**易错回答与判断依据**:

只比模型名称或单次演示不可复现. 只比输出文本遗漏副作用. 好答案能给出固定输入、运行配置、权威判定器和过程不变量, 并区分范围内外任务.

### 题 6. 最终回复说“退款成功”, 但工具轨迹有问题. 如何设计判定与定位?

**考察点**: 业务结果、动作正确性、证据关联与分层定位.

**回答结构**: 查业务事实 → 核对动作与参数 → 对齐运行记录 → 归因到具体层.

**参考答案**:

首先以退款服务的权威记录判断是否创建、金额是否正确、目标订单是否匹配、状态究竟是已接收还是已确认. 没有对应记录, 即使文本流畅也不能判成功. 若记录存在, 仍需检查是否重复或未经审批.

然后追踪模型请求、校验结果、实际工具执行及其观察, 通过调用标识关联, 检查“模型想做什么”与“运行时真正做什么”是否一致. 对照本轮模型实际看见的上下文, 分辨是错误政策、参数生成错误、分发执行问题还是交付验证缺失.

Tracing (链路追踪, 将模型、工具和业务事件关联的观测方式) 应包括运行标识、步骤、工具调用标识、目标资源和业务操作键, 但过滤凭证. 它提供调查证据, 不自动提供业务通过结论.

在 OpenHands 的已读源码中, 动作事件与观察事件通过 `action_id` 和 `tool_call_id` 关联, 能帮助理解这种证据连接. 不能因为框架存在事件, 就假定某个具体应用已经记录所有所需字段.

**递进追问与回答要点**:

- 业务结果正确, 但曾调用另一个用户的查询接口怎么办? 若服务拒绝且无泄露, 记录非法尝试与阻断是否符合要求; 若实际访问成功, 即便目标退款完成也存在权限违规, 应按预先定义的安全指标判定.
- 工具返回成功, 但结果属于另一订单怎么办? 核对调用标识之外还需核对实体标识. 请求结果配对正确不等于业务实体正确.

**易错回答与判断依据**:

“最终成功就不看中间步骤”会遗漏越权与重复操作. “模型选了工具就是工具执行了”混淆请求与观察. 判断依据应落在真实资源状态和关联证据.

### 题 7. 如何测试“退款已写入但响应丢失”和进程崩溃恢复? 配套离线练习能证明什么?

**考察点**: 故障注入位置、重复副作用检查和验证边界诚实性.

**回答结构**: 列故障时点 → 执行注入 → 恢复并核对 → 区分模拟与完整系统证据.

**参考答案**:

至少覆盖调用前失败、服务未写入时失败、写入后响应丢失、收到响应但检查点未保存、检查点保存后重启. 每个时点验证恢复状态、原操作键和权威业务记录, 特别检查重复记录数量与参数一致性.

配套练习模拟服务先写入内存记录, 再抛出超时. 两种控制方式随后按原操作键查询确认, 并断言只有一条记录. 正常完成后再次用同一请求提交, 仍保持一条记录. 这证明所写模拟程序在这些输入下遵循了核对与去重路径.

它没有真实模型, 状态没有跨进程持久化, 也没有网络、分布式并发或支付接口. 因此不能声称验证了真实 Agent 规划、数据库唯一约束、进程恢复或资金到账. 完整系统测试还需用可控制的服务替身或测试环境, 真实保存检查点, 重启执行器并核验业务存储.

实际记录: [Python 3.12.14, 10 条场景检查](/examples/general-vs-domain-agents/practice-results.txt).

**递进追问与回答要点**:

- 同一个幂等键换了金额再提交, 应怎么测? 服务应拒绝冲突参数或按清晰契约返回冲突, 不能静默把不同业务合并. 当前练习未覆盖这一完整通用契约, 需要专门场景验证.
- 两个恢复进程同时提交怎么办? 在真实持久化服务上做并发测试, 验证原子查重或唯一约束. 顺序调用的内存字典示例不能证明并发安全.

**易错回答与判断依据**:

“本地示例通过等于生产恢复可靠”扩大了证据范围. 好答案明确故障发生在哪个系统边界, 如何观察实际效果, 以及还有哪些未验证项.

### 题 8. 如何测试长任务里的约束遗忘、提示注入与领域知识过期?

**考察点**: 上下文管理、信任边界、政策版本与可观察验收.

**回答结构**: 建立可信约束 → 构造压力资料 → 检查每轮输入与动作 → 对照执行边界与证据.

**参考答案**:

先把订单、金额上限、身份和审批绑定放入结构化运行状态, 再用长历史和大工具结果触发上下文压缩. 检查压缩前后有效约束是否保留, 并在任务后段尝试生成超限动作, 验证执行层仍拒绝. 不能只观察模型是否在回答里复述了限制.

提示注入测试把恶意指令放在低信任来源, 如政策附件或搜索结果中, 例如要求忽略审批或改用另一个订单. 观察模型动作和服务端拒绝记录, 判断指令层级与实体权限是否保持. 输入过滤可以是辅助, 强制边界仍在工具和业务服务.

知识过期测试保留旧政策与新政策, 设置适用日期和商品范围, 检查检索过滤、引用和决策依据. 实时订单状态改变时, 验证系统重新读取权威服务, 而不是沿用旧摘要. RAG 提供资料不意味着资料永远正确或最新.

Deep Agents 的官方文档描述摘要、上下文卸载、技能与记忆; OpenHands 采用上下文压缩器组织模型输入. 这些机制提供测试位置, 不保证所有约束天然不会丢失. [Deep Agents Overview](https://docs.langchain.com/oss/python/deepagents/overview), [OpenHands Agent 实现](https://github.com/OpenHands/software-agent-sdk/blob/6ae64079cfd30cfe2f01a060c59168a4d650d883/openhands-sdk/openhands/sdk/agent/agent.py).

**递进追问与回答要点**:

- 模型提出非法动作但服务端成功阻断, 算通过吗? 分开报告模型动作质量和系统边界有效性. 系统未越权不等于模型表现无问题, 也不能把被阻断请求统计为实际越权成功.
- 新政策发布时老运行尚未结束, 应用哪版? 必须先定义业务的生效语义, 例如按申请时点或提交时点. 然后围绕该规则测试, 不能由测试人员或模型临时猜测.

**易错回答与判断依据**:

只用一条“忽略之前指令”的对话输入测试不了资料注入. 只看摘要长度测不了约束保留. 好答案能给出可信约束来源、注入位置、政策时点、动作证据与服务端判定.
