# 怎样连贯解释 Agent 的架构与请求链路?

<p class="article-kicker">第三批 · A1 面试专题</p>

本篇配套 [Agent 请求地图](../../learning/agent/agent-request-map.md). 所有架构和数字均为教学设计, 参考答案用于解释理解, 不表示你已在生产落地这些方案. 讨论范围是单次业务调用, 多步骤只作拓展.

## 开发专家视角: 模型说要调用工具以后, 系统还要做什么?

**考察点:** 能否区分模型、应用执行器和业务服务的职责, 能否解释数据与控制的流向.

**回答结构:** 先区分提议与执行, 再按一条查询串起输入、检查、派发、返回和结束.

**参考答案:** 模型生成工具名和参数, 只表示它提出了一个动作. 应用需要解析这份决策, 检查工具是否允许使用、字段和业务值是否合法、当前账号是否有权限、调用次数是否超限, 然后才派发给业务函数. 用户消息里的身份声明不能替代服务端认证.

例如用户查 SITE-A、CUSTOMER-X 昨天的发货量, 教学时钟固定为 2026-10-22 10:00, 上海时区. 应用提供时钟和工具说明, 模型提出 `query_shipments`, 参数区间为 10 月 21 日零点到 22 日零点, 左闭右开. 执行器检查后调用一次, 工具返回 12,840 只, 应用再将结果交给模型组织回答. 组织回答这一轮不再派发工具. 所以模型可以参与两次, 而业务工具只执行一次.

这条链路里, 提示词说明行为规则, 上下文提供本轮信息, 状态记录已执行次数与结果, 轨迹保留各事件以便核查. 这些东西不是同一个“记忆模块”. 工具超时则不能编造结果; 写操作超时还可能出现服务端已提交但响应丢失, 需要保留待核实状态, 不能贸然重试.

**递进追问:** 只在提示词里写“最多调用一次”够不够?

不够. 模型可能生成多个调用, 也可能在收到结果后继续请求调用. 本例由执行器检查整份计划的调用数量, 在派发前占用次数, 并关闭结果表达阶段的执行能力. 超时也算已尝试一次, 本例不自动重试. 如果真实工具包装器内部有重试, 还需要另记下游请求次数, 不能用一次函数调用掩盖多次业务尝试.

**易错回答与判断依据:** “模型自己访问数据库, 失败再让它试一次”混淆了决策和执行, 也缺少重复写入约束. 能否指出鉴权所在层、调用计数所在层和超时出口, 是判断回答是否完整的依据.

## 测试专家视角: 最后回答错了, 你从哪里查?

**考察点:** 是否会收集可见证据并逐层归因, 是否知道证据不足时不能硬判根因.

**回答结构:** 对齐请求标识和版本, 从最终结果往前比对, 再给一个具体反例.

**参考答案:** 我会关联用户输入、必要历史、固定时钟、工具目录和提示词版本, 然后看路由决策、提议参数、实际派发、工具返回和最终回答. 我不需要模型的隐藏推理, 需要的是系统对外可观察的事件.

如果工具返回 12,840 只, 回答变成 12,480 只, 优先检查结果表达. 如果工具返回的是另一个客户的数据, 先检查实际派发参数; 实际参数与模型提议不同, 查执行器或适配层; 提议本身就错了, 再看上下文是否足够、日期规则和工具说明是否明确. 如果只有最后一句话, 可以判回答不符, 但暂时不能断定是哪层造成的.

对于录入任务, 我会增加实际业务状态检查. 模型说“已录入”, 或工具返回了一个编号, 都不能独立证明记录已提交. 应在隔离的测试数据范围核对新增数量和字段, 将错误回答、错误动作和真实副作用分开记录.

**递进追问:** 本例阶段耗时为 42、820、6、240、910 ms, 能说明什么?

在这些阶段串行且不重叠的教学前提下, 合计 2,018 ms. 它只代表列出的处理阶段, 不自动包括浏览器网络等成本. 不是 P95, 也不足以说明系统性能稳定. 若 trace 中父阶段包含子阶段, 还不能直接相加.

**易错回答与判断依据:** “输出错了就优化 prompt”跳过了参数转换、真实数据与工具故障. “日志没有调用记录所以没调用”则忽略了采集完整性. 回答应能说明证据链和未知状态.

## 开发专家视角: 单次调用系统和多步骤 Agent 差在哪里?

**考察点:** 能否解释路径控制方式, 而不把工具数量和模型调用次数当成唯一分类依据.

**回答结构:** 先说明当前范围, 再解释观察后的动态决策, 最后列出新增测试边界.

**参考答案:** 单次调用的教学系统在做完一个动作后结束. 多步骤系统可能把执行结果交回模型, 由模型根据结果继续选择下一步, 直到任务完成或触发限制. 例如先查询问题再根据查询结果录入跟进事项, 后一步依赖前一步的实际内容.

固定工作流也可以安排多个模型和工具调用, 只是下一步由程序预先规定. 判断是不是动态决策循环, 要看路径控制方式. 不能因为有五十个工具就断定系统能完成五十步任务, 也不能因为业务工具只执行一次就否定这套系统的业务价值.

扩展后要测试停止条件、总预算、失败去向、状态更新与写操作约束. 当前单次能力下, 复合请求应按明确产品规则处理; 本例约定先要求拆分, 不擅自做前半部分.

**递进追问:** 是否一定要引入长期记忆和复杂规划器?

不一定. 应先说明任务为什么需要这些能力. 当前的固定查询可以仅使用本轮信息和必要历史; 没有跨任务存储需求, 不应把保存状态直接叫长期记忆. 学习时可以理解拓展组件, 但不能将它们画成公司当前必然存在的架构.

**易错回答与判断依据:** “Agent 等于 LLM 加工具加记忆”只是名词集合. 能解释一次真实信息流和一个终止条件, 才表明理解组件如何配合.

## 术语与来源

| 英文名称与缩写 | 中文含义 | 本篇具体作用 |
| --- | --- | --- |
| LLM / Agent | 大语言模型 / 智能体系统 | 区分决策组件与整体执行系统 |
| Context / State | 上下文 / 状态 | 区分模型可用输入与请求处理进度 |
| Executor / Trace | 执行器 / 轨迹 | 控制动作并为测试留下证据 |
| Workflow / Agent loop | 固定工作流 / 动态循环 | 说明下一步如何产生 |
