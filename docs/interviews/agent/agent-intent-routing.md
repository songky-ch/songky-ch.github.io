# Agent 意图识别与路由面试: 开发与测试双视角

配套学习: [Agent 意图识别与路由: 生产实现、测试案例与核心指标](../../learning/agent/agent-intent-routing.md).

- **目标**: 检验能否把概念落到接口、状态、指标、测试证据和生产发布.
- **范围**: Agent (智能体) 的 Intent (意图, 用户期望目标) 与 Routing (路由, 结合上下文和约束选择处理路径). LLM (Large Language Model, 大语言模型) 只提供识别候选, 权限和业务执行由受控服务处理.
- **技术分类 / 内容类型**: Agent / 面试专题.
- **最后核查日期**: 2026-10-18. 来源与学习文章一致: 美团 2021 技术文章、WOWService `2510.13291v1`、LinkedIn `2608.10224v1`、Uber COTA 2018、官方文档与研究论文.
- **验证状态**: 配套练习实际运行 30 条固定合成候选与 7 个测试方法; 未运行真实模型、企业服务或线上实验. 策略仍有 1 条已知业务路线错误, 不作为可上线实现.
- **经验边界**: 所有回答都是技术参考, 不代表你做过这些项目, 不保证真实面试出现. 企业公开事实与教学设计在答案中区分.

![意图识别与路由架构](../../public/images/agent-intent-routing/architecture.svg)

读图: 候选判断、路由决策与业务执行有不同职责. 面试回答要说明错误在哪层被发现、靠什么证据确认, 不能只讲“换更强模型”.

## 开发专家视角

### 1. 为什么“退款意图识别正确”仍可能导致错误路线?

**面试问题**: 用户输入“帮我退款”, 分类模型正确给出退款. 系统是否应该立即调用退款接口?

**考察点**: 是否区分意图、参数、权限、资格、确认和业务执行.

**回答结构**: 结论 → 三层职责 → 具体状态差异 → 数据契约 → 验证.

**参考答案**: 不应直接执行. 意图只表示目标, 路由还需要决定当前下一步. 未绑定订单应收集订单; 未登录应认证; 非本人订单应拒绝; 不符合资格应说明规则; 缺本次有效确认应先确认. 只有条件齐全才进入退款流程, 提交时业务服务还要重新校验.

识别器输出受约束候选、参数和证据; 策略输出注册过的路线和原因码; 执行器返回真实操作状态. 同一正确意图可以在不同状态对应不同正确路线. 测试时固定退款候选, 分别注入上述状态, 检查路线和禁止动作, 再在集成层检查业务终态.

**递进追问与回答要点**: 如果候选分数达到 0.99, 能否跳过认证? 不能. 分数是模型判断, 认证和资源归属来自可信服务, 二者没有替代关系.

**易错回答与判断依据**: “置信度高就执行”混淆预测与授权. 合格回答必须给出至少一个意图正确但路线不同的例子, 并说明由哪层校验.

### 2. 多业务、千级意图怎么实现, 是否一定需要多个 Agent?

**面试问题**: 同时支持外卖、酒店和零售, 意图数量较多且经常变化, 你会如何设计?

**考察点**: 标签体系、分层候选、模型选择和错误传播.

**回答结构**: 定义标签 → 领域候选 → 意图召回与排序 → 策略 → 验证取舍.

**参考答案**: 先定义用户目标、包含 / 排除边界和对应流程, 再选择模型. 可先识别业务领域, 在候选域内召回意图定义和正反例, 再用分类器或 LLM 排序. 对简单标准事件直接走受控映射, 复杂多轮才升级模型. 第一层要保留不确定性, 不能强制只留一个领域后让后层永远看不到正确候选.

多 Agent 只是组织方式. 一个统一模型配多个领域配置也可以完成识别; 路由层仍需要明确规则和状态约束. 美团 2021 文档公开了综合入口下的领域识别与澄清, WOWService v1 介绍统一模型下的多场景适配. 两者说明业务边界与流程可以独立于模型数量存在, 不代表它们使用完全相同架构. [美团 2021](https://tech.meituan.com/2021/09/30/Artificial-Intelligence-Customer-Service.html), [WOWService v1, 3.2](https://arxiv.org/html/2510.13291v1#S3.SS2).

**递进追问与回答要点**: 领域第一层准确率很高为什么端到端仍差? 检查候选召回、入口冲突、长尾领域以及错误是否被后层放大, 不只看总体均值.

**易错回答与判断依据**: “每个标签部署一个 Agent”没有解释维护成本与执行边界. 判断应看它是否减少混淆、能否独立更新和回归, 不是 Agent 数量.

### 3. 阈值怎么设, 为什么不能相信模型自报概率?

**面试问题**: 退款请求用 0.8 还是 0.95 的阈值? 你怎样证明选择合理?

**考察点**: Calibration (置信度校准)、错误代价、拒判和数据划分.

**回答结构**: 先定义分数 → 独立校准 → 风险覆盖曲线 → 分业务选择 → 硬边界保留.

**参考答案**: 首先确认分数来自哪里. 分类概率、向量相似度和 LLM 自报的“90%”不可直接比较. 在独立校准 / 阈值集上检查分数与正确率是否对应, 然后扫描阈值, 比较 Automatic coverage (自动处理覆盖率) 与 Selective risk (自动接受后的错误率). 高风险写入还要看按代价加权的错误和关键违规, 选择满足约束的方案后在封存测试集报告.

模型校准不能代替授权. 即使阈值有效, 错误候选仍可能高置信. 退款权限、具体操作确认和提交前状态检查必须独立存在. 本文练习的 0.80 是演示常量, 没有生产校准意义. 校准研究说明现代神经网络可能过度自信, 温度缩放适用于具备相应分类输出的条件, 不是对任意自报概率都成立. [Guo 等, 2017](https://arxiv.org/abs/1706.04599).

**递进追问与回答要点**: 阈值提高后错误率下降, 可以宣布提升吗? 同时报告覆盖率和用户成本; 若自动量几乎降为零, 不能只夸剩余样本准确.

**易错回答与判断依据**: “行业一般 0.9”缺少分数定义、数据和业务依据. 合格回答能复算分母并明确阈值在哪个集合选择.

### 4. 如何处理“可以”“换一单”“不是退款”这些多轮输入?

**面试问题**: 用户先确认 A 单退款, 又说“换 B 单, 不是退款, 要发票”, 系统怎么避免旧任务误执行?

**考察点**: Dialogue state (对话状态)、目标纠正、任务切换与确认失效.

**回答结构**: 本轮行为 → 活跃任务 → 状态迁移 → 确认绑定 → 并发保护.

**参考答案**: 不能只把每句独立分类. 本轮需要识别否认、纠正、换资源和切换目标; 明确关闭或挂起旧退款任务, 作废旧确认, 再进入 B 单的发票任务. “可以”必须绑定上一步具体问题, 而不是映射到永久有效的同意标记.

确认应在服务端关联用户、任务、操作、订单、金额、币种、状态版本和时效. 修改任一关键条件或撤销目标后重新确认. 旧模型响应晚到时, 用状态版本或顺序事件拒绝陈旧写入. 跨设备共享订单的最终合法性仍由业务系统判断. 只把聊天摘要更新为“用户要发票”而没有取消异步退款任务是不完整的.

**递进追问与回答要点**: 已绑定金额和订单, 为什么仍可能错? 若没识别出目标撤销, 旧凭据可能还被使用, 所以确认生命周期与最新任务状态必须一并校验.

**易错回答与判断依据**: “把历史都给模型, 它会记住”没有可检验状态. 回答必须明确哪些事件使旧确认失效, 并提供状态记录或操作日志的证据点.

### 5. 生产中如何处理高峰、缓存和模型故障?

**面试问题**: 高峰每秒 2,000 请求, 部分需要强模型, 你如何估算并保证路由服务可用?

**考察点**: 容量估算、时延预算、缓存正确性和故障放大.

**回答结构**: 流量分层 → 平均在途估算 → 尾部与限流 → 上下文缓存 → 故障路径.

**参考答案**: 若 15% 请求进强模型, 平均耗时 0.8 秒, 平均在途约 240. 这是教学估算, 不是压测结论, 还要按输入长度、供应方限流、尾部时延和突发流量确定容量. 把端到端 Deadline (截止时间) 传下去, 给重试设上限与剩余预算, 避免依赖故障造成请求倍增.

缓存公共意图定义与候选召回较容易; 对话决策需关联租户、任务状态、资源和版本, “可以”不能按纯文本跨会话复用. 模型故障与主动拒判使用不同原因码. 是否转人工由业务约定决定, 不把故障写成用户无法表达. 不论命中缓存还是使用备选路径, 都不能绕过真实写入校验.

**递进追问与回答要点**: 退款接口超时也按分类请求重试吗? 不能, 应查询幂等操作的真实结果, 区分未提交、处理中和已成功.

**易错回答与判断依据**: “加缓存、加机器”没有说明缓存键与任务状态. 合格回答应能指出纯文本缓存会造成的具体误执行.

### 6. 路由模块如何发布和回退?

**面试问题**: 提示词更新不改代码, 是否可以直接上线?

**考察点**: 行为版本化、状态兼容、影子和受控发布.

**回答结构**: 版本边界 → 相关回归 → 影子 → 灰度 → 业务观察与回退.

**参考答案**: 提示词会改变分类和工具行为, 必须当作行为版本管理. 模型、提示词、意图定义、策略、知识快照和状态模式都要可追踪. 先用同一批样本配对回归, 再在 Shadow mode (影子模式) 只计算新决策, 禁止真实副作用. 之后小流量灰度并观察任务成功、违规、人工负载和尾部时延.

回退不能只切换提示词地址. 新版生成的在途任务、确认凭据和状态字段是否被旧版理解, 需要提前处理. LinkedIn v1 公开讨论了版本化产物、分阶段发布与回退, 但并不说明任何提示词优化都可跳过业务门禁. [LinkedIn v1, 3](https://arxiv.org/html/2608.10224v1#S3).

**递进追问与回答要点**: 新旧路线一致率 99% 可以代替准确率吗? 不能, 旧系统也会错; 分歧和一致部分都需要代表性人工标注与业务终态检查.

**易错回答与判断依据**: “只是文本配置所以风险低”忽略实际行为. 合格回答能说明如何定位某条错误用了哪些版本, 并恢复正在执行的任务.

## 测试专家视角

### 7. 你如何制定测试数据和真值?

**面试问题**: 只有十万条历史聊天和原始工单队列标签, 如何开始评估路由?

**考察点**: 标注质量、泄漏、分层覆盖和统计单位.

**回答结构**: 数据治理 → 定义真值 → 分组切分 → 边界补充 → 总体加权.

**参考答案**: 先脱敏并明确意图体系和业务规则版本, 不把历史队列直接当正确答案. 抽样由两位标注者独立标注意图、正确当前路线、禁止动作和业务终态, 分歧仲裁, 无法判定的样本单列. 标注只使用当时能获得的信息, 不泄漏事后结果.

按会话和资源相关性分组, 做近重复清理, 使用时间窗检查新业务与政策变化. 训练、开发、校准和封存测试分开. 根据业务、语言、入口、难度和风险分层, 补充否定、指代、纠正、多目标和范围外样本. 安全挑战集可过采样, 但不能直接用其比例代表线上错误发生率; 总体结果需要生产权重和随机抽样支撑.

**递进追问与回答要点**: 人工都无法区分两个意图怎么办? 先检查定义是否重叠、上下文是否缺失, 允许不可判定或可接受集合, 不强迫随机选择一个标签.

**易错回答与判断依据**: “随机按消息切 8:2”容易把同会话泄漏到两边. 合格回答应解释数据划分单位与标签如何验证.

### 8. 如何证明是识别错、路由错还是执行错?

**面试问题**: 用户要发票, 最后发生退款. 你怎么定位?

**考察点**: 分层测试、证据关联与错误注入.

**回答结构**: 看业务事实 → 重建轨迹 → 找最早偏差 → 固定边界回放 → 修复验收.

**参考答案**: 先确认退款业务记录, 再用 Trace (调用轨迹) 关联用户轮次、当时状态、候选、路线、工具参数和结果. 若候选已是退款, 检查否定表达和历史干扰; 若候选是发票但路线退款, 固定候选重放策略; 若路线正确但工具退款, 检查工作流映射和异步旧任务; 若工具也无退款, 查是否其他渠道操作.

测试中注入正确和错误候选, 并独立控制工具返回和状态版本. 这样能证实后层是否有保护, 不依赖模型碰巧答对. 不只检查最终回答, 因为它可能礼貌但错误声称成功.

**递进追问与回答要点**: 日志没保存候选和状态怎么办? 本次只能报告已确认业务异常与归因缺口, 不能猜根因; 补可观测性后再构造复现.

**易错回答与判断依据**: “换一个模型看能否恢复”不能定位具体层次. 合格答案应能说清楚一次回放固定哪一层输入.

### 9. 30 条里对 29 条, 为什么仍不能上线?

**面试问题**: 配套练习路线准确率 96.67%, 7 个测试通过, 你给什么结论?

**考察点**: 分母、高风险切片、样本代表性和测试含义.

**回答结构**: 限定已证实范围 → 报风险指标 → 解释测试通过 → 列缺失证据.

**参考答案**: 这说明确定性策略在固定合成输入上处理了多数约束, 不能证明生产可用. 30 条样例中策略有 2 次进入退款准备, 其中 1 次错误, 该路线错误率是 50%. 它没有产生真实退款, 所以这是错误决策率, 不能说实际资金违规率是 50%.

7 个方法中一个明确断言已知语义失败仍存在, 其他方法覆盖可判定的策略条件. 测试通过表示代码符合练习预期, 不是满足业务上线门槛. 样例人工挑选, 候选注入, 没有真实识别、并发状态和业务终态, 96.67% 不能外推到生产. [实际结果](../../public/examples/agent-intent-routing/results.json).

**递进追问与回答要点**: 全部改成人工, 错误变零可以吗? 自动覆盖也变零, 不满足服务目标. 零接受时选择性错误率应记不适用, 同报覆盖和体验成本.

**易错回答与判断依据**: “准确率超过 95% 就合格”既无业务依据又掩盖错误代价. 判断要看危险切片、真实能力和未验证范围.

### 10. 怎么设计多轮、并发和确认的关键测试?

**面试问题**: 给出三组能发现“单轮分类测试发现不了”的场景.

**考察点**: 状态转换、确认作废与竞态.

**回答结构**: 初态 → 事件序列 → 每轮断言 → 终态与禁止副作用.

**参考答案**: 第一组对比同一“可以”在退款确认与人工询问后的路线, 检查待办绑定. 第二组确认 A 单 25 元后改 B 单或 30 元, 检查旧确认作废、重新资格判断和未提交写操作. 第三组先要退款再要发票, 故意让第一轮模型结果后返回, 验证旧版本无法覆盖最新目标.

每组都应断言活跃任务、资源、阶段、状态版本、确认和允许动作, 不只断言最终句子. 并发测试需要可控地延迟推理 / 状态提交, 正常串行回放不能证明竞态处理正确. 配套本地练习只执行了字段绑定, 未执行真实状态引擎或并发测试.

**递进追问与回答要点**: 用户改回 A 单能否恢复之前确认? 应按明确的确认生命周期与业务状态重新判断, 不能因字段碰巧相同就默认旧同意仍有效.

**易错回答与判断依据**: “把多轮拼成文本再测一次分类”缺少状态和动作断言. 合格答案包含可观测迁移与禁止调用证据.

### 11. 如何测试工具超时与重复退款?

**面试问题**: 系统调用退款超时后自动重试, 如何测试它不会重复扣账 / 退款?

**考察点**: Idempotency (幂等性)、不确定结果、故障注入和业务终态.

**回答结构**: 明确不确定性 → 注入响应丢失 → 查询 / 重试 → 查业务事实.

**参考答案**: 在沙箱准备订单和具体操作幂等键, 让业务服务成功写入后丢弃响应. 让客户端经历超时、重复投递和服务重启, 检查使用同一操作标识查询或重放时都获得同一结果, 账务事件和退款记录只有一份. 改金额却沿用同一键时, 按服务契约拒绝不一致请求.

还要测试业务仍在处理、查询暂时失败以及两个工作进程并发提交同一操作. 只统计客户端调用次数不够: 调了两次可能安全幂等, 调了一次也可能服务端重复写入. 最终判定以业务记录和金额不变量为准. 本文只有设计, 没有冒称已测试真实退款服务.

**递进追问与回答要点**: 把会话号当幂等键有什么问题? 同一会话里两笔独立合法操作会被错误合并, 所以键要表达具体操作身份.

**易错回答与判断依据**: “超时再试三次”没有处理已成功但响应丢失. 合格答案必须设计这个故障点并检查数据库 / 账务终态.

### 12. 如何评价真实企业案例和线上实验?

**面试问题**: 某报告说路由准确率提升 30.6%, 是否足以证明新识别模块有效?

**考察点**: 百分比 / 百分点、样本口径、组件归因和实验设计.

**回答结构**: 查原始定义 → 查样本和随机化 → 查处理组合 → 查护栏 → 限定结论.

**参考答案**: 先确认是相对百分比还是百分点. LinkedIn v1 表 5 从 38.2% 到 68.8%, 是 +30.6 个百分点, 并注明路由项每组 356 条固定标注决策; 不能写成全量生产用户的准确率. 处理组同时改变提示词、检索和评测闭环, 因而只能支持组合效果, 不能归因到单一模块. [LinkedIn v1, 5](https://arxiv.org/html/2608.10224v1#S5).

自己设计 A/B test (随机对照实验) 时, 按会话 / 用户等合适单位固定分组, 处理重复用户相关性, 预先定义主指标、Guardrail (护栏指标) 和停止规则. 同时看任务成功、再次联系、违规、人工负载、尾部时延和成本. 对多指标和重复观察采用适当统计方法. 影子中的一致率不是准确率, 需要独立真值.

**递进追问与回答要点**: 如果新系统处理更快但满意度下降? 不应只宣布效率收益, 要检查草率结案、澄清不足、未成熟观察窗和不同业务切片.

**易错回答与判断依据**: “大厂数据说明方法一定通用”忽略来源、版本和外部有效性. 合格答案应明确哪些事实已证实、哪些仍需目标业务验证.
