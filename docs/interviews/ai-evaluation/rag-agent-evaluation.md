# RAG、Agent 与混合评测面试: 开发与测试视角

先看系统有没有找对资料、回答完整, 再看它有没有按规则办对事情. 前一部分是检索增强生成 (RAG, Retrieval-Augmented Generation) 的主要评测对象; 根据任务选择工具、推进多轮操作的智能体 (Agent), 还需要检查每次动作和实际状态. 混合系统要把两段证据连起来. 本专题给出技术参考答案, 不代表读者已经实施过这些项目.

## 开发专家视角

### 1. 怎样构建一个可回放的 RAG + Agent 评测运行器?

**面试问题**: 售后助手需要查规则、查订单并退款. 怎样比较两个版本, 同时分清检索、决策和工具问题?

**考察点**: 任务契约、环境隔离、真值隔离、证据关联、判定器分层与版本控制.

**回答结构**: 成功条件 → 固定输入和环境 → 执行与采集 → 分层判题 → 对照与归因.

**参考答案**: 先把成功写成可验证条件: 适用规则支持决策, 用户授权有效, 目标订单金额正确, 无重复退款, 告知与实际结果一致. 每题保存公开输入、知识版本、订单快照、用户身份、工具契约与评判器专用真值, 运行时不能让 Agent 看到后者. 每次试验从干净环境开始, 两个版本使用相同任务集和预算, 同时记录模型、提示词、工具和裁判版本.

把一次任务的消息、检索片段、工具参数、返回和状态变化串在同一份运行记录里 (Trace), 每一步再留下自己的操作记录 (Span). 代码检查金额、对象、授权与终态; 难以直接计算的语义支持和答案质量, 再交给按人工标准校准过的评分模型 (LLM-as-a-Judge). 先逐任务计算联合成功, 再报告各层分数与成本. 终态成功不能消除过程中的禁止副作用, 局部好分也不能补偿终态失败. 回放工具返回便于隔离 Agent 版本差异, 另设真实沙箱集成测试验证工具本身.

**递进追问与回答要点**: 如果 Agent 第二版发出了录制时没有的调用怎么办? 录制回放只适合既有调用空间, 不能编造返回维持流程. 标记回放覆盖不足, 在隔离环境补充对应状态与调用后重测; 分开报告纯回放和集成运行结果.

**易错回答与判断依据**: “固定随机种子就能完全复现”忽略远程服务与工具环境变化; “只保存最终消息”无法验证实际状态. 判断答案是否成立, 看能否还原同一任务的输入、证据、动作、结果与各自版本.

### 2. Context Precision、Context Recall 和 Faithfulness 应怎样接入?

**面试问题**: 检索结果标签为 `[1, 0, 1]`, 有两条相关片段. 怎样计算精确性, 又怎样防止把不同框架分数混用?

**考察点**: 指标对象、排序敏感性、参考事实与生成事实的不同分母、API 数据契约.

**回答结构**: 先说口径 → 举数值例子 → 解释字段和依赖 → 说明局限.

**参考答案**: 普通 Precision@3 (前三项精确率) 是 2/3. Ragas 的 Context Precision (上下文精确性) 按相关位置累积 Precision@i 再归一化, 此例为 (1 + 2/3) / 2 = 5/6, 考虑了相关项排序. Context Recall (上下文召回) 的模型版将参考答案拆成事实, 衡量这些事实能否被检索上下文支持; Faithfulness (忠实性) 则将生成答案拆成事实, 检查答案是否被实际上下文支持. 两者分母分别是参考事实和生成事实.

适配器要明确需要 `reference`、`response` 还是 `retrieved_contexts`, 以及输入是候选检索结果还是最终送给模型的上下文. 同名指标可能因事实拆分、判定提示词和阈值不同而不具可比性. 应记录实现版本和裁判配置, 在同一标注集上校准. 2026-10-18 核实的官方 Ragas 文档展示 collections API, 不应把旧教程接口与新接口混写成已运行代码. [Ragas Context Precision](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/), [Recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/), [Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/).

**递进追问与回答要点**: 若只召回一个相关片段并只回答其中事实, Faithfulness 会怎样? 可能为 1, 但其他必需事实未被覆盖; 必须检查召回、完整性与适用性. 若语料过期, 忠实性高也不表示当前答案正确.

**易错回答与判断依据**: 把三者都说成“答案准确率”, 或把 CP 恒写成相关数除 k, 都没有识别判定对象. 能明确谁被拆成事实、拿谁做证据, 才算理解.

### 3. 如何同时允许合理替代路径并限制危险动作?

**面试问题**: 一个 Agent 先查规则再查订单, 另一个顺序相反, 两者最终都完成退款. 是否应该用完整参考轨迹精确匹配?

**考察点**: 终态与过程约束的分工、局部时序、参数匹配、框架模式边界.

**回答结构**: 先确认业务必要顺序 → 选择匹配粒度 → 核验终态与副作用 → 说明实现.

**参考答案**: 如果两项查询相互独立, 不应强制唯一全局顺序. 退款前必须具有有效规则、实时订单前置条件与用户确认, 可以用必要事件的依赖关系检查, 然后核验目标订单退款一次且其他订单不变. 对没有硬顺序的查询可放宽匹配, 对写操作对象、金额和确认时点严格检查.

AgentEvals 的 `strict`、`unordered`、`subset`、`superset` 分别表达固定次序、放宽次序、不允许超出参考以及至少覆盖参考. 参数比较还要配置, 这些模式不能自动推导业务规则. τ²-bench 指定提交的文档解释: 参考 `actions` 可以用于回放生成目标数据库, 在 `reward_basis` 仅包含 DB 与 COMMUNICATE 时并不要求照抄参考路径. 因而参考解是生成真值的方法, 未必是唯一解. [AgentEvals 规范](https://docs.langchain.com/langsmith/trajectory-evals), [τ² 任务规范](https://github.com/sierra-research/tau2-bench/blob/96a3ef92329baf908ffe9dfe188cea34e8701d2a/docs/evaluation.md).

**递进追问与回答要点**: “先重复退款, 后冲回一笔, 最终余额对”是否成功? 如果契约禁止重复支付, 过程已失败, 终态无法抵消. 应检查动作事件与外部副作用, 不能只查净余额.

**易错回答与判断依据**: “所有 Agent 都用 strict”会误杀合法路径; “只看终态”会漏掉危险副作用. 正确答案须说清哪些顺序是业务必需, 哪些只是实现习惯.

### 4. 混合系统失败后怎样做组件归因?

**面试问题**: 售后规则明明存在, Agent 仍然给不符合条件的订单退款, 怎样避免盲目调检索器?

**考察点**: 分阶段证据、受控干预、参数与状态链路、因果结论边界.

**回答结构**: 找最早失效点 → 固定输入做干预 → 分层验证 → 重跑完整任务.

**参考答案**: 先检查解析语料中是否保留规则, 再看候选召回、重排、压缩和实际模型输入, 确认是否丢失关键例外条件. 将真实上下文替换成已核验充分的 Oracle Context (理想证据上下文), 其余环境保持不变并多次运行. 若改善, 证据供应是重要瓶颈; 若仍错, 固定正确证据和订单状态单测规则决策. 决策正确但执行错, 进一步查订单与金额映射、工具返回、重试和事务终态.

还要检查评判器是否把合法拒绝判成未完成, 或把旧规则当成正确规则. 一次 Oracle 替换改变了后续轨迹, 只能支持诊断, 不能单凭一次结果证明唯一根因. 修复组件后, 用原始输入重新跑完整任务及关联风险任务组, 防止组件修复未转化为整体收益.

**递进追问与回答要点**: 检索日志显示片段存在, 为什么模型仍没用? 检查它是否真的进入最终上下文, 是否被截断, 以及模型决策是否正确解释条件. 候选日志不是模型实际输入的替代证据.

**易错回答与判断依据**: “召回有关键词就说明检索没问题”没有核查充分性与实际上下文. 判断答案是否有效, 看干预有没有固定变量, 是否沿证据、决策、参数和状态逐段验证.

### 5. 四个工具怎样分工, 才不会重复执行和重复计费?

**面试问题**: 团队要求接入 EvalScope、MTEB、Ragas 和 Langfuse, 怎样把它们组成可追溯的评测流程?

**考察点**: 职责边界、组件与应用评测、数据契约、版本关联、执行入口.

**回答结构**: 先分工 → 约定输入输出 → 选执行入口 → 固定版本 → 汇总发布证据.

**参考答案**: 我会把 EvalScope 用作离线模型与性能任务入口, 通过其 MTEB 后端评检索组件, 通过 Ragas 后端评已经生成的应用回答和实际上下文. 应用自身还要运行完整任务, 用独立状态检查核实订单、金额、授权和副作用. Langfuse 记录应用运行、数据集实验和分数, 方便从报告定位到某次任务. 每个评分作业只由一个入口执行, 报告同步不能再调用一次裁判.

先统一 `case_id`、`trial_id`、运行与操作标识, 再记录数据集、知识、索引、模型、提示词、工具和裁判版本. 不依赖输出行号关联, 不用一个模型名称充当完整版本. 若选 Langfuse 实验执行应用并调用 Ragas, 就不再让 EvalScope 对同批预测重复评分. 数据集版本只冻结题目, 不会冻结外部知识库和业务环境. 接齐工具不代表自动具备发布系统, 仍要实现报告适配、必需检查和放行规则. 这是本文的教学架构, 接口能力参考 [EvalScope 后端](https://evalscope.readthedocs.io/zh-cn/latest/user_guides/backend/rageval_backend/mteb.html) 与 [Langfuse 数据集](https://langfuse.com/docs/evaluation/experiments/datasets).

**递进追问与回答要点**: 换 embedding 后 MTEB 提高了, 可以直接把新查询向量连到旧索引吗? 不能. 要核对查询/文档编码配置并重建匹配的候选索引, 检查权限过滤与真实应用. 组件成绩不证明新索引与完整系统正确.

**易错回答与判断依据**: 把四个工具串在每个用户请求里, 或宣称 MTEB 高分证明退款正确, 都混淆了阶段与判定对象. 有效回答要能说明每份报告由谁产生、对应哪个版本、怎样关联任务, 以及哪些业务检查仍由自己负责.

### 6. 在线评分为什么拿不到完整轨迹, 应怎样实现?

**面试问题**: 检索与工具调用都有记录, 但线上裁判只看见最后一句回答. 怎样让评分可信, 又不让裁判拖慢用户请求?

**考察点**: 评分作用域、异步证据聚合、迟到事件、幂等作业、未知与失败分离.

**回答结构**: 确定评分对象 → 汇齐实际证据 → 异步执行 → 处理迟到和重试 → 关联分数.

**参考答案**: 先看评分规则绑定的操作. Langfuse 当前的操作级评测不自动载入所有兄弟和子操作, 因此评完整业务时, 要在逻辑根操作显式保存所需汇总, 或由自建评分任务按运行标识取齐上下文、工具参数和独立终态. 查询候选片段不能替代实际送入模型的上下文, 某个模型调用也不能代表完整任务.

主请求执行实时权限与确认检查后继续办理, 评分器通过异步事件读取证据. 终态迟到时先等待, 到期仍不足则记不可判定并排查; 补齐后以新证据版本重评. 已有明确错单证据时直接判失败, 不让其他缺失字段掩盖它. 用运行、操作、评分器版本和证据版本组成作业去重键, 评分重试不能再跑业务写入. 线上通常没有标准答案, 可以评忠实性和可核实状态, 不能伪造参考答案计算召回. [Langfuse 评分作用域](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge), [Ragas Context Recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/).

**递进追问与回答要点**: 写分数网络超时, 是否可以直接再调用一次? 先核对作业账本和已写入分数标识, 使用已设计的去重/重试机制; 不假设 SDK 天然提供这份幂等保证. 重评时注明证据或评分器变化, 不把新分覆盖成旧版本结果.

**易错回答与判断依据**: “有 trace 就一定能评完整业务”忽略作用域; “缺终态算失败/成功”混淆证据缺口与已知结论. 看答案是否同时交代主请求、异步评分、迟到证据和作业重试的实际去向.

## 测试专家视角

### 7. 通用领域和垂直领域如何分别设计测试集?

**面试问题**: 同时评一个通用研究助手和一个金融文档问答系统, 能否共享同一套准确率与数据集?

**考察点**: 覆盖维度、真值粒度、领域风险、数据泄漏和分组报告.

**回答结构**: 共享测量骨架 → 区分覆盖与领域判据 → 数据构造 → 解释结果边界.

**参考答案**: 可以共享任务、运行、证据、判定和报告结构, 但不能只用同一数据集和一个均值. 通用研究助手要覆盖主题、长尾实体、语言、文件类型、工具组合、多步骤与开放问题, 检查事实和来源质量以及任务完成. 金融文档问答要额外固定公司、财年、币种、单位、报表列和计算口径, 构造相邻年份、同名实体、表格脚注和单位混淆反例.

FinanceBench 的已核实首题要求 3M 2018 财年资本支出, 参考值 1577 百万美元; 把单位改成十亿美元不能因文本很像就通过. 这是公开数据参考值, 并非本次独立审计年报. CRAG 适合广泛事实问答, GAIA 面向通用助手, 都不直接代表企业私有分布. 数据按文档、实体、时间或任务族划分, 近似改写不能跨调优与留出集泄漏. 分别报告宏平均、流量权重结果与关键任务组, 高代价错误单列. [FinanceBench 样本](https://github.com/patronus-ai/financebench/blob/cc39aeb4afdf33909ee1412188bf89035950c2eb/data/financebench_open_source.jsonl), [CRAG](https://arxiv.org/abs/2406.04744), [GAIA](https://arxiv.org/abs/2311.12983).

**递进追问与回答要点**: 没有真实用户日志怎么办? 由领域专家写任务与反例, 合成题扩充覆盖并独立复核, 明确代表性限制; 上线后用脱敏真实失败补充, 不把合成分布冒充真实分布.

**易错回答与判断依据**: “垂直题就是通用题加行业名词”遗漏领域计量与规则真值. 能写出同一事实在时间、单位和权限上的具体反例, 才能证明覆盖有实质内容.

### 8. 回答和引用都正确, 但办错订单, 怎样判定并定位?

**面试问题**: Agent 正确解释了政策, 对用户说 O-1 已退款, 实际工具操作的是 O-2. 自动评测怎样发现?

**考察点**: 独立状态真值、业务参数语义、局部通过与整体失败、证据完整性.

**回答结构**: 先给整体结论 → 列必要证据 → 各层判定 → 指明修复验收.

**参考答案**: 整体失败. RAG 的依据性与引用可以通过, 但参数与终态必须失败, 最终告知也与事实不符. 将用户身份、目标订单、工具参数、工具返回及订单库前后差异用同一运行标识关联, 检查目标订单的退款金额和其他订单不应变化的状态. JSON Schema (结构化数据约束) 合法、API 返回成功只说明请求可执行, 不证明操作对象符合用户目标.

原合成练习中的 `wrong-order` 就验证该场景: 证据覆盖通过, 参数和状态失败. 修复后用同一任务重测, 要看到 O-1 正确退款、O-2 未变化, 同时检查会话中途切换订单和重复执行的关联用例. 如果没有终态日志, 应说明无法证明完成, 并记录判定覆盖缺口. 已有明确违规证据时可判失败, 不因为另一个字段缺失就掩盖已知问题.

**递进追问与回答要点**: 工具写入成功但返回超时, 测试如何检查重试? 注入“状态已改变、响应丢失”的故障, 检查是否查询结果或正确使用业务幂等机制, 最后核实外部副作用一次发生, 而非只看最终一句话.

**易错回答与判断依据**: “工具成功所以任务完成”混淆技术执行与业务成功. 有效答案必须包含目标对象、实际动作和独立终态三方比对.

### 9. 怎样确认大模型裁判值得信任?

**面试问题**: 自动裁判判 90% 通过, 专家发现不少错误单位和缺失条件, 应如何排查?

**考察点**: 标注规范、难例、混淆矩阵、证据隔离、裁判漂移.

**回答结构**: 冻结评分项 → 专家独立标注 → 测裁判错误 → 校准并重测.

**参考答案**: 先把“正确”拆成事实、单位、条件完整、引用和状态等可独立判项, 准备包含边界反例的人工金标准. 至少对争议样本进行独立专家标注与裁决, 检查专家本身是否一致. 再计算裁判对各项的混淆矩阵; 若以“有害错误”为正类, FN (假阴性) 就是漏报错误, 漏报率为 FN/(TP+FN). 总体一致率可能被大量简单正确样本抬高, 必须看高风险任务组.

对数字与单位采用确定性规则, 对语义支持关系使用明确 Rubric (评分细则), 要求返回证据定位与不确定原因. 被评答案与检索文档视为数据, 防止其中指令改变裁判任务. 比较答案时随机顺序、隐藏版本名, 用交换顺序复查偏好. 裁判提示词或模型更换后重新校准, 新旧分数注明测量系统变化. 多裁判一致仍可能共享偏差, 不替代专家难例. [判定器类型与校准边界](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

**递进追问与回答要点**: 专家也不同意怎么办? 先检查任务是否歧义、规则是否缺适用条件, 不能直接用投票掩盖无法定义的真值. 修订标注规范并保留争议记录, 将确实不可判定项单列.

**易错回答与判断依据**: “换最强模型就可信”没有给出误判证据; “一致率 95% 足够”没有说明类别分布. 判断应落在具体评分项、错误类型与人工对照.

### 10. 怎么报告重复试验和版本改进才不误导?

**面试问题**: 每题运行 5 次, 版本 A 有时成功, 版本 B 更稳定. 怎么选择指标并处理缺失日志?

**考察点**: 随机性、任务级样本、pass@k 与 pass^k、覆盖率、统计不确定性.

**回答结构**: 业务目标决定指标 → 逐题统计 → 处理未知与费用 → 配对比较.

**参考答案**: pass@k (k 次至少一次成功) 适合允许多候选择优的目标; pass^k (k 次全部成功) 更能体现每次都要可靠的服务目标. 在同题独立同概率的简化模型下, 两者是 1 − (1 − p)ᵏ 与 pᵏ, 实际按每题 n 次 c 次成功用组合估计再平均, 不对整体均值直接取幂. 每次运行都重置业务状态, 固定模拟用户和预算, 另列工具或环境异常.

两个版本使用同批任务配对比较, 重采样按任务分组而非把同题 5 次当 5 道新题. 报告分组变化与不确定性, 不只看总分. 缺失关键证据进入 unknown (不可判定), 同时报告所有计划试验中的已知成功比例、可判定样本条件成功率和判定覆盖率. 练习中 2 成功、4 失败、1 未知, 分别是 2/7、2/6、6/7, [2/7,3/7] 是未知取不同结果的识别区间, 并非统计置信区间. 失败和重试成本都要进入总成本. [非确定性指标说明](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [τ-bench 原论文](https://arxiv.org/abs/2406.12045).

**递进追问与回答要点**: 新版本总分提高 2 个百分点能否上线? 还需样本量、差异不确定性、关键任务组退化、硬约束、裁判变更和预算变化证据. 没有统一 2 个百分点即有效的规则.

**易错回答与判断依据**: 混写 `pass@k` 与 `pass^k`, 删除失败运行或未知记录, 把所有 trial 当独立任务, 都会造成结论偏差. 正确答案应给出指标对象、分母与适用假设.

### 11. 怎样证明失败回流没有污染回归集与留出集?

**面试问题**: 线上低分与用户差评每天自动导入数据集, 团队说数据飞轮已经完成. 测试应该检查什么?

**考察点**: 失败信号和真值的区别、审核准入、隐私与用途隔离、近似重复、回归修复验证.

**回答结构**: 检查候选来源 → 验证证据和审核 → 检查用途与划分 → 验证回归和复发.

**参考答案**: 低分或差评只能生成调查候选. 我会检查同一事件重试是否被合并, 数据是否允许处理, 规则和终态是否齐全, 审核者是否独立确认系统失败. 对裁判误报保留驳回原因, 对歧义任务保留待决, 不强制生成一个标准答案. 获准样本应包含公开输入、独立参考、预期状态、初始环境和来源标识, 不能拿模型旧答案当真值.

再按任务族、实体、时间或来源查近似重复和跨用途泄漏. 受保护留出任务族不自动流入调优或训练, 已经暴露并用来修复的题也不能继续称为未见题. 回归集需要相邻反例与正常样本, 否则新版本一律拒绝也可能看起来更好. 最后验证失败题和关联任务在同一环境下通过, 并在发布后按暴露量监测同类失败复发; 入库数量不能替代修复结果. [数据集准入与版本承载](https://langfuse.com/docs/evaluation/experiments/datasets); 审核规则与数据用途划分是本文教学设计.

**递进追问与回答要点**: 对线上告警人工审核后 90% 确实失败, 能说失败召回率 90% 吗? 不能, 这是已审核告警中的精确率. 漏报需要独立随机样本中的人工真值, 还要说明抽样与类别分布. 风险样本过采样后的平均数不能直接代表全流量.

**易错回答与判断依据**: “低分自动变金标准”“每道题换个问法就能放留出集”“回流越多越好”都缺少质量和隔离依据. 应能给出去重、受限、证据不足、待审核、驳回、受保护和准入各分支的可检查结果.

拿一条“回答看似正确但操作错订单”的反馈走图: 独立业务证据确认后批准, 再决定用途. 如果它属于留出任务族, 不能沿着“已经确认失败”就直接进入调优回归集. 修复后继续监测复发, 才完成闭环.

### 12. 文本指标提高但业务结果变差, 发布流程怎样拦住?

**面试问题**: 新版 Ragas 与 MTEB 报告通过, 但状态检查失败; 另一个版本离线全通过, 线上终态还没成熟. 应分别怎么判?

**考察点**: 必需检查、硬约束、未知处理、分阶段放行、延迟结果与回滚.

**回答结构**: 按阶段给结论 → 列证据 → 定义阻断/观察/晋级 → 解释不能外推的边界.

**参考答案**: 第一个版本阻断, 文本与检索分数不能抵消错单、金额或授权问题. 所有必需检查保留自己的结果, 先看已知失败, 无失败但缺报告则补测. 第二个版本最多取得小流量试运行资格; 在线终态未成熟时继续等待并报告成熟度, 不能提前宣称任务成功或业务改进.

发布前约定关键任务组、质量差异、覆盖率、性能预算和回滚条件, 不套用一个通用 0.8 阈值. 小流量按会话或租户稳定分组, 同时看观测覆盖和评分积压, 因为“没有告警”也可能是没有记录. 有明确退化按规则回滚, 保留失败证据回到修复. EvalScope 模型服务压测不替代整条应用的检索、工具、排队和重试延迟. 业务写入副作用不会随应用回滚自动撤销, 影子运行不能重复执行真实退款. [EvalScope 性能测试范围](https://evalscope.readthedocs.io/en/latest/user_guides/stress_test/quick_start.html); 发布规则为本文教学设计.

**递进追问与回答要点**: 只修参数映射, 是否必须重跑全部 MTEB? 先检查依赖版本和覆盖范围. 未变组件的有效报告可复用, 但必须重跑受影响的工具、端到端任务和相邻风险题. 复用要有对应版本证据, 不能把“应该没关系”当作报告.

**易错回答与判断依据**: “平均分提高就发布”“离线过了线上一定过”“缺日志就是没出错”都把不同阶段混成一个结论. 应能指出哪个阶段取得了什么资格, 哪些结果已失败或仍未知, 以及下一步需要什么证据.

## 快速实操验收
