## 开发专家视角

### 给 Agent 一组问题和标准答案, 为什么还不算完整 benchmark?

**考察点**: 任务契约、环境状态、轨迹与业务结果.

**回答结构**: 先给反例 → 列固定条件 → 说明运行和取证.

**参考答案**: 同一句“查昨天的发货量”, 在不同时钟和账号下可能应查询不同日期、看到不同客户. 所以除了输入和参考答案, 还要固定时区、账号权限、初始数据、工具返回脚本、允许动作和结束条件. 对一次业务派发的 Agent, 我要保存真实工具名称、参数、派发次数和结果, 再核对回答与业务状态. 回答正确但查错客户, 仍不能算任务完成. 预期与标注留在评测侧, 不直接塞给被测模型.

**递进追问**: 检查数据库的评分器查询也算 Agent 第二次工具调用吗?

不算, 前提是它属于独立评测取证, 不将结果回传给 Agent 帮它完成任务. 必须用执行者标识区分被测行动和裁判取证. 如果取证结果参与了被测决策, 就改变了测试条件.

**易错回答与判断依据**: 只保存最终文本, 无法证明实际动作正确. 要求模型透露隐藏推理也不能代替执行器轨迹.

## 测试专家视角

### 怎样划分开发集和冻结集, 避免分数看起来虚高?

**考察点**: 风险覆盖、近义泄漏、版本与标注质量.

**回答结构**: 风险分组 → 家族切分 → 复核规则 → 冻结与更新.

**参考答案**: 教学规划可用 120 条任务, 开发集 80 条、冻结集 40 条, 覆盖查询、录入、澄清、拒绝和故障处理. 数量不是通用标准, 先确保关键风险有代表. “昨天发了多少”和“昨日发货数量”属于同一语义家族, 只换客户代号的模板副本也应整体分到一侧. 我在开发集调整提示词, 冻结任务、环境和评分规则后再比较版本. 标注意见不一时先核对产品契约, 不用模型投票来发明成功标准.

**递进追问**: 冻结集发现了缺陷, 修复后还能再跑吗?

可以作回归检查, 但若已根据这些具体问题调试, 它就参与了开发. 继续宣称独立泛化能力需要新的保留任务. 保留旧集仍有价值, 只是报告要写清用途.

**易错回答与判断依据**: 随机按句子切分可能把几乎相同的问题分到两侧. 声称已执行 120 条任务也不成立, 这里提供的是规模设计和局部 demo.

### 40 条任务每条跑三次, 98 次通过, 怎么报告?

**考察点**: 任务与尝试分母、未知项和重复稳定性.

**回答结构**: 先核对总数 → 披露未知 → 分开尝试和任务指标.

**参考答案**: 共计划 120 次尝试, 合成快照有 98 次通过、18 次明确失败、4 次证据不足. 按计划的确认通过比例为 81.67%, 未知占 3.33%; 只看可判定尝试是 98/116=84.48%, 必须同时披露排除项. 若 28 条三次全过, 6 条两次过, 2 条一次过, 4 条零次过, 则至少一次通过是 36/40=90%, 三次全过是 28/40=70%. 不能把前者说成单次请求成功率.

**递进追问**: 三次都通过, 能说明系统完全稳定吗?

只能说明这三次在给定条件下通过, 有限重复不能证明真实成功概率为 100%. 还需关注样本代表性、系统版本和裁判波动. 每次恢复账号、数据和替身脚本, 否则看到的差异可能是状态污染.

**易错回答与判断依据**: 丢掉未知样本却不披露, 或只挑最好一次, 都会夸大结果. 已有可靠失败证据时不能用其他日志缺失把失败改为未知.

## 术语与依据

| 英文名称与缩写 | 中文含义 | 本篇具体作用 |
| --- | --- | --- |
| Benchmark / Task | 任务集 / 任务 | 固定比较对象 |
| Trial | 一次尝试 | 同一任务的独立运行 |
| Fixture / Holdout | 初始条件 / 保留集 | 控制起点与独立比较 |
