# EvalScope 架构面试: 开发与测试双视角

配套学习文章: [EvalScope 架构详解](../../learning/ai-evaluation/evalscope-architecture.md).

本专题对应官方源码提交 [`3ff0a0c`](https://github.com/modelscope/evalscope/tree/3ff0a0c425cc89cec91a5d48141e22a61ce53a9b), 源码核查与框架运行日期 2026-10-19, 文档整理与评分变体验收日期 2026-10-20. 该源码声明 `0.0.0_dev`, 不应与任意发行版本混用.

案例全部是光模块维护的教学模拟. 已执行实验使用真实 EvalScope 与固定回答模型, 覆盖注册、加载、推理接口、规则评分、报告和缓存. 没有真实模型能力结果、生产设备操作、完整检索或智能体流程实测. 以下是技术参考答案, 不代表个人生产经历, 也不声称真实面试一定出现这些问题.

阅读时可以先口头作答, 再对照每题参考答案. 重点不是记住类名, 而是能讲清“谁负责什么、需要哪些证据、为什么得到这个结论”.

## 开发专家视角

### 1. 从 `run_task` 开始, 一条维护工单怎样走到最终报告?

**面试问题**: 配置里只有任务名称和模型信息, 框架怎样完成装配? 评测器和任务适配器各负责什么?

**考察点**: 是否理解装配、执行调度、领域逻辑和模型访问的分工, 能否说清数据形态的变化.

**回答结构**: 配置与分流 → 按名称装配 → 样本执行 → 评分与持久化 → 聚合和报告.

**参考答案**: `run_task` 先解析任务配置 `TaskConfig`, `run_single_task` 准备输出目录并按后端分流. 原生路径会创建延迟初始化的模型对象 `LazyModel`, 按 `datasets` 中的名称找到任务元数据 `BenchmarkMeta`, 构造领域适配器 `DataAdapter` 和评测调度器 `Evaluator`, 检查配置后逐个执行评测器.

以低接收功率工单为例, 适配器先把原始记录变成样本 `Sample`: 告警与手册片段进入输入, 参考诊断和支持引用保留在评测侧. 评测器安排样本执行, 调用适配器的 `run_inference`; 默认单轮路径通过统一模型层请求具体模型接口 `ModelAPI`, 得到 `ModelOutput`, 再包装成运行记录 `TaskState`.

评测器先保存预测, 然后让适配器计算指标. 单题分数 `Score` 带有各维度值, 再包装成 `SampleScore`; 每个子集完成后聚合成 `AggScore`, 最后生成报告 `Report`. 评测器知道如何安排和保存, 适配器知道这张维护工单怎样判对错, 模型接口负责与具体被测系统通信.

**递进追问与回答要点**: 一条题的评分依赖多条预测怎么办? 不能硬套普通单题路径. 本提交支持 `use_batch_scoring`, 这类任务会推迟评分, 由 `BatchReviewer` 在后续阶段组织处理. 回答时必须说明这是适配器声明的执行差异.

**易错回答与判断依据**: “适配器只读数据, 评测器负责所有判分”不成立, 因为 `DataAdapter` 契约包含推理、指标、聚合和报告. “所有样本都先全部预测, 再全部评分”也不符合本提交默认单题工作项路径. 判断依据是实际方法调用, 不能只凭类名猜职责.

### 2. 增加光模块维护任务, 最少需要扩展哪些位置?

**面试问题**: 已有工单 JSONL 和一个标准聊天服务, 要检查诊断、动作、引用版本, 是否需要重写评测器?

**考察点**: 扩展边界、真实接口契约、注册时机、主指标与指标语义.

**回答结构**: 复用调度 → 注册领域适配器 → 转换样本 → 返回结构化分数 → 声明报告语义 → 接模型服务.

**参考答案**: 普通单轮场景通常不需要重写评测器. 继承 `DefaultDataAdapter`, 用 `record_to_sample` 将业务输入、参考答案和评分元数据分开, 用 `match_score` 产生领域指标. 如果读取普通本地 JSONL, 要确认使用本地加载器. 注册元数据约定任务名称、子集、模板、指标和评测语义版本. 自定义模块必须先被导入, 注册装饰器才会执行.

已有标准聊天服务可选择相应模型调用类型, 比如 `eval_type="openai_api"`; 协议私有时才实现自己的 `ModelAPI`. 这与选择哪个框架执行的 `eval_backend`, 以及用规则还是模型判分的 `judge.strategy`, 是三个不同的配置维度.

本案例在 `Score.value` 中保留诊断、动作、安全、引用等维度, 并以全部满足的 `joint_pass` 作为主要质量指标. 单题的 `main_score_name` 和报告的 `primary_metric` 不是同一层设置. 本提交还需要让报告知道自定义指标的含义, 即指标语义: 越高越好、范围 0 到 1、显示时乘 100 为百分比. 完整实验通过报告生成钩子显式声明, 没有修改框架全局目录.

以下为已执行代码的核心节选, 非完整脚本:

```python
def match_score(self, original_prediction, filtered_prediction,
                reference, task_state):
    values = score_response(filtered_prediction, reference, task_state.metadata)
    return Score(
        value=values,
        prediction=original_prediction,
        extracted_prediction=filtered_prediction,
        main_score_name="joint_pass",
    )
```

**递进追问与回答要点**: 只把 `joint_pass` 放进 `metric_list` 就能当报告主指标吗? 本提交中还需选择准确指标身份, 并声明质量语义. 未声明的新名字会被默认解释为诊断项, 诊断项不能当主要质量分. 计算逻辑的注册与报告语义的声明是两件事.

**易错回答与判断依据**: “只返回 0.8 就行”会丢失多维判断、原始回答、状态和指标身份. “装饰器写上就一定生效”忽略了模块是否导入. 判断方法是看执行时注册表是否有该名字, 检查逐题结果和报告中主指标是否正确.

来源: [`DataAdapter`](https://github.com/modelscope/evalscope/blob/3ff0a0c425cc89cec91a5d48141e22a61ce53a9b/evalscope/api/benchmark/benchmark.py), [注册表](https://github.com/modelscope/evalscope/blob/3ff0a0c425cc89cec91a5d48141e22a61ce53a9b/evalscope/api/registry.py), [报告语义解析](https://github.com/modelscope/evalscope/blob/3ff0a0c425cc89cec91a5d48141e22a61ce53a9b/evalscope/report/generator.py).

### 3. 评分规则改了, 如何复用旧预测? 哪些情况不能这样做?

**面试问题**: 发现引用版本判分写错了, 已有一批模型回答. 如何重评分, 如何证明没有重新调用模型?

**考察点**: 预测缓存与评分缓存的分离、运行身份、重新评分的适用条件与观测证据.

**回答结构**: 说明缓存分层 → 检查身份 → 显式重新评分 → 验证调用数量与结果 → 说明不能复用的变化.

**参考答案**: `use_cache` 指向以前的输出目录. 预测和评分都可复用时, 普通恢复会直接使用旧结果; 只有预测时, 重新评分而不重新推理. 设置 `rerun_review=True` 则要求复用预测、重算评分. 原生任务会先检查评测语义版本和运行身份指纹, 普通恢复要求匹配; 显式重评分可以覆盖不匹配并记录来源.

因为这里只修正“旧手册引用该怎样判”, 被测输入和回答没有变化, 可以复用答案. 验证时不只看报告分数, 还要看被测模型调用数、预测缓存和本轮评分记录. 本文固定回答实验首跑 6 次, 普通恢复与强制重新评分均为 0 次调用. `LazyModel` 延迟创建真实模型对象, 可以在无需新预测时避免初始化被测模型, 但模型裁判仍可能因重评分而被调用.

如果实际工单输入、模型权重、系统提示、知识库内容或工具环境变了, 旧预测就不一定代表新系统. 即使技术上能强制复用, 也不能据此声称测试了变化后的行为. 指纹只覆盖明确记录的配置, 不能自动证明外部手册或线上别名背后的模型没变.

**递进追问与回答要点**: 参考答案变了是否一定重新推理? 要看变化是否只在评分侧. 纯粹修正错误标注可重评分; 若参考答案变化反映了业务条件或输入事实变更, 要先核对旧预测是否仍回答同一道题. 不能只按“字段名是不是 target”机械判断.

**易错回答与判断依据**: “目录有缓存就复用”忽略身份和语义. “温度设 0 就完全可复现”忽略模型、数据、检索和环境版本. 判断依据应包含配置快照、输入版本、原始预测和实际调用记录.

来源: [缓存身份机制](https://github.com/modelscope/evalscope/blob/3ff0a0c425cc89cec91a5d48141e22a61ce53a9b/evalscope/evaluation_versioning.py), [`LazyModel`](https://github.com/modelscope/evalscope/blob/3ff0a0c425cc89cec91a5d48141e22a61ce53a9b/evalscope/api/model/lazy_model.py).

### 4. 从“回答维护问题”扩展为“执行维护流程”, 需要增加哪些证据?

**面试问题**: 模型会输出 `next_action="inspect_path"`, 能否说已完成维护智能体评测? 如果还会检索手册, 怎样区分检索错和动作错?

**考察点**: 静态问答、检索增强生成与智能体流程的边界, 轨迹与环境状态的作用.

**回答结构**: 先划评测对象 → 检索增加依据 → 工具增加轨迹 → 状态验收 → 对应框架路径.

**参考答案**: 输出一个动作字段, 证明的是“建议了什么”, 没证明“执行了什么”. 静态问答只需输入和答案; 先检索资料再生成的系统称为检索增强生成 (RAG), 还要保存真实检索片段、手册型号和版本; 能连续选择工具、读取观察并继续行动的系统称为智能体 (Agent), 还要记录实际工具参数、返回、步骤、终止原因和环境状态.

例如工单要求端口 1, 助手实际查了端口 2. 最终诊断可能碰巧正确, 但维护流程仍有错误. 又如检索拿到旧手册, 答案忠实复述旧资料, 也不能据此判断当前业务正确. 必须分别看“找到了什么”“是否照着证据回答”“工具是否作用于正确对象”“最后是否复测”.

源码中的 `AgentLoop` 驱动生成、解析和工具执行, 策略解释动作, 环境负责执行并回传观察. 领域工具和状态判定仍需实现. RAGAS 的接入可通过第三方 RAGEval 路径评估既有检索生成记录; 它不会因为你传入数据文件就自动搭建业务检索器. 两条路径不能不加说明地套用同一个执行器.

**递进追问与回答要点**: 工具参数满足结构约束, 是否可以判任务成功? 结构合法仅说明字段形状符合要求, 仍要检查设备、端口、时间、手册版本、动作顺序与复核结果. 工具调用能力和业务任务完成是不同层次.

**易错回答与判断依据**: “最终回答对就全通过”无法发现过程与状态错误. “用了 RAGAS 就自动评了所有维护风险”没有业务依据. 判断时要求对方举出一条工具调用和一份最终状态证据, 并说明各自的评分方法.

来源: [`AgentLoop`](https://github.com/modelscope/evalscope/blob/3ff0a0c425cc89cec91a5d48141e22a61ce53a9b/evalscope/api/agent/loop.py), [RAGAS 接入](https://github.com/modelscope/evalscope/blob/3ff0a0c425cc89cec91a5d48141e22a61ce53a9b/docs/zh/user_guides/backend/rageval_backend/ragas.md).

### 5. `eval_batch_size=4` 是否说明服务永远只收到 4 个请求?

**面试问题**: 配置了多个子集和多个数据集, 怎样解释并发边界? 如何与性能压测区别开?

**考察点**: 任务调度层次、样本与请求的区别、压测负载模型.

**回答结构**: 原生工作池范围 → 模型提供者差异 → 多步请求 → 独立压测路径.

**参考答案**: 本提交默认原生评测把同一个基准的多个子集样本放进统一工作池, 用 `eval_batch_size` 作为线程池最大工作数. 这是样本执行层面的并发. 在默认入口里, 多个评测器仍按循环逐个执行, 不等于所有基准一起并行.

一个样本可能一次请求就完成, 也可能内部执行多轮工具和模型调用. 具体模型提供者还可能处理本地批量或其他并发. 因而不能把 4 个样本直接等同于全系统永远 4 个底层请求, 也不能一律理解为 GPU 一批恰好推理 4 条.

性能压测走独立 `perf` 路径. 闭环负载限制同时在途请求, 完成后补入; 开环负载按计划时间产生请求, 不等待前面的请求结束. 两者模拟不同到达过程. 本提交压测中请求产生任务和统计任务通过异步队列协作, 不是调用领域适配器来计算维护诊断分.

**递进追问与回答要点**: 服务变慢后, 闭环结果为什么可能掩盖告警持续到达的压力? 固定并发会因为请求变慢而降低新请求发出速度, 而真实告警到达不一定受响应速度约束. 应先说明要模拟哪一种负载, 再解释结果, 不能只比较一个吞吐数字.

**易错回答与判断依据**: “把质量评测并发调大就是完整容量压测”忽略到达过程、持续时长、错误和输入长度. 判断依据是请求实际发送时间、在途数量和统计窗口, 不是只看参数名.

来源: [`_run_pool`](https://github.com/modelscope/evalscope/blob/3ff0a0c425cc89cec91a5d48141e22a61ce53a9b/evalscope/evaluator/evaluator.py#L314-L360), [压测流水线](https://github.com/modelscope/evalscope/blob/3ff0a0c425cc89cec91a5d48141e22a61ce53a9b/evalscope/perf/core/pipeline.py).

## 测试专家视角

### 6. 怎样设计一组能暴露错误归因的维护工单?

**面试问题**: 只准备低功率、过温等典型正例够不够? 怎样让模型不能靠关键词猜答案?

**考察点**: 数据覆盖、条件反例、未知状态、型号与版本约束、标注独立性.

**回答结构**: 列业务判断 → 设置控制条件 → 准备相似反例 → 明确未知与验收 → 保留依据.

**参考答案**: 不够. 要围绕实际需要做的判断安排数据. 低接收功率可能来自对端发射、连接器、光路或本端接收等不同原因, 不能让所有低 Rx 样本都标为本端模块坏. 应固定部分观测, 改变是否已有对端数据、是否排除光路等条件, 看下一步是否随证据改变.

本次六条模拟题包括低 Rx 先查路径、多邻口过温先查散热、Tx 与偏置趋势异常后升级复测、新模块兼容性核对、信息不足时补采, 以及 DOM 当前正常但误码增加时继续定位. 后两条专门防止模型强行诊断或草率关单. 每条保存允许的下一步和人工支持引用, 不把“是否用了某个关键词”当正确性.

真实数据应包含型号、端口、时间、测量单位、手册版本等必要条件. 同一设备系列的相似工单不能随意分到训练和测试两边后就认为没有泄漏; 要按业务相关性划分并记录依据. 本文模拟固定回答模型直接按工单编号返回答案, 只能测管道, 不能用来证明泛化能力.

**递进追问与回答要点**: 只有一个 DOM 快照, 能否标为激光器老化? 不应越过证据. 可将答案标为发射侧可疑并要求复测, 具体失效机理需要更多观测或测试. 题目阈值必须来自对应型号条件, 不能把示例的 -13 dBm 当所有模块的统一标准.

**易错回答与判断依据**: “每种告警各一条就覆盖完”缺少相似条件反例与未知状态. “参考答案是专家写的所以无需审查”忽略版本和标注分歧. 判断依据是改变一个关键条件后, 期望决策是否有明确、可解释的变化.

来源: [学习文档的模拟数据与证据边界](../../learning/ai-evaluation/evalscope-architecture.md#_11-把架构接到光模块维护业务上), [Cisco 排障依据](https://www.cisco.com/c/en/us/support/docs/switches/catalyst-9200-switch-stack/222738-troubleshoot-fiber-links-on-catalyst-900.pdf).

### 7. 回答引用了真手册, 为什么还可能不通过?

**面试问题**: `OM-003` 诊断与动作都对, 但引用旧版手册. 怎样判分? 能否把各维度平均后宣布通过?

**考察点**: 多维证据、必要条件、正确性与安全性的关系、评分器的负例验证.

**回答结构**: 明确业务必须条件 → 分别判分 → 联合通过 → 解释规则边界 → 用变体验证.

**参考答案**: 如果当前任务要求依据适用版本的手册, 旧引用就不能通过证据检查. 仍应保留诊断、动作等正确项, 让结果说明它到底错在哪. 本实验的 `OM-003` 是结构、诊断、动作、安全均为 1, 证据为 0, 所以联合通过为 0.

这不是框架规定所有业务都必须这样判, 而是本例明确的验收规则. 对必须同时满足的条件取平均, 会让“一个关键条件失败”被其他高分抵消. 更好的解释是报告各项, 主指标记录是否全部满足. 安全动作也不等于有效动作: 查错方向但不改状态可以很安全, 却不满足本题下一步要求.

先走结构不合格出口, 结果全为 0; 再走结构合格分支, 四个业务维度独立检查. 这两条路径分别检验格式约束和业务约束, 不能只测一条“全部正确”的路径.

引用检查还要限定能力: 本例判断引用是否属于人工标注的支持集合, 不是只检查文档存在; 也不独立证明整段自由文本每句话都能被手册支持. 完整自然语言忠实性需要更细标注或经过校准的判定.

**递进追问与回答要点**: 怎样证明评分器能抓住此错, 而非刚好返回 0? 只改引用版本, 预期仅 `evidence_valid` 和 `joint_pass` 变化; 保持引用正确、改诊断, 应仅诊断相关项及联合通过变化. `verify.py` 已执行这类业务变体和格式变体, 而非只重复正常路径.

**易错回答与判断依据**: “文档 ID 存在就算有依据”会接受无关手册. “安全 90% 就一定可上线”没有预先约定的业务门槛. 判断依据应是逐题规则、独立负例和明确分母, 不能靠一个平均分代替.

### 8. 100 条题只判出 80 条, 其中 72 条正确, 应该报什么?

**面试问题**: 裁判返回无法解析内容、被测模型输出错误结构、请求执行失败, 应不应该都记成 0?

**考察点**: 无效判分与能力错误的区别、覆盖率、执行完整性和不确定状态.

**回答结构**: 分清失败角色 → 定义各指标分母 → 报覆盖与执行状态 → 找原因并重评.

**参考答案**: 应先分清是谁没做好. 被测系统按要求输出 JSON 却给了错误结构, 可以按本任务规则记格式失败. 裁判自己返回不可解析内容, 说明没有形成有效判断, 不能无声地说被测系统答错. 网络请求失败则属于执行问题, 也不能与诊断错误混成同一个原因.

在给定数字下, 有效判定准确率为 72/80=90%, 判分覆盖率为 80/100=80%. 如果业务另定义按全部请求计算的有效正确产出, 是 72/100=72%. 要同时说明这些口径和缺失原因, 不能只拿 90% 宣布完成 100 条评测.

本提交 `Score` 带可用性状态, 裁判摘要记录有效观察与失败; 执行摘要另记录 requested、succeeded、errored 和 incomplete. 指标有效数量不一定等于整个任务样本量. 某个合法策略是否保留规则分, 要按适配器声明解释, 不能把所有失败机械变成同一个 0.

**递进追问与回答要点**: 开启 `ignore_errors` 后能否忽略这 20 条? 该选项只是允许其他样本继续, 不会让评测变完整. 应列明失败范围, 保留已完成预测, 修复后恢复或重评分, 再看覆盖与执行状态是否达到预期.

**易错回答与判断依据**: “失败一律 0, 最保守”会混淆评测设施与被测能力. “失败都剔除, 其余均值就是真实质量”会隐藏选择偏差. 判断依据是能否从逐题记录辨识错误角色, 并明确每个分母为什么成立.

来源: [`Score` 与裁判摘要](https://github.com/modelscope/evalscope/blob/3ff0a0c425cc89cec91a5d48141e22a61ce53a9b/evalscope/api/metric/scorer.py), [执行完整性](https://github.com/modelscope/evalscope/blob/3ff0a0c425cc89cec91a5d48141e22a61ce53a9b/evalscope/evaluator/execution_tracker.py).

### 9. 同一轮报告出现 83.3% 和 87.5%, 如何验证而不是直接报缺陷?

**面试问题**: 诊断子集 4 题过 3 题, 边界子集 2 题全过. 总分应该是多少? `limit=3` 又会怎样影响运行数量?

**考察点**: 聚合层次、样本权重、有效数量、子集限制与报告口径.

**回答结构**: 先算原始计数 → 分别算样本加权与子集等权 → 对照报告层次 → 核对限制与缺失.

**参考答案**: 六条题总共通过五条, 按样本计是 5/6≈83.3%. 如果两个子集等权, 则 (3/4+2/2)/2=87.5%. 两者衡量不同的加权方式, 先核对报告对应字段与业务定义, 不应看到不同数值就直接判缺陷.

本提交 `Category.score` 按子集样本数加权, `Category.macro_score` 对子集等权. `Metric` 还会对分类再做一层汇总. 默认只有一个分类时, 指标层宏平均不一定等于子集宏平均. 应从原始子集数量和分数向上重算, 不只看字段里有 `macro` 就认定含义相同.

`limit=3` 在这个原生路径按子集起作用, 诊断最多三条, 边界本来只有两条, 所以最多五条. 报告应说明实际选入多少、成功执行多少、指标有效多少. 把“总数必须是三”当验收标准会误报.

**递进追问与回答要点**: 高风险子集只有两条, 是否应该被大子集淹没? 需要事先定义业务口径, 可以单列高风险类的验收条件或约定权重. 测试负责验证约定实现一致, 不能事后挑一个看起来更好的分数当总指标.

**易错回答与判断依据**: “所有均值都是分数相加除以子集个数”忽略样本权重. “Num 是输入行数”忽略重复、过滤、执行失败与指标不可用. 判断依据是可回算的原始计数及对应层次.

来源: [报告聚合模型](https://github.com/modelscope/evalscope/blob/3ff0a0c425cc89cec91a5d48141e22a61ce53a9b/evalscope/report/report.py#L180-L235), [样本与限制](https://github.com/modelscope/evalscope/blob/3ff0a0c425cc89cec91a5d48141e22a61ce53a9b/evalscope/evaluator/evaluator.py#L173-L194).

### 10. 模型首字很快, 是否说明整张维护工单处理很快?

**面试问题**: 模型接口首输出时延很好, 但工程师仍要等很久. 怎样组织性能验证并定位?

**考察点**: 单请求与多步任务的区别, 流式指标、负载形态、输入长度与完整性.

**回答结构**: 定义业务计时点 → 分段记录 → 设计业务输入与负载 → 联合看时延、吞吐和错误.

**参考答案**: 不能直接等同. 首输出时延 TTFT 是请求发出后到第一个可观测输出片段的时间, 它不包括所有检索、工单读取、多轮工具与复核. 业务任务时延应从工单进入到获得有效结论或完成验收计算, 再把检索、模型各轮请求和工具等待分别记录.

性能样本要包含短告警、带长手册、带历史监测、多轮维护等实际形态. 负载选择要对应告警到达还是固定工程师交互; 同时看时延分布、成功率、错误和吞吐统计窗口. 不能用随机短文本的接口结果直接宣布整个维护系统容量.

后续每个输出单位平均耗时 TPOT 要在有后续解码阶段时才有意义. token 是模型文本单位, 不等于字数; 流片段也不一定一个片段就是一个 token. 单个 token 的回答没有后续阶段, 不应硬算或拿来比较解码速度.

**递进追问与回答要点**: 所有 HTTP 状态都是 200, 是否可以认为没有失败? 还要按当前 API 插件检查响应内容、流中的错误及正常结束情况. 当前固定源码提交就包含对 200 流内错误的处理修正. 判断应以请求实际是否正常完成为准, 不能只看 HTTP 外壳.

**易错回答与判断依据**: “TTFT 好就代表工单完成快”漏了多步等待. “平均吞吐高就能满足业务”漏了长尾与错误. 本文未执行真实性能压测, 参考答案描述的是源码机制和验证方法, 不提供生产容量结论.

来源: [压测统计](https://github.com/modelscope/evalscope/blob/3ff0a0c425cc89cec91a5d48141e22a61ce53a9b/evalscope/perf/utils/benchmark_util.py), [本次固定提交的流内错误修正](https://github.com/modelscope/evalscope/commit/3ff0a0c425cc89cec91a5d48141e22a61ce53a9b).
