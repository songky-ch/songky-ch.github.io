# RAG benchmark 面试记录: 我怎样解释参考、版本与退化

<p class="article-kicker">表达记录 · R5 · 从已有测试经验延伸的方案</p>

我的实际经验主要是光电维护 Web 平台的功能测试、Postman 接口核对和 SQL 数据比对. RAG benchmark 尚未在工作中落地, 所以下面的回答会明确区分已做过的核对习惯和计划采用的评测设计. 我不会把合成样本、示例通过率或待验证的流程写成个人项目成绩.

[正文](../../learning/ai-evaluation/rag-benchmark-design.md)使用 D3 的六条资料设计了九条任务. 这里保留两条讨论主线: 开发视角关心评测能否公平复现, 测试视角关心覆盖、判定与退化是否可信.

## 开发视角: 知识库持续更新, benchmark 怎样保持可比?

**关注点.** 任务参考是否独立, 源资料与索引是否一致, 是否知道本次到底改变了哪个条件.

**表达顺序.** 我先讲完整版本清单, 再用一次日期更正说明受影响的任务, 最后解释比较方式和重放限制.

**我的回答.**

我会把 benchmark 看成带运行条件的一组测试任务. 问题文本之外, 还要保存源快照、账号权限、时间解释、独立参考和评分规则. 被测方案的检索、索引、生成提示词和模型配置另行记录. 否则同一道“昨天有哪些问题”, 今天运行与明天运行就已经不在比较同一件事.

我的合成案例里, C102 在 v1 的发生时间是 2026-10-20 14:30. 问“10-21 之前有哪些 A/X 的生产问题”, 参考集合是 C101、C102. 如果假想 v2 将 C102 更正为 10-21 08:30, 参考集合就只剩 C101. 日期字段查询、列表、计数和“昨天”的自然日查询都要更新. 根因状态虽然没变, 引用的源记录版本也要复核.

因此我会让参考依赖源记录版本, 让索引构建依赖源快照, 并在运行前验证两者一致. 我不会从这次检索结果反推标准答案, 因为漏检的记录可能就此被从参考里抹掉. 对精确数量, 还需要完整范围保证; 取到两条相似片段不能证明总量只有两条.

比较算法 A、B 时, 我会先保证它们使用同一源快照、任务和评分口径. 如果本次改动是切片或检索策略, 两边可以有不同索引, 但它们必须从同一源资料构建, 差异需要登记. 资料也变化时, 我会在 v1 下比较 A/B, 再在 v2 下比较 A/B, 不用 A/v1 的分数直接对比 B/v2 并归因给算法. 旧快照无法重放时, 我会明确说明这次只能观察综合变化, 不能得出单一因素结论.

**进一步讨论.**

| 追问 | 我会补充的判断 |
| --- | --- |
| 文案不一样, 就要判回答错误吗? | 不要求逐字一致. 先看对象、必答字段、证据、禁止断言与行为是否满足; 语义判断保留依据 |
| 换了评分模型, 分数还能比较吗? | 先固定评分条件, 或将两版保留的轨迹用新评分器一起重评; 单独给新版换裁判会混入测量变化 |
| 资料含有评估问题的答案, 算泄漏吗? | 正常业务资料可检索是 RAG 的前提. 评测专用答案、问题或评分提示进入模型示例或索引, 才破坏这里想测的能力 |
| 固定正确上下文后得分很高, 能证明系统好吗? | 只能说明该上下文条件下的生成表现. 它跳过检索, 不能代替端到端报告 |

**我需要避免的判断.** 给任务文件起一个 v1 名称并没有冻结外部知识库. 新旧源资料、索引和参考混用时, 即使分数有小数点, 结论仍可能无法解释. 我也不能承诺只要固定随机种子就能完全复现模型输出.

## 测试视角: 怎样证明覆盖有意义, 而且没有被总分误导?

**关注点.** 问题是不是只覆盖容易答的事实, 参考是否可信, 未决结果是否被藏起来, 退化是否影响实际业务.

**表达顺序.** 我先按预期行为组织样本, 再讲开发集与冻结集的划分, 用成对结果说明报告, 最后回到自己尚未验证的部分.

**我的回答.**

我会先把业务问题分成可按资料回答、需要保留未知、需要澄清、权限不允许和依赖不可用几类. D3 的九条合成任务覆盖字段、时间列表、精确计数、跨记录关联、未知根因、相对日期、模糊日期、越权和超时. 它们的通过条件不同, 不能统一要求模型说出一个确定答案.

比如 C102 原因待确认, 正确行为是保留未知. 检索超时则是本次系统无法查询, 不能说 C102 不存在. 问“前几天”且没有产品默认规则时, 我会期待澄清日期. 对未授权 C104, 不只看最终回答是否泄漏, 还要检查它是否已进入模型上下文. 这些检查都需要事先确认产品约定.

扩充真实任务时, 我会结合授权脱敏请求、历史缺陷与风险样本, 保留类型分布和来源. 开发集与冻结评估集先按语义任务族和同源改写分组, 避免“什么时候发生”和“发生日期是什么”分到两边, 造成表面上的未见样本. 九条公开演示题无法证明泛化, 我会直说它们用于校准判定口径.

版本报告会保留每条任务的状态变化. 在一个独立假想的百条完整评分报告里, 78 条两版都通过, 4 条从通过变失败, 8 条从失败变通过, 10 条都失败. A 是 82%, B 是 86%, 净增 4 个百分点. 但我更需要核查那 4 条退化是否涉及权限泄漏、错误根因或错误计数. 发布判断不能只看净增长.

如果出现未决评分, 我会报告全部样本数、已确认通过数、已判定数、未决数和原因. 运行器故障、被测系统失败、评分器失败分开记录. 对随机输出再安排重复运行, 保留逐条通过频次, 不能拿挑选出的最好一次替代报告.

**进一步讨论.**

| 追问 | 我会补充的判断 |
| --- | --- |
| benchmark 要多少条才够? | 我目前没有真实请求分布, 不能给通用数量承诺. 先保证任务类型、风险与判定明确, 再看各类样本量和重复运行的不确定性 |
| 是否可以全部让 LLM 生成题和答案? | 可以辅助提议, 但独立参考仍要回到冻结源资料核对. 同一个模型自出题自判分不能证明业务正确 |
| 回答“无法确定总数”是否通过? | 在缺少完整计数依据时体现诚实, 但精确计数任务仍未完成. 分项通过不能冒充业务能力通过 |
| 已经看过冻结集的失败, 还能使用吗? | 可以继续作为回归集. 多次针对性调优后, 需要另留未参与调优的任务检查泛化, 不继续声称完全独立 |
| 4 条退化都是 LLM 裁判误判呢? | 保存原始轨迹与依据, 人工复核争议并校准裁判. 修订评分后按相同规则重评两版, 不只给希望获胜的一版改分 |

**我需要避免的判断.** 一百条问题不自动等于覆盖充分, 通过率也不是准确率的通用替代词. 我会说明每条任务怎样算通过、分母是否包含未决, 以及各风险类型的结果. 这些仍是我从接口和 SQL 核对习惯延伸的设计, 尚未在真实项目中验证收益.

## 术语与依据

| 名称 | 我在面试中的含义 |
| --- | --- |
| Benchmark | 带任务、环境、参考和评分约定的评测基准 |
| Independent reference | 独立参考, 不从被测系统输出反推 |
| Snapshot / Index | 源资料快照 / 从快照构建的检索索引, 两者分别记录 |
| Split / Leakage | 集合划分 / 评测专用信息进入被测输入的泄漏 |
| Paired comparison | 相同任务和条件下逐条比较版本变化 |
| Review | 尚未完成可靠判断, 与已确认失败分开保留 |
