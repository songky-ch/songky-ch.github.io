# Agent 评测体系面试: 双环、证据与可信判定

先说清用户要办成什么, 再拿报告和调用记录验证, 最后解释改动带来了什么变化. 这是评测智能体 (Agent, 会按任务选择工具并执行动作的系统) 时贯穿六道题的思路. 以下是可以用于练习表达的技术参考答案, 不代表任何人的项目履历, 也不保证真实面试题频率.

对应[学习文章与可执行练习](../../learning/ai-evaluation/meituan-agent-evaluation-overview.md). 本篇可独立阅读; 六道题分别从“怎样实现”和“怎样证明它可信”展开. 2026-10-19 按新规范更新表达和图解, 来源核查与原运行记录仍保留 2026-10-17 的范围.

来源与范围: 美团《Agent 评测白皮书》系列01, 2026-09-10 发布版本的可提取正文; Anthropic 的评测随机性、评判器与环境设计段落; 开放遥测体系 OpenTelemetry 的追踪定义. 最后核查 2026-10-17. 小红书配图、美团图像中的表格及该系列其他篇章未逐图或逐篇读取. 所有数值、门店、字段和脚本是教学补充.

验证状态: 配套 Python 3.9.6 确定性合成练习已运行, 含五类样本、两个版本及断言. 未连接真实模型、业务系统或线上实验. [本次结果](/examples/meituan-agent-evaluation-overview/practice-results.txt).

## 开发专家视角

### 1. 如何把“为 A 店生成销售报告”变成一个能回归的评测任务?

**考察点**: 能否把业务要求写成任务 (Task), 能否从请求一直查到最终交付, 即端到端检查 (End-to-End / E2E), 并保留必要过程约束和回测条件.

**回答结构**: 固定业务目标 → 固定输入与环境 → 定义结果和必要过程约束 → 留下运行证据 → 对照版本.

**参考答案**: 我会把任务写成“按指定周期查询 A 店销售并生成可读取的报告”, 固定门店、周期和销售快照. 成功条件至少包括报告存在、门店与周期正确、数据与快照一致; 如果任务要求查询某个授权数据源, 再检查该来源及参数. 不能只检查回复里是否出现“已完成”, 因为口头承诺不等于产物落地.

执行时记录输入、工具调用、返回数据和报告引用, 再由独立检查逻辑验证产物. 把逐项评价标准 (Rubric)、数据与环境都固定下来, 再让两个系统版本执行同一任务. 每次从干净状态开始, 防止旧报告或缓存让新版虚假通过. 美团第二节给出任务、资产和回测结构; 实际约束应由业务合同决定, 不能照抄本文工具名.

**递进追问与回答要点**: 如果存在多条正确工具路径, 是否逐步比对唯一轨迹? 不应该. 应检查授权范围、关键事实和必要动作等约束, 接受等价合法路径. 只有当顺序本身是需求, 例如先确认再提交, 才强制验证顺序.

**易错回答与判断依据**: “让模型打一个综合分即可”没有产物证据和可复现输入; “过程和示范不同就是错”会把合法策略误拒绝. 能指出最终状态、证据来源与必要约束, 才构成完整任务设计.

![一份任务对齐交付检查与过程检查](/images/meituan-agent-evaluation-overview/task-contract.svg)

读图从同一份 A 店任务往两路走: 报告检查证明交付, 工具记录检查证明必要过程. 两种结论分别保存, 联合判定再按任务要求处理未知项.

### 2. 在线出现坏样本, 如何决定修 Agent 还是修评测?

**考察点**: 能否用独立事实判断错误, 分别修系统与修标准, 并把结果送回下一次验证. 这两条持续回流的路径就是反馈循环 (Loop).

**回答结构**: 保存可关联样本 → 核对业务事实 → 检查 Agent 行为 → 检查评分标准 → 固定标准回测.

**参考答案**: 先拿到同一任务的输入、工具参数、返回数据与产物, 用业务成功条件复核. 若系统查了 B 店却要交付 A 店报告, 是 Agent 缺陷; 若评分器因为回复含“已完成”而给它通过, 同时是标准缺陷. 两个修复流程可以并行存在, 不能用互斥分类掩盖其中一个问题. 若报告完全正确, 只是措辞为“报告已生成”却被拒绝, 就先修标准, 而不是强迫系统背评分口令.

复核后的样本连同原因、来源和标准版本入集. 修 Agent 后用固定标准做回归; 修标准后应在同一批旧记录上复评, 量化哪些结论改变. 再用新标准统一评两个 Agent 版本, 才能区分“尺子变了”和“能力变了”. 这是对美团 1.2 与 4.3 的工程化教学展开.

**递进追问与回答要点**: 如果看不到工具输入呢? 将对应过程项记为未知, 先补证据. 有独立结果证据时可保留结果结论, 但不能据缺失轨迹声称参数选错. 若缺口影响发布所需判定, 门禁应暂停.

**易错回答与判断依据**: “评分低就改提示词”假设评分器绝对正确; “人工认为没问题就删样本”会丢掉标准偏差的证据. 好答案能保存分歧, 分别定位被测系统、评判逻辑和数据缺口.

![证据齐全后分别判断系统与评分规则是否需要修复](/images/meituan-agent-evaluation-overview/rubric-routing.svg)

读图用“查 B 店却回已完成”走一遍: 业务错与评分误放行同时成立, 两路都要改. 缺日志的样本先走未知出口并补采集, 不强行给它归因.

### 3. 多轮会话跨工具服务, 怎样保存能支持归因的证据?

**考察点**: 怎样把多轮会话 (Session) 接起来, 让一次执行追踪 (Trace) 包含各操作跨度 (Span), 并通过上下文传播 (Context Propagation) 关联跨服务操作.

**回答结构**: 区分关联层次 → 保存状态变化 → 关联工具操作 → 对照最终状态 → 逐层定位.

**参考答案**: 我会先分清“同一段会话”“同一个业务目标”和“这一轮执行”. 应用层分别用 `session_id`、`task_id`、`turn_id` 记录这些关系. 每轮可以有独立 `trace_id`, 其中模型调用和工具操作再用跨度标识与父子关系关联. 跨服务传播追踪上下文, 必要时关联独立或异步执行. OpenTelemetry 定义了跨度、上下文和链接; 会话层次是本文教学设计, 不是其强制字段.

例如第一轮问“上周销售”, 第二轮说“改成本周, 仍看 A 店”. 我会核对第二轮可用输入是否包含修正后的日期, 再查工具实际参数、返回数据与报告周期. 若传入工具的是上周, 回查约束更新和参数构造; 若参数为本周却返回上周数据, 排查工具端处理. 若数据正确而报告仍写上周, 排查产物生成. 只看最后回复无法做这种定位, 第一处异常也需要额外证据才能认定根因.

**递进追问与回答要点**: 改为异步生成报告后, 没有父子跨度怎么办? 保留业务任务标识, 并用合适的跨度链接建立因果关联, 记录提交时间与产物完成状态. 不靠时间相近推断两条记录属于同一次任务.

**易错回答与判断依据**: “一个会话等于一条 Trace”把业务会话和执行粒度绑定; “采集模型所有思考就能定位”没有可实施的证据契约. 正确回答应指向可获得的输入、输出、动作与状态, 并明确关联方式.

![从第二轮条件沿工具、数据和报告定位偏差](/images/meituan-agent-evaluation-overview/evidence-chain.svg)

读图跟着“改成本周, 仍看 A 店”走, 对齐工具参数、返回数据和产物. 底部每种异常指向应回查的证据, 第一处异常仍需复现确认根因.

## 测试专家视角

### 4. 怎样证明评分器识别的是业务质量, 而不是表面措辞?

**考察点**: 有没有独立参考判定, 能否用正反例区分把失败判成通过的误放行 (False Accept) 和把正确结果判成失败的误拒绝 (False Reject).

**回答结构**: 准备独立参考事实 → 构造正反例与等价变体 → 对比逐项结论 → 检查分歧 → 回归标准.

**参考答案**: 我会让“内容是否正确”和“回复怎么说”分别变化. 先准备成功、真实失败、合法措辞变化和证据不足四类记录. 在本文窄场景中, 参考判定直接来自固定快照、工具参数和产物, 因而不依赖另一个模型的意见. 固定标准为“回复含已完成”会接受错店与无产物, 也会拒绝内容正确的同义回复. 这些反例证明评分器在利用无关表面特征.

配套五条合成记录里, v1 的四条证据完整记录中有两次误放行和一次误拒绝, 另有一条证据不足. v2 修掉门店错误后, 误放行减少为一次, 误拒绝仍为一次. 这里只报告计数, 因样本是人为构造, 不能把它解释为线上误判率. 真正校准时应对有代表性的样本独立标注与复核, 同时检查人之间及人与评分器之间的分歧.

**递进追问与回答要点**: 如果两个标注人也不同意呢? 先定位标准歧义、上下文缺失或事实争议, 补充明确条件并保留裁定记录. 一致性高不必然代表正确, 仍要核对业务事实; 也不能把多数票当作所有任务的真值来源.

**易错回答与判断依据**: “测一批随机样本, 看平均分”缺少独立参考判定; “让同一个模型再评一次”不排除共同偏差. 好答案能用受控措辞变体与结果反例, 证明标准对什么敏感、对什么不敏感.

![同一批记录横向比较标准, 同一标准纵向比较版本](/images/meituan-agent-evaluation-overview/controlled-comparison.svg)

读图横向比较只换规则, 纵向比较只换系统版本. 左上 3/4 与右下 3/4 虽然同分, 隐藏的问题却不同, 不能据此声称系统毫无变化.

### 5. 通过数从 2/4 提高到 3/4, 为什么仍不能认定可以上线?

**考察点**: 指标分母、证据覆盖率、硬约束、回归与业务外推边界.

**回答结构**: 解释改进对象 → 查看未解决样本 → 核对覆盖与门禁 → 区分本地改进和业务收益.

**参考答案**: 还不能放行. 得分只说明门店问题修好了: 同样四条证据完整样本, 在同一新标准下, 通过数从 2 变成了 3. 但 `no_artifact` 仍失败, 另一条 `missing_trace` 的联合判定仍未知. 本例门禁要求全部五条有证据且通过, 所以两个版本都是 `BLOCK`. 这是练习声明的硬约束, 不是推荐所有业务使用同一个阈值.

报告中应并列呈现可判定样本通过率 3/4、证据覆盖率 4/5、失败原因与未知原因. 不应把未知样本从所有分母里悄悄删除. 如果业务只要求最终产物且已有可靠结果证据, 可以另报结果层通过与过程层未知; 发布判断仍由明确的业务条件决定. 五条合成样本也不能证明线上流量覆盖、延迟成本或业务收益.

**递进追问与回答要点**: 总体完成率下降, 每个任务类型的完成率都不变, 怎么排查? 固定分组口径比较任务占比及权重. 新增困难任务占比提高会拉低汇总值, 不能直接归因于新版退化. 同时保留分层样本量和失败证据, 避免只看总分.

**易错回答与判断依据**: “提高了 25 个百分点所以可以发版”忽略剩余硬失败和证据缺口; “未知都算失败”把质量缺陷与观测缺陷混成一个结论. 好答案能说明门禁条件, 同时保持指标可解释.

![保留失败与未知样本的五条任务发布门禁](/images/meituan-agent-evaluation-overview/release-gate.svg)

读图先检查证据覆盖, 缺失就补采集后重跑; 覆盖齐全再检查五条是否全过, 仍有失败就修复后重跑. 本例三条通过不会绕过任何一道检查.

### 6. 每个任务多跑几次, 什么指标能说明稳定性?

**考察点**: 能否分清一次试验 (Trial)、试验通过率 (Pass Rate)、多次至少成功一次的 pass@k 和多次全部成功的 pass^k, 并说清独立性与样本量限制.

**回答结构**: 明确业务成功事件 → 定义分子分母 → 声明随机性假设 → 选择指标 → 检查环境相关性.

**参考答案**: 如果关注一次试验成功占比, 报告通过次数除以试验总次数. 如果产品允许多次尝试并选出一个正确结果, pass@k 衡量 k 次至少一次成功; 如果要求多次运行都可靠, pass^k 衡量 k 次全部成功. 两者不等于把同一任务多跑 k 次后计算一个平均值. [Anthropic 指标说明](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)明确区分了这两个事件.

假设各次试验相互独立, 且成功概率都为 p, 即独立同分布 (IID), 则 pass@k 为 $1-(1-p)^k$, pass^k 为 $p^k$. p=0.75、k=3 时, 分别为 98.44% 和 42.19%, 单次通过率仍为 75%. 这些是概率算例, 不代表跑三次就能精确估计真实可靠性. 真实报告应说明试验次数、任务组成与不确定性, 并控制缓存、残留文件和共享依赖造成的相关性.

**递进追问与回答要点**: 同一工具故障导致全部试验失败, 能否断言模型能力下降? 不能. 应按错误证据先定位共享依赖, 记录故障环境, 再用已声明规则重测. 不能只删除失败结果来抬高通过率, 也不能把确定性回放当成多次独立模型试验.

**易错回答与判断依据**: “pass@3 就是三次中成功比例”混淆事件概率与经验平均; “多跑几次自动消除波动”忽略相关故障. 好答案能定义事件, 给出条件, 并说明数据如何采集与解释.

## 术语表

| 英文名称与缩写 | 中文含义 | 本文具体作用 |
| --- | --- | --- |
| Agent | 智能体 | 需要交付业务产物的被测系统 |
| Task | 任务 | 固定输入与成功标准的评测单元 |
| End-to-End / E2E | 端到端 | 检查最终业务目标是否完成 |
| Rubric | 逐项评价标准 | 识别业务约束与评分器缺陷 |
| Loop | 反馈循环 | 分别驱动 Agent 与评测系统修复 |
| Session | 会话 | 关联跨轮业务信息 |
| Trace / Span | 执行追踪 / 操作跨度 | 组织某次执行和具体操作证据 |
| Context Propagation | 上下文传播 | 关联跨服务操作 |
| OpenTelemetry | 开放遥测规范与工具体系 | 为追踪、跨度与链接提供定义 |
| False Accept / False Reject | 误放行 / 误拒绝 | 检查评分器相对参考判定的两类错误 |
| Trial / Pass Rate | 单次试验 / 试验通过率 | 描述重复运行及经验成功占比 |
| pass@k / pass^k | k 次至少一次成功 / k 次全部成功 | 区分多次尝试能力与稳定成功要求 |
| IID | 独立同分布 | 概率算例成立的条件 |
