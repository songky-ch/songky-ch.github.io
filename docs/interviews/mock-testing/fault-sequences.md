## 开发专家视角

### 怎样验证一个只读接口第一次超时, 第二次成功?

**关注点**: 依赖边界、异常与重试策略、精确调用证据.

**表达顺序**: 先定策略 → 保留被测逻辑 → 注入顺序 → 同查结果与调用.

**我的回答**: 先明确这是 D1 只读查询的示例策略: 总共最多两次尝试, 第一次 QueryTimeout 后申请等待 0.2 秒再试. 我保留真实的重试包装函数, 把下游 fetch 换成按顺序抛出超时、返回两条记录的替身, 把等待函数换成可记录参数的替身. 预期返回成功数据, fetch 恰好调用两次且参数相同, pause 只调用一次且参数为 0.2. 这样才能区分真正执行重试与直接伪造成功. 这些是拟采用的方法, 不是已经完成的生产实践.

**进一步讨论**: 如果使用 assert_has_calls 验证两个调用, 足够吗?

不够证明没有额外调用. 它允许序列前后还有其他调用. 本例可直接比较完整 call_args_list, 或结合精确 call_count. 即使最后得到成功结果, 三次调用也违反两次尝试的约定.

**我需要避免的判断**: 把被测重试函数直接 Mock 成成功, 只能证明调用者接受成功值, 无法证明重试逻辑. 把两次尝试说成两次重试, 也会把总调用数算错.

## 测试专家视角

### 除了先失败后成功, 还要检查哪些出口?

**关注点**: 异常覆盖、空结果与坏结构的区别、状态隔离.

**表达顺序**: 列条件 → 给可控返回 → 预期次数和终态 → 检查测试污染.

**我的回答**: 我会分别准备首次成功、连续两次超时、合法空列表和错误返回结构. 首次成功只调用一次且不等待; 连续超时调用两次、等待一次并返回 unavailable; 合法的 total=0 和 items=[] 是查询成功但没有记录, 不应重试; 缺少契约字段则返回 invalid_payload, 也不应借重试掩盖接口变化. 每条用例新建替身和数据, 避免上一条消耗了顺序返回列表, 导致下一条从第二项开始.

**进一步讨论**: reset_mock 能让顺序脚本从头再来吗?

默认 reset_mock 清理调用记录, 不会把已消耗的 side_effect 迭代器倒回去. 本例直接为每条用例重新创建 Mock 和脚本. 脚本耗尽出现 StopIteration, 应先排查多调用或复用污染, 不把它误报成业务超时.

**我需要避免的判断**: 把所有异常都吞掉并返回成功, 会使测试失去定位能力. 本例只重试明确的 QueryTimeout; 其他未约定异常另行暴露, 不能自动归为可重试.

### Mock 立即抛超时, 能证明真实 3 秒超时配置生效吗?

**关注点**: 逻辑测试与真实网络等待的证据边界.

**表达顺序**: 区分事件和时间 → 说明可证明部分 → 指出还缺的证据.

**我的回答**: 不能. 立即抛异常模拟的是“调用方收到了超时信号”, 能验证异常后走哪个分支. pause 收到 0.2 也只证明申请了这个等待, 不证明真的等待了 200 毫秒. 要验证真实客户端 3 秒超时, 需要受控延迟服务和实际客户端, 说明连接/读取/总预算的具体含义, 记录时钟和误差范围. 单元层的快速异常测试与集成层的真实超时测试回答不同问题.

**进一步讨论**: 可以把这里的重试直接迁移到单次工具 Agent 吗?

不能. D4 约定一次业务派发, 超时也已经消耗这次机会, 应诚实说明没有拿到结果. 写入超时还可能已提交, 不能凭没收到响应就自动重试. 重试授权、幂等和状态确认要另按契约设计.

**我需要避免的判断**: 把 Mock 测试耗时当成接口延迟, 或把只读重试推广到写入与单次调用 Agent, 都扩大了证据和策略边界.

## 术语与依据

| 英文名称与缩写 | 中文含义 | 本篇具体作用 |
| --- | --- | --- |
| side_effect | 顺序行为 | 每次调用消耗一项或抛异常 |
| call_args_list | 完整调用记录 | 核对参数、顺序和额外调用 |
| Retry / Timeout | 重试 / 超时 | 区分再次尝试与失败信号 |
