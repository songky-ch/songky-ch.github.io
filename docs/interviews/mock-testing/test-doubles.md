# 怎样解释 Mock、Stub、Fake 与测试边界?

<p class="article-kicker">第二批 · M1 面试专题</p>

配套学习: [依赖还没准备好, 我怎样继续测试](../../learning/mock-testing/test-doubles.md). 参考回答表达技术理解, 不把学习示例改写为个人已经完成的项目实践.

## 测试视角: Mock 测试究竟在测什么?

考察能否指出真实执行的对象与被替换的依赖. 回答按“测试目标 → 替换位置 → 两类断言 → 未覆盖范围”展开.

### 可以这样回答

“它不是测试假数据本身, 而是让依赖按指定方式响应, 再看真实的被测代码能否正确处理. 例如摘要程序依赖生产问题查询, 我固定返回两条记录, 让摘要逻辑真实运行, 检查它是否输出正确数量和编号.

“若目标还包含传参, 我会同时断言查询函数收到正确局点、客户和调用次数. 这能发现固定返回掩盖的参数错误. 但查询服务的权限、SQL 和网络没有执行, 仍需要相应的集成测试.”

### 追问: 如果把摘要函数也 Mock 掉呢?

如果测试目标就是摘要逻辑, 把它替换掉会跳过真正想验证的部分. 断言固定返回只是确认配置与预期一致. 如果另一条测试的目标是摘要的调用者, 摘要才可能成为合理的替换边界. 是否合适取决于被测对象, 不是函数名字.

## 开发视角: Stub、Fake 和 Mock 怎样选择?

考察各自解决的问题与维护代价, 不要求死背术语. 先讲需要控制什么, 再讲例子和局限.

### 可以这样回答

“只需要稳定输入时, 我用一个固定返回的桩. 需要同一组小数据根据不同条件返回不同结果时, 可以用简化实现. 需要确认调用方式时, 则记录并核对调用参数和次数. 三种能力可以结合.

“例如固定桩对 X 客户和 Y 客户都返回两条, 能测摘要输出, 却可能漏掉传参错误. 小型内存实现能让 X 返回两条、Y 返回一条. 调用断言则直接检查到底传了谁. Fake 需要维护自己的逻辑, 不能让它长成第二套完整生产系统.”

### 追问: Python Mock 类只设置返回值, 算哪一种?

从本次用途看, 它主要扮演提供预设回答的桩. `Mock` 是库的类名, 与严格术语分类不能机械一一对应. 再增加调用断言后, 它同时承担交互验证. 解释测试目的比争论类名更重要.

## 测试视角: 替身用例全通过, 联调却失败, 可能是什么问题?

先检查是否真的执行了预期的被测代码, 再核对替身契约和真实返回. 例如真实服务把字段改为 `count`, 替身仍提供 `total`, 局部测试会继续通过. 又如真实认证、序列化和异常路径没有经过替身测试, 联调失败可能就在这些边界上.

追问“多加一百条固定返回用例有用吗”时, 应回答数量本身无法弥补未覆盖的路径. 需要针对契约变化和真实依赖补充有效证据, 而不是把所有绿色结果相加当成整体质量.

## 术语与依据

| 名称 | 含义与用途 |
| --- | --- |
| Test Double | 替身总称, 提供可控依赖 |
| Stub / Fake | 预设返回与可工作的简化实现 |
| Mock | 记录交互并进行调用验证 |
| SUT | 真正需要执行和验证的被测对象 |
